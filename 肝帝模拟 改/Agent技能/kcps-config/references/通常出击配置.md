用这份规则指导 Agent 生成、修复或审计 KCPS 出击任务配置。目标是产出可以直接加载的 `.conf.json`，并且正确处理任务接取、海域带路、舰船装备、战斗策略、疲劳、终止条件和跨海域推进。

开始前必须阅读 [公共规则.md](公共规则.md) 和 [命名规则.md](命名规则.md)。活动海域必须改用 [活动海域出击配置.md](活动海域出击配置.md)，不得套用通常海域的等价船轮换和无锁船配船逻辑。任务实际是演习时改用 [演习配置.md](演习配置.md)，实际是纯编成时改用 [编成配置.md](编成配置.md)；这些规则共用 `../scripts/poi-kcps-api` 的库存、结构归一化、配装审计和配置校验工具。

## 使用时机

当用户要求以下任一事项时使用：

- 为舰 C 任务生成 KCPS 出击配置。
- 修复 KCPS 出击配置卡住、走错路、装备为空、终止条件错误等问题。
- 把多海域任务打包成一个配置文件。
- 审计已有出击配置的战斗策略、夜战策略、编成/改装字段或总控关联。

## 出击输出差异

- 种类固定为中文 `出击`；文件名为 `<JST_YYYYMMDD> <频次> 出击 <任务名>.conf.json`。
- 每个海域或阶段是独立配置，配置名为 `<频次> 出击 <任务名> <海域/阶段>`。
- 多海域任务打包在同一配置文件中，但各配置只包含本海域或阶段相关的执行单元。
- 其余输出位置、JST、频次证据、文件卫生和术语遵守公共规则。

示例：

```text
<WORKSPACE_ROOT>\<JST_YYYYMMDD> 单次 出击 鎮守府近海海域の哨戒を実施せよ！.conf.json
```

## 必须先确认的信息

生成前必须搞清楚：

- 游戏内任务编号 `api_no`、准确日文任务名、当前任务状态。
- 每个海域、所需次数、要求胜利等级、是否必须 boss 或特定节点。
- 任务要求的旗舰、舰种、指定舰、舰队数量、速度、索敌、制空、运输桶、大发、电探等条件。
- 路线分歧、节点类型、是否可能绕路、是否有随机进 boss 概率问题。
- 用户账号中可用舰船 ID、装备库存、改修/锁定/消耗限制、当前舰队状态、疲劳、入渠、远征占用。
- 是否需要并行。如果要并行，舰船不能和其他正在跑的任务冲突；装备通常可以拆换，但仍要避免同一配置内部竞争失败。

## 资料查询顺序

> **铁律：路线分歧条件与推荐编成必须来自网上攻略，禁止凭推测设计路线。** 规划任何海域的路线/编成前，先查网上攻略（日文 wikiwiki、kcwiki、TsunKit/KCNav，以及当天更新的攻略博客/聚合站），提取确切的分歧条件（各节点进入所需的舰种/隻数/速力/索敵/制空）与推荐编成例，**交叉验证 ≥2 个来源**，把确切条件写进 `说明` 执行单元，并逐条核对实际编成是否满足。凭推测拼路线会让出击反复走错分歧、到不了目标点（典型：开路/ギミック海图，舰种隻数或索敵不达标就永远卡在死路分支）。

> 路线验收必须从出发点开始逐个分歧重放，并将**舰种判定**和 UI 中看似相近的船型严格区分。例如 5-3 的 G 点只要含航空战舰就强制进入 J；`大和改二重`是航空战舰，而`大和改二`是高速战舰。若声明 D-G-I-O-K-E-Q，校验器必须拒绝任何含航空战舰的编成，不能仅因条件策略覆盖 I/K/Q 就判定路线正确。

1. 任务条件以日文 wikiwiki 为准。
2. 海域路线和节点先查 TsunKit nav：`https://tsunkit.net/nav/`。
3. 路线分歧、敌编成、特殊规则再用日文 wikiwiki 交叉确认。
4. 制空、索敌、陆航航程、舰载机/装备效果可用社群常用工具辅助，例如制空権シミュレータ、作戦室、KCNav/TsunKit，但结论仍要回到日文 wikiwiki 或游戏 API 校验。
5. NGA/中文攻略只能作为配船配装参考，必须适配用户账号并回到 wiki/TsunKit 验证。
6. 英文 wiki 或其他语言资料只作为旧机制的低优先级辅助，不作为新任务、新海域、限时任务和特殊规则的主依据。
7. 舰船与装备状态优先从 poi/KCPS API 和本地工具查，不要凭记忆猜。

常用本地工具：

```powershell
$SKILL_ROOT = '<SKILL_ROOT>'
$WORKSPACE_ROOT = '<WORKSPACE_ROOT>'
$env:KCPS_WORKSPACE = $WORKSPACE_ROOT

# 从本次设置指定的默认配置文件中查找某海域的出击配置
pwsh -ExecutionPolicy Bypass -File (Join-Path $SKILL_ROOT 'scripts\poi-kcps-api\inspect\KCPS-FindSortie.ps1') -Sea 1 -Area 4

# 规范化出击战斗策略的机器可检查部分
pwsh -ExecutionPolicy Bypass -File (Join-Path $SKILL_ROOT 'scripts\poi-kcps-api\normalize\KCPS-NormalizeSortieStrategyRules.ps1') -Path (Join-Path $WORKSPACE_ROOT '<JST_YYYYMMDD> 单次 出击 <任务名称>.conf.json')

# 为通常海域配置启用等价船疲劳轮换
pwsh -ExecutionPolicy Bypass -File (Join-Path $SKILL_ROOT 'scripts\poi-kcps-api\enable\KCPS-EnableEquivalentShipRotation.ps1') -Path $WORKSPACE_ROOT -CheckOnly
pwsh -ExecutionPolicy Bypass -File (Join-Path $SKILL_ROOT 'scripts\poi-kcps-api\enable\KCPS-EnableEquivalentShipRotation.ps1') -Path $WORKSPACE_ROOT

# 为出击后低疲劳受损船加入扔桶入渠恢复
pwsh -ExecutionPolicy Bypass -File (Join-Path $SKILL_ROOT 'scripts\poi-kcps-api\enable\KCPS-EnablePostSortieBucketDocking.ps1') -Path $WORKSPACE_ROOT -CheckOnly
pwsh -ExecutionPolicy Bypass -File (Join-Path $SKILL_ROOT 'scripts\poi-kcps-api\enable\KCPS-EnablePostSortieBucketDocking.ps1') -Path $WORKSPACE_ROOT

# 为使用陆航出击/防空的海图加入出击后陆航休息和补给
pwsh -ExecutionPolicy Bypass -File (Join-Path $SKILL_ROOT 'scripts\poi-kcps-api\enable\KCPS-EnablePostSortieLandBaseRest.ps1') -Path $WORKSPACE_ROOT -CheckOnly
pwsh -ExecutionPolicy Bypass -File (Join-Path $SKILL_ROOT 'scripts\poi-kcps-api\enable\KCPS-EnablePostSortieLandBaseRest.ps1') -Path $WORKSPACE_ROOT

# 首选收尾入口：串联全部规范化/增强工具，再做二次幂等检查、任务 ID 与总校验。
pwsh -ExecutionPolicy Bypass -File (Join-Path $SKILL_ROOT 'scripts\poi-kcps-api\validate\KCPS-FinalizeSortieConfig.ps1') -Path (Join-Path $WORKSPACE_ROOT '<JST_YYYYMMDD> 单次 出击 <任务名称>.conf.json')
pwsh -ExecutionPolicy Bypass -File (Join-Path $SKILL_ROOT 'scripts\poi-kcps-api\validate\KCPS-FinalizeSortieConfig.ps1') -Path (Join-Path $WORKSPACE_ROOT '<JST_YYYYMMDD> 单次 出击 <任务名称>.conf.json') -CheckOnly
```

## 新实装或 wikiwiki 未更新任务

新实装任务经常会出现 wikiwiki 条目还没完全进入正文、搜索结果先被攻略站收录的情况。处理顺序如下：

- 任务 ID、频次、缓存刷新和来源冲突处理先遵守公共规则。
- wikiwiki 仍是长期基准；但当 wikiwiki 尚未收录当前新任务，而多个当天更新的攻略站和游戏 API 详情一致时，可以用它们交叉确认海域、编成、胜利等级和前后置。
- 攻略站只用于补足 wikiwiki 暂缺的信息，例如新任务的海域、路线和编成例；路线和节点仍要回到 TsunKit/nav 或 wikiwiki 海域页确认。
- 如果 API 详情没有写胜利等级，攻略站间出现 A 胜/S 胜分歧时，保守按更高胜利等级配置终止条件，除非用户要求省资源或已有实测确认 A 胜即可。

## 决策循环

不要把配置设计拆成“先决定编成，再决定配装，再决定阵型”的流水线。舰船、顺序、装备、阵型、夜战、特殊攻击、烟幕、陆航、支援和终止条件必须一起迭代推演，直到能解释“为什么这样比替代方案更好”。

推荐循环：

1. 读任务硬条件：任务指定舰、舰种、旗舰/2番舰/随伴位置、胜利等级、次数、海域阶段。
2. 读海域难点：路线分歧、boss 强度、道中威胁、空袭、潜水、夜战、对地、PT、索敌、制空、是否有弹药/燃料惩罚。
3. 先列可行舰队骨架：满足任务与带路，并标出每艘船可能承担的角色，而不是立刻锁死编成。
4. 同时推演配装与顺序：装备会改变制空、索敌、射程、夜战能力、特殊攻击、AACI、对潜、对地和 PT 对策；顺序又决定夜战出手、警戒阵分工、特殊攻击位置和昼战射程抢手。
5. 同时推演阵型和夜战：如果要用特殊攻击，必须自己决定在哪个点使用、为什么该点最难、所需阵型是否会降低常规火力或影响警戒/反潜；如果只需 A 胜或白天稳定，不要无脑夜战。特殊攻击和阵型不直接消耗稀缺物品，不需要先问用户，但必须能解释采用或不采用的理由。
6. 判断烟幕、支援、陆航、消耗品是否必要：只有当它们能显著改变通过率或 S/A 胜稳定性时才考虑。烟幕不直接消耗装备，应该由 Agent 根据使用节点、敌电探风险、我方命中损失和是否影响击杀自行决定；决定使用或不用都写清理由。消耗品默认不使用。
7. 做替代方案比较：至少比较一个保守省资源方案和一个高通过率方案。差距明显时写进 `说明`；只有涉及可消耗装备/道具时才先询问用户。
8. 最后才写 KCPS JSON，并再次核对编成、改装、出击策略、终止条件和说明是否与决策一致。

满足任务舰种要求不等于路线可达。按本次分歧证据逐节点核对舰种、数量、速力、索敌与阶段优先级，计算额外战斗的油弹和生存代价，再一起调整编成、舰船顺序与配装。不把其他任务的固定舰队或路线作为当前任务的默认方案。

每个配置交付前，心里必须有这张决策表：

```text
海域/阶段 | 难点 | 编成骨架 | 舰船顺序 | 关键装备 | 阵型/夜战 | 特殊攻击/烟幕/支援 | 消耗品 | 替代方案 | 采用理由
```

如果任何一列只是“沿用模板”而没有理由，就继续查资料或改配置。

**交付/审计前逐项自检（多段海图 P1/开路/P2/P3 每段单独核，别假设各段相同）：**

1. **路线覆盖**：每个战斗/选路节点都有条件策略（含 boss 点）；节点值用 KCNav 进入边 ID 对照路线规格。
2. **手动选路节点（針路選択 / 能動分岐）**：攻略标「能動分岐」的点必须有条件策略 + 非空 `DefaultWayPoint`（外切目标节点圆的矩形点击区），否则卡选路画面。
3. **编成 vs 路由分歧条件**：实际编成舰种/隻数/速力/索敵满足攻略给的路由条件；**多段海图逐段不同**，别拿上一段编成套下一段。
4. **终止**：boss 击沉用本段 boss 节点 + 攻略破坏次数；运输条用 `MapHp`/`OnAutoStop`；到达后显示标准归投终点页面的节点用 `StopIfArrivedEndPoint`，不显示该页面或尚未验证的节点才改用可靠的替代计数。`说明` 写的次数必须 = 字段值。
5. **制空**：用制空権シミュレータ / 作戦室核对 boss 制空门槛（确保 / 优势），别只凭 Memo 估算。
6. **阵型 / 夜战**：各点按敌编成 + 特殊攻击逐点推演。
7. **一致性**：`说明` 描述 vs 实际编成 / 字段一致；多段海图严防从上一段**复制错**（节点编号、boss 停止条件、编成都是常见踩坑）。

阵型不是默认值。每个战斗点都必须按敌编成、我方角色和特殊攻击推演：

- 水上+潜水混合 boss 或任务要求 S 胜时，不能无脑单纵。要比较单纵、复纵、梯形：单纵水上火力最高但反潜打折，复纵常用于兼顾水上清场和反潜，梯形常用于触发大和型/长门型等特殊攻击并兼顾一定反潜。
- 特殊攻击通常全程只能使用一次，且有阵型、旗舰/2号位/3号位、损伤、舰种和舰队形态条件。不能只因为带了大和/武藏、长门/陆奥、Nelson/Rodney 等船就选择对应阵型；必须先确认任务硬条件允许把触发船放到所需位置。若任务要求空母旗舰、指定船旗舰或指定 2 号位导致特殊攻击位置不成立，就不得把阵型理由写成“发动特殊攻击”，应改用复纵/单纵/其他阵型并写明“任务位置锁定，特殊攻击不可用”。典型例子：任务硬性要求空母旗舰时，即使 2/3 号位放大和/武藏，大和型特殊攻击也不会在 boss 触发；不能为了不存在的特殊攻击选择梯形阵。
- 若决定在 boss 用特殊攻击，编成和装备必须一起重排：触发船必须放在正确位置，倍率装备如徹甲弾、水上电探、测距仪等要给到参与攻击的船，并且道中点必须避免误触发对应阵型。若决定不用，也要说明不是因为遗漏。
- **特殊攻击的「舰队组成」条件必须查那个攻击本身的规则，不要拿别的攻击的规则套——不同特殊攻击的舰种限制不一样。** 关键区别：**大和型/长门型「一斉射」(大和タッチ/武大摸) 要求「水上艦6隻」，而这里的「水上艦」= 非潜水艦，空母（正規/装甲/軽空母）算水上艦**。所以 `戦艦2+空母1+軽巡1+駆逐2`、甚至 `戦艦2+空母4` 都满足 6 水上艦，**带空母照样能发大和タッチ**（攻略实证：高速+空優流就是 2战舰+4空母 + 武大摸）。**「排除空母系/潜水艦」是 Nelson Touch 的规则，不是大和型/长门型的**——别张冠李戴。大和タッチ的真正硬条件是：旗舰=大和改二/改二重（武蔵タッチ时武蔵改二）、2番(及3番)为指定战舰、旗舰/2番/3番**小破以下**、**梯形陣**（连合为第四警戒）。位置满足时，含空母的火力编成 boss **该用梯形发タッチ**，タッチ是无视制空的昼战大爆发，往往是 boss 主力输出。验证某攻击能否发动时，去 wiki 查它本身的发动条件，并用一个能跑通的实战编成印证。
- 阵型选择要和夜战一起判断。若 boss 需要 S 胜且可能残潜，阵型不足以处理潜水目标时，必须增加反潜手段或改阵型；若只要 A 胜，则可能不需要牺牲水上火力去追潜水目标。
- 说明执行单元必须写出关键点阵型理由，尤其是 boss、混潜点、夜战点、空袭点、潜水点、警戒阵点和特殊攻击点。
## 多海域任务结构

一个任务文件可以包含多个 KCPS 配置。普通海域按“每个海域一个配置”；如果同一海图有多段攻略、多个ゲージ、开路/解锁、P1/P2/P3 或多个任务目标点，则按“每个海域阶段一个配置”，不要把不同阶段揉进同一个总控。

- 不创建只有任务名、没有实际执行作用的配置。
- 不创建单独的 `收尾` 组，除非用户明确要求。
- 配置命名：`频率 出击 任务名 海域编号`。
- 多阶段海图配置命名：`频率 出击 任务名 海域编号 P1`、`频率 出击 任务名 海域编号 P2`、`频率 出击 任务名 海域编号 P3`；如果阶段目标不是普通 P 编号，可用 `开路`、`解锁`、`运输`、`5-6-3` 等明确后缀。
- 同一海图的不同阶段仍放在同一个任务配置文件内，只是拆成多个 KCPS 配置。
- 每个阶段配置只包含该阶段需要的执行单元、路线、终止条件、陆航和说明；不要让 P1 的总控或出击条件引用 P2/P3 的执行单元。
- 如果任务只要求某个海图的后续阶段，但账号还没开到该阶段，先从游戏 API 确认当前 gauge/阶段，再决定前置放置方式。默认把可复用或较复杂的前置血条/运输条/开路放入独立普通“攻略”配置文件，不套用任务舰船限制；任务配置只保留实际目标阶段并监听攻略文件的 `UserEvent`。若前置很短、用户需要一个可直接连续运行的任务文件，也可在同一文件加入独立的 `<阶段>前置` 配置，但必须满足：不套任务舰船限制、使用该阶段自己的路线规格与终止条件、在 `说明` 标明这是账号当前进度所需前置、只推进到任务目标可进入为止，不附带任务无关的后续开路/血条。
- 对通常海域的新多段攻略，P1、P2、P3、开路、到达ギミック都必须作为独立配置逐段设计。不要把“P1 输送 + 到 R 一次 + P2 战力”揉在一个总控里；每段都要有独立路线规格、终止条件、战斗策略和说明。
- 多阶段海域按当前开放条件拆分：运输、开路、后续血条等分别保存独立配置，再通过已经核对的完成消息串联。若任务仅要求后续某阶段，只把任务限制应用于该阶段，不回填到普通前置攻略中。阶段数量、目标点和解锁次数由本次数据确定。
- 执行单元使用短名：`总控`、`接任务`、`编成`、`改装`、`入渠`、`捞出`、`补给`、`出击`、`陆航休息1`/`陆航休息2`/`陆航休息3`、`扔桶`、`出击完成`、`说明`；活动通知名称按活动规则。
- 根据本次配置的编成流程决定是否需要 `预编成`；没有明确的清场或调整用途时不添加前置编成。

推荐配置内顺序：

1. `说明`：`MemoWorkflow`
2. `总控`：`RelationalSortieWorkflow`
3. `接任务`：`BasicAcceptQuestWorkflow`
4. `编成`：`BasicOrganizeFleetWorkflow`
5. `改装`：`BasicRefitEquipmentWorkflow`
6. `入渠`：`BasicDockingWorkflow`
7. `捞出`：`BasicDockingWorkflow`
8. `补给`：`BasicSupplyFleetWorkflow`
9. `出击`：`SimpleSortieWorkflow`
10. `陆航休息1`/`陆航休息2`/`陆航休息3`：`BasicOutfitLandBasedAirCorpWorkflow`，仅在对应基地航空队用于出击或防空时存在；尾号始终等于基地航空队编号，单队时也不省略 `1`
11. `扔桶`：`BasicDockingWorkflow`
12. `出击完成`：`SimpleRaiseUserEventWorkflow`，由本单元的触发条件判断目标达成，再发送完成消息；不需要对外通知的独立单图可省略。

### 出击循环只在第一步刷新数据（`RefreshDataBefore*`）

关联出击的已验证循环顺序是：`接任务 → 编成 → 入渠 → 改装 → 解体 → 补给 → (总控刷新) → 出击 → …`。每个会读游戏数据的执行单元都有一个「执行前先刷新数据」开关，字段各自命名：`BasicOrganizeFleetWorkflow.RefreshDataBeforeOrganize`、`BasicRefitEquipmentWorkflow.RefreshDataBeforeRefit`、`BasicSupplyFleetWorkflow.RefreshDataBeforeSupplyFleet`、`BasicDockingWorkflow.RefreshDataBeforeDocking`、`RelationalSortieWorkflow.RefreshDataBeforeSortie`、`RelationalExpeditionWorkflow.RefreshDataBeforeExpedition`。

**规则：整轮循环只需在第一步刷新一次，即只保留 `编成` 的 `RefreshDataBeforeOrganize = true`；其余所有 `RefreshDataBefore*` 一律设 `false`。**

- `编成` 是循环里第一个读船/装备数据的步骤（`接任务` 不读船数据），在它之前刷新一次就拿到了本轮最新的游戏状态。
- 后续 `改装 / 补给 / 入渠 / 扔桶 / 出击` 都在同一轮内紧接着跑，KCPS 会在本地跟踪这期间的状态变化，无需再各自向服务器重复拉取；多余的刷新只是徒增请求、拖慢循环、且服务器状态约 3 分钟才变一次。
- 生成配置时默认就按此设置；不要因为模板里 `改装` 默认开了刷新就保留。`陆航休息N` 同理保持 `RefreshDataBefore=false`。
- 校验器 `KCPS-ValidateConfig.ps1` 会检查：除 `RefreshDataBeforeOrganize` 外，任何 `RefreshDataBefore*` 为 `true` 都报问题。

## 说明执行单元

先满足公共 `说明` 规则；本节只补充出击配置特有内容。每个海域或阶段都要独立写任务目标、路线、胜利次数、风险和依据，不能只在文件级写一份笼统说明。

- 当前账号尚未开放海域、任务未出现在 API、地图阶段未知、前置条件未确认，但为了后续加载先预置配置。
- 配置偏离标准攻略模板，例如为了用户账号库存、疲劳、并行、不动远征船、KCPS 行为限制或装备数量不足而改用替代舰船/装备。
- 陆航点选坐标、节点 ID、夜战突入、终止条件、路线概率等来自图像目测、旧配置迁移或间接推算，而不是已验证字段。

写法要求：

- 说明必须具体到海域或阶段，不要只在文件级写笼统提醒。
- 明确写出“为什么这样配”和“风险是什么”，例如 `5-6 当前 API 未开放，仅按 wiki P3 boss Z 预置；需先完成 P1/P2/开路后再运行`。
- 如果配置使用了次优替代装备，要写清替代原因和可能影响，例如制空降低、夜战火力降低、索敌余量未知。
- 有舰载机、水战、水爆或陆航时，说明必须单独写“制空”小段：海域目标制空门槛、自己舰队无熟练最低制空、仅战斗机满熟练且其他飞机无熟练的制空、所有飞机满熟练的制空。默认可假设战斗机熟练度能维持到满，但不能默认舰攻、舰爆、水爆、喷气机等非战斗机都有熟练；如果配置依赖非战斗机熟练度，必须写明先刷熟练和被打空后的风险。
- 说明必须有 `【出击阈值】`，写清出击前入渠剩余 HP 上限、旗舰/伴随舰最低士气、阈值依据，以及是否为高士气单次出击。
- 通常海域不运行活动专用的复杂概率模拟，也不强制写 `【出击概率分析】`；按攻略、路线、制空、索敌和账号强度完成轻量校验即可。
- 审计时把编成船名对回 `编成.SelectShipArgs`，路线/节点值对回 `出击.Strategies[].Condition.Value`，击破次数对回总控字段，阵型对回条件策略；不一致时同步修实际字段与说明。
- 制空等数值无法当场复核时不要保留旧数字，改为明确待复核；来源记录在本次私人证据中，成品按复核需要保留来源。
- 禁止交付带有“未验证 boss 点 ID”“使用默认 boss 策略”“若 KCPS 未识别 boss 再手动确认”之类措辞的出击配置。无法确认游戏内任务 ID、地图点 `Condition.Value` 或 boss 进入边时，先拒绝生成或继续调查，不要输出可运行配置。
- 如果资料已确认，则不需要把常规打法重复写成长篇攻略。

## 士气阈值与循环策略

最低士气根据当前目标、舰队能力和用户的执行方式决定，不能从旧任务继承固定档位。声明阈值及其依据，并核对实际出击门禁。

`49` 是当前自然恢复可达到的上限。旗舰或伴随舰的最低士气超过该值时，关闭 `SleepUntilMoraleRecoveredFlag` 和 `SleepUntilFlagShipMoraleRecoveredFlag`，不能用自然等待实现高士气准备。

循环上限与士气阈值分别决定：一次出击、有限多轮或人工补充均应在当前计划说明。需要手工准备或补充时标明交接点，不声称可以无人值守恢复高士气；没有用户要求时不添加自动刷闪或给粮逻辑。

交付前检查 `KCPS-ValidateConfig.ps1` 的士气恢复门禁报告；兼容字段仍名为 `HighMoraleSingleLoopProblems`，其名称不代表强制所有高士气配置单循环。

## 跨海域推进

同一任务的多个海域默认按本次规划顺序接续；只有用户要求分别启动或选择互斥方案时才明确安排为独立配置。普通海域的 Boss 评级次数目标使用 [跨海域接续](跨海域接续.md) 中的计划和工具。其他完成条件、跨文件阶段与活动海域仍按对应阶段规则设计，不能套用 Boss 评级判据。

- 所有海域的 `总控.EnableOnLoad = true`，否则后续海域总控没有启用，无法监听前一海域发出的 `UserEvent`。
- 所有海域的 `总控.TriggerOnEnabled = false`。这对应 UI 里的“启用时立即触发”，默认不许勾选。
- 第一个海域也不默认立即触发；启动链条时由用户手动触发第一个海域的 `总控`，或在用户明确要求时另做独立启动器。
- 后续海域保持启用但不立即触发，只通过 Python `OnEvent(e)` 响应上一海域消息。
- 前一海域确实达到目标后才发出完成 `UserEvent`。自动停止也可能由循环上限或容量不足触发，停止本身不是通关证明。
- 通常海域完成消息格式为 `任务标识 海域及阶段 Clear`。任务标识从已确认的任务 API ID 或本次明确的稳定链标识单独保存，不从显示配置名的首词推断。示例为 `<任务ID或链标识> <海域> <阶段> Clear`；后续监听完全相同的字符串。活动海域按 [活动海域出击配置.md](活动海域出击配置.md) 包含阶段用途、目标和完整条件。
- 非任务攻略使用本次明确的稳定链标识；消息应唯一对应实际完成条件，不能因没有任务编号而复用其他方案的消息。
- Boss 评级接续由总控保存并转发原始结束统计，独立 `出击完成` 单元在自己的触发条件中判断并发送完成消息；下一图只监听消息，不读取上一图战绩。不要把该通知挂入 `AutoStoppedTriggerWorkflows` 或其他直接触发关联，这会绕过通知的触发条件。保留安全停止条件及停止后的入渠清理。其他类型的通知按其专用规则核实发送条件与关联。
- 后一海域 `总控` 用 Python `OnEvent(e)` 接收上一海域消息后启动。
- 不使用跨配置的原生 GUID 关联来推进海域；原生关联只在同一配置内可靠。
- 每个阶段只保留一个承担接续的完成通知；除非有明确的额外监听或提示用途，不另加重复的通知执行单元。

以下是仅接收消息的 UI 模板，不包含完成判定。它不能替代 [跨海域接续](跨海域接续.md) 工具生成的受管理内嵌脚本；后者包含生命周期钩子，应保留其专用标记，不要改成这个简单模板。

KCPS 用标记注释 `# Auto Generated Python Script` 区分可编辑模板与内嵌脚本。需要由 UI 模板编辑器继续编辑的纯监听脚本使用下面的标准形态：**首行标记注释、`def OnEvent` 前不留空行、Tab 缩进、条件写成 `if …: return True`、保留 `pass` 占位、`return False` 收尾**。

> `Script` 字段始终由 KCPS 的 IronPython 引擎编译。严禁写成 C#/PowerShell 的 `function OnEvent($event) { ... }`、`-is [Type]` 或花括号函数体；这种内容会在配置载入启用时立即 `SyntaxError`。生成后必须由校验器确认 `TriggerScriptSyntaxProblems` 为空。

```python
# Auto Generated Python Script
from KancollePlayerSimulatorKai import *
from KancollePlayerSimulatorKaiCore import *
def OnEvent(e):
	if isinstance(e, UserEvent) and e.Message == r'By6 1-2 Clear':
		return True
	pass
	return False
```

- 条件子句固定为 `isinstance(e, UserEvent) and e.Message == r'<完整消息>'`——这正是 KCPS `UserEventCondition` 生成的形态（`r'...'` 原始字符串、单引号、消息要带配置名编号前缀）。
- 多个上游条件时，每个写成一段 `	if <子句>:` + 换行 + `		return True`，全部条件之后保留一行 `	pass` 再 `	return False`（模板编辑器靠这个 `pass` 占位回填新条件，删掉它会导致编辑器无法续加条件）。
- 不要用 4 空格缩进、`def` 前留空行、或省略首行 `# Auto Generated Python Script`；任一偏差都会让 KCPS 把它当「内嵌脚本」。

## 总控关联与完成阈值

`RelationalSortieWorkflow` 每个阶段都有两类字段：关联执行单元列表和完成事件阈值。

规则：

- 阈值不能大于该阶段关联执行单元数量。
- 通常只有一个 `入渠`、一个 `补给`、一个 `编成`、一个 `改装` 时，对应阈值都必须是 `1`。
- 如果模板残留 `DockingBeforeFinishedEventThreshold = 2`，但只有一个 `入渠`，总控会在入渠完成后继续等待第二个入渠完成事件，表现为“跑到入渠就卡住”。
- 如果配置“补给后不出击”或“编成/改装后不继续”，同样检查对应阶段的关联执行单元数量和 `*FinishedEventThreshold` 是否匹配。
- 总控只应该引用本配置内的执行单元；跨海域推进用 Python `UserEvent`，不要把另一个配置的 GUID 当作本配置的关联执行单元。
- 集合数组、可空字段、PowerShell 单元素数组和 `KCPS-NormalizeRelatedWorkflowCollections.ps1` 的规则统一见公共文档；出击校验仍必须确认 `WorkflowRefShapeProblems` 与 `JsonCollectionShapeProblems` 为空。
- 修改现有配置时，按字段与界面项的对应关系核对结构；UI 上看似有执行单元，不代表总控阈值和关联列表一致。生成和文件校验不要求自动加载配置或操作界面。
- 生成或修改配置后，必须用 `KCPS-ValidateConfig.ps1` 检查 `RelatedThresholdProblems`。
- 还必须检查 `CompletionNoticeProblems` 和接续链检查结果：既检查已有通知的关联，也检查同一任务多海域是否缺少接续、完成判据和前后消息是否匹配。独立通知检查通过不能证明整条链完整。

常见应为 `1` 的字段：

```text
QuestBeforeFinishedEventThreshold
OrganizeBeforeFinishedEventThreshold
RefitEquipmentBeforeFinishedEventThreshold
DockingBeforeFinishedEventThreshold
DockingAfterFinishedEventThreshold
SupplyBeforeFinishedEventThreshold
SupplyAfterFinishedEventThreshold
```

## 出击后扔桶入渠

为了降低连续出击不同海域时的疲劳停顿，出击配置默认加入一个名为 `扔桶` 的 `BasicDockingWorkflow`。它的目标不是常规维修，而是：出击后把“已受损且士气很低”的当前出击舰队船用高速修复入渠，使修复完成后士气回到 40。

字段规则：

- `扔桶` 放在执行单元列表中 `出击` 后面，便于 UI 阅读；真正的触发位置是 `总控.DockingAfterWorkflows`。
- `LimitFleetFlag=true`，`LimitFleetValue` 必须严格限定为本配置实际出击舰队。`FleetSelection` 是位标志：第 1 舰队为 `3`，第 2 舰队为 `12`，第 3 舰队为 `48`，第 4 舰队为 `192`；联合舰队主队必须合并第一、第二舰队为 `15`，同时使用第三、第四舰队支援时支援入渠必须合并为 `240`。
- `入渠`、`捞出`、`扔桶` 三个主队入渠执行单元必须使用同一个、由出击形态推导出的主队范围：普通单舰队按 `出击.Fleet`，游击部队固定第三舰队 `48`，联合舰队固定第一、第二舰队 `15`。不得从模板机械保留第一舰队的 `3`。支援舰队使用独立的 `入渠（支援舰队）`，按实际启用的支援编成执行单元合并位标志。
- `LimitHpPercentFlag=true`，范围 `0.00..0.99`，只处理非满血船。
- `LimitMoraleFlag=true`，范围 `0..min(32, 出击士气阈值-1)`。默认出击阈值 33 时就是 `0..32`。
- `InstantRepair=true`，`InstantRepairTimeLimit=00:00:00`，`ApplyInstantRepairToDockingShips=true`。
- `ForceDocking=true`，这是为了避免修复渠被占时 `BasicDockingWorkflow` 因无空渠而停在运行状态，导致总控等待出击后入渠完成事件。这个选项可能会先对占用修复渠的船使用高速修复；如果某个任务不允许这种额外桶消耗，必须在 `说明` 中写明并改用更保守的流程。
- `Repeat=true`、`AutoStop=true`，让它循环处理所有符合条件的船，直到没有可修船后自动停止。
- `SkipExpeditioningShips=true`，避免误处理远征中的船。
- `EnableOnLoad=false`、`TriggerOnEnabled=false`，不能自己启动，只能由总控出击后触发。

总控关联规则：

- `总控.DockingBeforeWorkflows` 必须包含常规入渠执行单元，通常是 `入渠` 和 `捞出`。联合舰队配置还必须把 `组成联合舰队` 作为该列表的第一个启用项；KCPS 借用这一阶段在出击前组成联合舰队。`捞出` 属于出击前入渠阶段，用于出击前处理已经在修复渠中的船，不属于出击后阶段。
- `捞出` 之所以能处理固定船，依赖单候选编成位置设为 `ChangeIfRepairing=false`、`SkipRepairingShips=false`；关联出击先运行编成、后运行出击前入渠，字段设反会在“捞出”触发前报“第 N 个位置选取候选船失败”。
- `总控.DockingAfterWorkflows` 只放 `扔桶`。不要把 `捞出` 或其他常规入渠执行单元放进出击后入渠。
- `DockingBeforeFinishedEventThreshold` 必须等于该列表中会发送“入渠完成”事件的启用入渠执行单元数量；联合舰队的 `组成联合舰队` 虽位于此列表，却不发送入渠完成事件，不能计入阈值。例如 `组成联合舰队 + 入渠 + 入渠（支援舰队） + 捞出` 共4项时阈值是3。`DockingAfterFinishedEventThreshold` 等于启用的 `DockingAfterWorkflows` 入渠执行单元数量。阈值太小会提前进入后续步骤，阈值太大会卡住。
- 因为 `BasicDockingWorkflow` 会循环入渠，`总控.AutoStoppedDisableWorkflows` 必须包含本配置内所有 `BasicDockingWorkflow`：通常是 `入渠`、`捞出`、`扔桶`。这样总控自动停止后会切实关闭所有可能还在循环的入渠执行单元。
- 修改或生成后必须运行 `KCPS-EnablePostSortieBucketDocking.ps1 -CheckOnly` 和 `KCPS-ValidateConfig.ps1`；校验中的 `PostSortieBucketDockingProblems` 必须为空。该校验必须同时检查 `入渠`、`捞出`、`扔桶` 的主队范围，以及存在时的 `入渠（支援舰队）` 范围，不能只检查出击后的 `扔桶`。

## 接任务

- 每个海域组都要有 `接任务`，这样从中途海域恢复时仍会确认任务已接。
- ID 来源、缓存刷新、无法确认时拒绝生成，以及 `SelectMethod`、`FailIfNotExist` 等基础字段遵守公共规则。
- `api_title` 必须能和 `接任务.Memo` 或配置名对上；标题对不上视为 ID 不可信。
- `EnableAcceptedQuestCache = true` 可以保留；`EnableExistanceQuestCache` 可按 KCPS 默认不启用，但不能替代实际 API 校验。
- 不要假设用户只能接 7 个任务；用户可能能接 8 个，也可能手动调整任务栏。
- 是否允许替换低优先级任务，要根据时限和风险判断。限时任务通常可以允许替换。
- 修改或审计旧配置时，必须先运行实时任务 ID 校验：

```powershell
$SKILL_ROOT = '<SKILL_ROOT>'
$WORKSPACE_ROOT = '<WORKSPACE_ROOT>'
$env:KCPS_WORKSPACE = $WORKSPACE_ROOT
pwsh -ExecutionPolicy Bypass -File (Join-Path $SKILL_ROOT 'scripts\poi-kcps-api\validate\KCPS-ValidateQuestIds.ps1') -Path (Join-Path $WORKSPACE_ROOT '<JST_YYYYMMDD> 单次 出击 <任务名称>.conf.json')
```

## 编成

- 使用 `BasicOrganizeFleetWorkflow.Positions[].Selections[]`。
- 不要只填旧字段或 UI 辅助字段。
- 不要留空候选行；空候选行会导致选船失败。
- 默认不使用 `预编成`。
- 舰船选择顺序：任务强制条件、路线稳定、战斗能力、用户账号可用船、并行冲突、疲劳替换。
- 核对当前占用与本次并行、等待和资源要求。替代方案仍须满足任务及路线硬条件，并说明相对通过率、成本和准备时间的取舍。
- 游戏编成本身不允许同一舰船本体的不同改造或同本体多号机同时进入同一舰队，KCPS 也会按同本体规则跳过后续候选。不要在同一舰队里同时指定同一艘船的不同改造形态或二号机组合，例如 `瑞鳳改二` 与 `瑞鳳改二乙` 会导致后面的位置选船失败。需要两个轻空母时选不同本体，例如 `龍鳳改二 + 瑞鳳改二乙`。
- 通常海域可以使用“等价船疲劳轮换”；活动海域不许使用。当前规则按“只有活动海域会贴条，且活动海域必贴条”处理，所以只在 `Sea=1..7` 的通常海域展开等价候选，其他 `Sea` 必须跳过并告警。

### 等价船疲劳轮换

用于连续推进多个通常海域时降低同一艘船反复疲劳导致的停顿。此功能不能替代对路线、战力、装备和舰队顺序的设计，只能在“同一位置的替换船对任务和路线完全等价”时使用。

等价定义：

- 同一账号中存在的同一改装状态舰船，即 `api_ship_id` 相同。
- 补强增设可用状态一致。**已验证字段规则是 `api_slot_ex != 0` 即已开孔（可用）：`-1` 表示已开孔但空着，`> 0` 表示已开孔且装着装备，只有 `0` 才是未开孔。** 切勿用 `> 0` 判定。如果该位置配装依赖补强槽装备，等价候选必须与锚点开孔状态一致。
- 不比较等级、运、HP 上限、当前 HP、当前士气、当前装备；这些差异不参与“能否成为等价候选”的判断。
- 不在涉及贴条锁船的海图使用；目前活动海域视为必贴条，脚本必须按非 `Sea=1..7` 跳过。

KCPS 字段设置：

- `Selections[]` 使用多个 `Type=0`、`Value=<船舶ID>` 的精确 ID 候选，主方案船放第一，等价二号机按稳定顺序追加。
- **「位置」与「候选」的关系（避免误读成“多了一艘船”）**：出击船数等于 `Positions` 对象个数；每个位置只从自己的 `Selections` 里选一艘。一个有备选的 6 位置编成仍只出击 6 艘，不是 7 艘。KCPS UI 会把候选平铺显示，因此审计要数 `Positions`，并确认同一位置的轮换候选具有相同 `api_ship_id`。
- `SelectionSortingMethod=1` 表示保持列表原顺序；`0` 会使 KCPS UI 的“尝试候选船顺序”下拉框空白。
- `ChangeIfMoraleInRangeFlag=true`，范围 `0..出击士气阈值-1`。当前位置当前船低于出击阈值时，KCPS 会判定需要换船。
- `SkipMoraleInRangeFlag=true`，范围同上。候选船低于阈值时被跳过。
- `IncludeCurrentShip=false`、`IncludeCurrentSelection=false`，让候选完全由 `Selections[]` 顺序控制。
- `KeepIfAllSelectionsFailed=false`。所有候选都疲劳或不可用时必须让编成失败，交给总控错误处理等待下一轮，而不是保持错误编成继续出击。
- 保持 `SkipRepairingShips=true`、`SkipExpeditioningShips=true`、`SkipShipsInOtherFleets=true`。

上面的字段只适用于**多候选轮换位置**。单候选固定位置必须使用另一套修复中舰船规则：

- KCPS 关联出击的顺序是 `编成 → 出击前入渠`，所以“捞出”无法救回一个已在编成阶段被跳过的固定船。
- 当某位置恰好只有一个候选时，必须设 `ChangeIfRepairing=false`、`SkipRepairingShips=false`。这样 `编成` 可以先把正在修复的固定船编入舰队，随后 `DockingBeforeWorkflows` 中的 `捞出` 对它使用高速修复。
- 单候选仍保持 `SkipExpeditioningShips=true`；远征中的船不能靠“捞出”解决。
- 当某位置有多个等价候选时，保持 `ChangeIfRepairing=true`、`SkipRepairingShips=true`，优先换成没有入渠的等价船，不额外消耗高速修复材。
- 每个出击配置都必须恰有一个 `捞出`：限定当前出击舰队、只选择“正在修复”、`ForceDocking=false`、`InstantRepair=true`、`ApplyInstantRepairToDockingShips=true`、`Repeat=true`、`AutoStop=true`，且只能由总控的 `DockingBeforeWorkflows` 触发。

关联出击错误处理：

- 启用 `MinimalSleepSecondsAfterFailureOccuredFlag=true`，`MinimalSleepSecondsAfterFailureOccuredValue=180`，因为服务器状态约 3 分钟刷新一次。
- “忽略执行失败”中只启用 `IgnoreSortieFailure=true`（UI：`忽略关联出击执行单元执行失败`）；其他 `Ignore*Failure` 全部关闭。该组合会让出击失败自然进入下一轮，而不是反复弹出同一错误。
- “跳转到循环结算步骤”中的全部 `FinishLoopIf*FailureFlag` 关闭。不要用“出击/编成连续失败少于等于 N 次则跳转到循环结算”代替上面的忽略出击失败；它会累计失败次数，超过阈值后抛异常，并可能造成同一编成错误反复执行和弹窗。
- `StopIfOrganizeBeforeSelectFailed=false`。但编成、改装、接任务失败不应被忽略；这些通常表示配置或占用问题，应停止并暴露根因。

推荐工具：

```powershell
$SKILL_ROOT = '<SKILL_ROOT>'
$WORKSPACE_ROOT = '<WORKSPACE_ROOT>'
$env:KCPS_WORKSPACE = $WORKSPACE_ROOT
$target = Join-Path $WORKSPACE_ROOT '<JST_YYYYMMDD> 单次 出击 <任务名称>.conf.json'
pwsh -ExecutionPolicy Bypass -File (Join-Path $SKILL_ROOT 'scripts\poi-kcps-api\enable\KCPS-EnableEquivalentShipRotation.ps1') -Path $target -CheckOnly
pwsh -ExecutionPolicy Bypass -File (Join-Path $SKILL_ROOT 'scripts\poi-kcps-api\enable\KCPS-EnableEquivalentShipRotation.ps1') -Path $target
pwsh -ExecutionPolicy Bypass -File (Join-Path $SKILL_ROOT 'scripts\poi-kcps-api\enable\KCPS-EnableEquivalentShipRotation.ps1') -Path $target -CheckOnly
```

新生成通常海域配置后必须对目标配置文件实际运行一次该工具；不能只在设计时想到“以后可换船”却仍交付单候选。最后一次 `-CheckOnly` 必须显示 `Updates=0`，并且 `KCPS-ValidateConfig.ps1` 中 `MultiCandidateRotationProblems` 与 `SingleCandidateSalvageProblems` 都必须为空。

### 排布顺序

编成顺序不是装饰字段。生成配置前必须先确认任务是否限制旗舰、2番舰、指定随伴舰或特殊攻击位置；限制位置锁死后，再优化剩余自由位。

必须查的资料：

- 任务条件：wikiwiki 任务页或游戏 API detail，确认是否要求旗舰、2番舰、随伴固定、特定舰在前两位等。
- 夜战：wikiwiki `夜戦`。夜战无视射程，按舰队从上到下交替出手；不能夜战的舰仍占用己方出手顺位，会让后面的夜战舰延后。空母是否能夜战要单独判断，不是看舰种或名称：需要满足夜间航空攻击相关装备条件，且夜战/夜攻/夜爆、夜間作戦航空要員、搭载槽和残机都要能支撑实际输出。
- 阵型：wikiwiki `陣形`。警戒阵会按位置区分主力舰/警戒舰，6舰通常 1-3 为主力、4-6 为警戒，5/6 回避更高，4号位较危险；5舰以下规则不同。
- 特殊攻击：逐舰 wiki 页确认位置和阵型，例如 Nelson/Rodney Touch、長門/陸奥一斉射、大和改二特殊砲撃、Colorado/Maryland、金剛型僚艦夜戦突撃、潜水艦隊攻撃等。涉及特殊攻击时，位置优先级高于一般夜战排序。
  - **每种特殊攻击的发动条件不同，别张冠李戴用别的攻击的规则去套**。典型易错点：**大和型/長門型「一斉射」(大和タッチ/武大摸/長陸奥) 的「水上艦◯隻」里，空母(正規/装甲/軽空母)算"水上艦"——带空母照样发动**（"水上艦"=非潜水艦）；`戦艦2+空母1+軽巡1+駆逐2` 甚至 `戦艦2+空母4` 都满足。**"排除空母系/潜水艦"是 Nelson Touch 的规则**，不是大和型/長門型。判断某特殊攻击能否发动，要查它**本身**的发动条件页，并用一个能跑通的实战编成印证；不要只信对攻略页的概括（概括可能把"水上艦"误读成排除空母），一个含空母+タッチ的实战编成就是反证。把含空母的 boss 编成误判成"发不出タッチ"而改阵型(如把梯形改单纵)，等于拆掉攻略说"必需"的タッチ，会害卡关。
- 昼战攻击顺：砲撃戦按射程决定，同射程内顺序随机；若需要让特定舰先手，可以用长射程/超长射程装备调射程，但会影响装备格、火力、命中和路线条件，必须写进说明。

排序原则：

1. 先固定任务要求位和特殊攻击位。比如任务要求空母旗舰时，哪怕空母不能夜战也不能挪走；但后续自由位仍要优化。
2. 若 boss 或关键点设置夜战突入，不能把不能夜战的空母/补给/部分潜母等放在夜战舰前面，除非它们是任务固定位置、夜战空母配置已成立，或有明确保护/特殊攻击理由。
3. 夜战排序按“先清障、后收尾”设计：命中稳定但伤害中等的连击舰、对陆/PT/小船清扫舰可以靠前；高火力 CI、对 boss 特化、关键 S 胜收尾舰通常靠后，避免早出手打到低价值目标。
4. 如果敌方有必须尽早压制的高威胁单位，且我方某舰对其有专门手段，可以把该舰提前；如果敌方残血 boss 难杀，则把最高夜战上限/CI 舰放后。
5. 昼战排序不仅看位置，还看射程。航母、战舰、航巡、轻巡、驱逐的出手顺序可能被射程装备改变；射程调整必须服务于“谁先清小船、谁先打高甲、谁避免抢弱目标”的目标。
6. 警戒阵道中若以回避通过为目标，脆弱小舰通常放警戒舰位，主力输出和任务固定舰避免放在 4 号危险位；但 boss 需要火力时不能无脑警戒阵。
7. 对潜、开幕雷击、航空战、支援、闭幕雷击等阶段不完全按队列顺序解决问题，不能把它们和夜战排序混为一谈。
8. 排序改变后必须同步 `编成` 和 `改装`：KCPS 改装常按位置选择舰船，移动舰船时要移动整艘船的装备配置并更新 `SelectValue`。
9. 不要为了“让空母能夜战”而默认牺牲昼战、制空、开幕、彩云、触接或路线装备。只有当海域难点确实在夜战，且夜战空母的装备组合比普通夜战舰/CI 舰更适合解决问题时，才采用夜战空母配装和前置排序；否则把空母按昼战/制空角色处理。

写配置前必须形成内部“顺序理由表”：

```text
位置 | 舰船 | 任务/特殊位置锁定 | 昼战射程/角色 | 夜战能力 | 目标分工 | 排序理由
1 | 任务旗舰 | 是 | 长/主输出 | 可/不可 | ... | ...
```

如果自由位排序不是常规“夜战弱舰靠后、收尾舰靠后”，必须在 `说明` 执行单元写明原因。

## 改装

改装不是“按装备类型填槽”。必须先确认任务和海域要解决的问题，再按选定舰、槽位、库存和稀缺装备分配。目标是让 KCPS 的每个槽都落到明确装备，避免宽泛候选导致性能低或执行失败。

资料核对顺序：

1. 查日文 wikiwiki 的任务页、海域页、选定舰船页、关键装备页。
2. 查 wikiwiki `装備`、`装備考察`、`対空砲火`、`航空戦`、`夜戦`、`対潜攻撃`、`対地攻撃`、`PT小鬼群` 等机制页。
3. 查 TsunKit nav 确认节点类型、敌制空、索敌/路线、boss 强度和是否存在夜战/空袭/潜水/对地/PT。
4. 用 poi/KCPS API 和本地工具确认账号中装备数量、改修、熟练度、锁定、当前被谁携带；不要凭记忆猜库存。
5. NGA/中文攻略只能给“可能的舰种与打法”，不能直接复制装备；必须按用户库存和 wiki 机制重配。

配装决策顺序：

1. 先确定每艘船的角色：带路件、制空、开幕、昼战主火力、夜战收尾、AACI、防潜、对地、索敌、PT 处理、疲劳/资源节省。
2. 再确定舰队顺位：旗舰是否保护或提高夜战 CI，谁先进昼炮击，谁在夜战负责收尾，谁的射程会抢手。
3. 再确定稀缺装备分配：唯一或数量不足的装备给边际收益最高、且承担关键角色的船；其他船明确使用次一级替代，而不是让多个槽争同一件装备。
4. 最后逐槽落装备：每个普通槽和补强增设槽都要有明确选择器；除非用户要求 fallback，否则一个槽只放一个精确装备。
5. 注意**舰特定槽的装备类型限制**：少数舰的某个普通槽不接受某些类型，放错会在 KCPS 运行时报「第 N 装备槽中没能选定任何装备」。先查该舰 wikiwiki 页的「装備」「スロット」说明，再按游戏 master 中装备的 `api_type[2]` 分类登记和校验；装备名称正则只能作为 master 暂时未知时的后备，不能作为主判据。典型陷阱：吹雪改三第4槽禁止主炮和攻击用鱼雷，`12.7cm単装高角砲改三`虽名为高角炮，仍是类别1的小口径主炮，不能放第4槽；`対潜短魚雷(試作初期型)`名称含「魚雷」，但装备类别是`爆雷`，可以放第4槽，不能按文字把它误判为攻击用鱼雷。`KCPS-FitBonus.json/slotRestrictions`应优先写`forbidTypeIds`/`allowTypeIds`，`KCPS-ValidateConfig.ps1`只在无法取得装备 master 时回退名称规则，并且名称白名单不得覆盖已知的结构化禁用类别。任何特殊槽结论都要保留 wiki 或实测依据，不能把某一艘船的限制外推到同舰种全部船。
6. **装备类别必须与母舰槽位兼容——不能只看名字猜。** 名字带「改」≠舰载：**`烈風改` 是「局地戦闘機」(类别48，陸航/基地专用)，根本装不上空母**；真正的舰载艦戦(类别6)是 `烈風改二`/`烈風改二戊型`/`烈風 一一型`/`烈風(六〇一空)`/`試製烈風 後期型`/`紫電改二`/零戦系。判定：**该舰可装类别 = `api_mst_stype[stype].api_equip_type`(值=1) ∪ `api_mst_equip_ship[shipId]`(单舰额外，如由良改二能装水戦45、伊勢改二能装艦爆7/8)**；装备类别取 `api_type[2]`（6艦戦/7艦爆/8艦攻/9艦偵/10水偵/11水爆/25オートジャイロ対潜/26対潜哨戒機/45水戦/48局戦/47陸攻/41大艇）。**症状要会反推**：某槽放了不兼容类别→该槽永远填不上→KCPS 在换装时报看似无关的「第 N 槽当前装备与第 M 槽将要换上的相同」(中间槽空缺) 或「第 N-1 槽为空，不可以为第 N 槽更换装备」——这类"换不上去/槽空缺"的真正根因常常是某件装备类别不兼容、选不上，而**不是**顺序或跨槽搬运问题（KCPS 换装求解器靠拖拽交换能正确搬运跨槽装备，能力没问题）。`KCPS-ValidateConfig.ps1` 已加 `Test-KcpsConventionalSlotEquipment` 普通槽类别兼容性检查（对应已有的补强槽 ex-slot 检查），会直接报「'X'(类别N=…)不可装备于 母舰」。

必须考虑的加成和协同：

- **装备契合是两套独立机制，配装前必须分别核对，别只按“最高火力/对空/雷装”排序：**
  - **机制 A：装備ボーナス（stat 加成）** —— 由 (舰 + 装备[+数量/改修]) 决定的 火力/命中/回避/雷装/对空 +X。同名舰、舰级、国籍、改造阶段、改修值都可能不同；很多有个数上限、二件目衰减、同类只取最高、与其它装备组合「只算一次」(シナジー)、或共存覆盖/互斥。**典型陷阱：换上「下位/相近」装备就丢了加成**——例如某些船只对「四連装後期型魚雷」给雷装加成、对「五連装」不给；只对「改」版徹甲弾给加成、对无印不给；某船能装水战但官方不给水战加成。配装时必须查 wikiwiki 该舰页和该装备页的「装備ボーナス」表，把“第几件仍有补正、哪些可叠加、哪些只算一次”推敲进去。
  - **机制 B：フィット命中補正（俗称“超重主炮”）** —— 大口径主砲(46cm/51cm系)装在不适配的舰种/舰级上有命中惩罚（也可能是正补正），`命中补正 = 系数 × √门数`(非线性，2门≈×1.41)，与机制 A 完全独立。同一艘船同口径不同型号主砲的超重系数往往相同（差别在火力和机制A，不在命中）。判定：`系数×√门数 < 0` 即超重。
  - **两套都不在游戏 API**（master 数据只有基础值，KCPS 也不算 fit），游戏服务器算实际数值时应用、规则只在 wikiwiki/检证。**所以必须查 wiki，且游戏会更新加成，引用前核对 wiki 时效。**
- **火力 vs 命中按敌人和队内角色权衡（超重主炮的核心判断）：** 昼战火力 cap=220，到 cap 后堆火力 √衰减几乎无意义→转命中。**优先火力**：boss 装甲极高 / 靠徹甲弾CI/特殊攻击一发定胜负 / 反航战火力够不到 cap / 战舰特殊攻击(タッチ)的旗舰·2号位(タッチ是 post-cap 倍率，素火力差被放大，且2号位倍率通常>旗舰，把最好的主砲和徹甲弾给2号位)。**优先命中**：要稳 A 胜 / boss 回避高(驱逐/PT/空母棲姫) / 夜战 CI 要命中 / 通常砲击已到 cap。超重命中惩罚**不影响特殊攻击/弾着的发动率**(发动率只看 Lv/運/电探/索敵)，只让发动后每发更易 miss→靠観測機+水上電探+徹甲弾+命中改修补回。
- 装备组合协同：昼战主主侦/主主彻侦、夜战主鱼电见/鱼电见/鱼雷 CI、AACI、对潜套、对地套、PT 套、舰载机战爆联合、触接、彩云、索敌等要作为组合判断。
- 槽位差异：同一艘船不同普通槽可装装备可能不同；航母/航巡/航战/水母的搭载数不同，舰载机放哪个槽会改变制空、开幕、熟练损耗和触发效果。
- 格纳库增设：用过「格納庫増設」道具的舰，实际各槽搭载上限在 poi 舰员数据的 `api_onslot_max` 字段（仅扩张过的舰个体有此字段，是舰个体属性、与札无关），会大于图鉴/master 的 `api_maxeq`。算制空、开幕、熟练损耗、选"谁带哪架飞机"时以 `api_onslot_max` 为准；`KCPS-AuditAirPower.ps1` 和 `KCPS-EnableEquivalentShipRotation.ps1` 已适配。
- 舰队级功能装备：彩云的反 T 不利能力是舰队级功能，不因为同一舰队带多架而线性增强。默认一队最多带 1 架彩云，并优先放在“不牺牲关键制空/输出、搭载较小且不易影响舰载机熟练”的槽；只有索敌、触接率或任务机制经计算确实需要时，才允许第二架，并必须写进说明。
- 补强增设：KCPS 中补强增设装备槽固定是 `EquipmentSlot.SlotEx = 6`，JSON 必须写 `Slot = 6`。先核对选定实例是否已开孔。仅作为可选收益的装备可以设置 `IgnoreSlotNotAvailable = true`；承担提速等硬条件的装备不能因未开孔而静默跳过。补强槽不能只按装备大类或舰种猜，必须查游戏 API/KCPS 数据：`api_mst_equip_exslot` 给通用可进补强槽的装备类型，`api_mst_equip_exslot_ship` 给逐装备的舰船/舰种/舰级 override 和 `api_req_level` 改修等级门槛。`api_mst_equip_exslot_ship.api_stypes` 中的 `99` 表示舰种通配，例如 `改良型艦本式タービン` 当前用此规则允许进入补强槽；校验脚本必须把它当通配而不是未知舰种。若某装备需要 `api_req_level > 0`，配置前必须确认账号中可被选中的同名装备存在满足改修等级的个体。
- 改修和熟练度：改修可能影响火力、命中、制空、AACI、对地、PT 等；熟练度可刷时可以把舰载机视为可恢复，但仍要避免无意义大损耗。
- 提速配装先核对当前路线要求的速力、舰船实际基础速力及其专属提速规则，再决定缶、タービン及槽位。不按舰种名称或旧模板推断基础速力；必要装备和补强增设兼容性均由当前主数据与来源确认。已经满足路线速力的舰船，不为沿用旧方案占用额外槽位。
- 制空目标由当前敌编成、可用舰队和整体战术决定，不把航空优势作为所有配置的固定门槛。比较不同制空状态下的伤害、生存、特殊攻击、烟幕与夜战能力，明确各方案的条件与代价；所需制空值由本次敌编成计算，不保存某个活动 Boss 的历史数值。
- 比较可用装备时，计入舰船特定 bonus、改修、熟练度、面板值、隐藏补正、叠加上限和同时装备数量限制。先满足任务、路线、兼容性和库存硬条件，再按本次目标、资源预算、保留要求及准备成本选择。更高战斗指标不自动压过其他目标；采用替代装备时，在 `说明` 写出与当前角色有关的取舍，不以照抄模板代替比较。
- 索敌：索敌任务或沟点要计算装备、舰船素索敌和装备 bonus 的影响；不要随手拆侦察机/电探。
- 制空目标：先决定该海域要空确、空优、均势还是放弃，再以“到关键点时仍满足目标”为准留合理余量。制空够用后，不要继续堆纯舰战/水战；应把多余格子换成开幕、昼战、触接、索敌、电探减旋涡、AACI 或生存装备。若制空数值很高但主要来自 `AU-1`、`F4U-7`、爆战、喷气机等同时承担输出的飞机，不按纯制空过剩处理，但仍要确认这些飞机比低对空高雷装/爆装飞机更适合当前海域。
- 熟练度审计：`KCPS-AuditAirPower.ps1` 同时输出无熟练下限 `BaseAirPower`、仅战斗机满熟练 `FighterMaxOnlyAirPowerEstimate`、所有飞机满熟练 `AllMaxProficiencyAirPowerEstimate`。交付说明优先使用“仅战斗机满熟练”作为可依赖值；“所有飞机满熟练”只作为熟练度刷满后的上限参考。不要把无熟练下限直接等同于实战制空；5-5、6-5、5-6 这类强航空图通常还要考虑道中损耗、陆航削制空和关键点目标。若配置依赖非战斗机熟练度或陆航削制空，必须在 `说明` 写明，并提醒熟练度被打空时先刷熟练。
- 装母与喷气机：不要因为有 `橘花改`、`噴式景雲改` 就默认上喷气机。只有当海域道中或 boss 需要额外开幕手数、舰载机损耗和钢材消耗可接受、且能使用喷气机的装母/航母不会破坏路线或任务条件时才使用。装甲空母的中破可动是重要收益，特别适合 3-4 这类道中和 boss 都强、空母昼战承担主输出的海域；但在强防空点、低收益弱图或只需轻量通过时，喷气机可能只是增加损耗。

按海域类型调整：

- 夜战或高装甲 boss：需要决定是否固定夜战、是否要夜战 CI、谁放旗舰、是否使用见张员/水雷见张员、照明弹/探照灯/夜侦等；若只需 A 胜且白天稳定，避免过度夜战装备和夜战突入。
  - **每艘小船都要对击杀有贡献，别把船配成纯防空/纯辅助**。靠夜战收尾的图，担任夜战的驱逐/轻巡必须带输出（魚雷/主砲做 CI），不能只塞高角砲+电探变纯 AACI——纯防空船对 boss 零输出、打不下来。AACI/防空让最合适的一两艘兼顾即可。
  - **按船的素质选 CI 类型**：先看这艘船的裸**雷装 vs 火力**哪个高（查游戏面板）。雷装系(雷装>火力，如多数水雷战队驱逐)走**魚雷CI**(2 条魚雷，×1.5，吃雷装)最强；火力系特型(火力高、雷装一般)走**砲CI/連撃**或主魚混合。别盲目按攻略给的某船配法套到素质不同的同名/相近船上。注意舰自身的魚雷/主砲 fit bonus 和相互シナジー(如吹雪型 三連装後期型魚雷+A型砲 雷装+6)能放大对应 CI。
  - **強空袭图的夜战驱逐优先选「高角砲」而非纯火力主砲**：高角砲(対空)兼顾保命+输出，夜战 CI 由魚雷触发、主砲只是加成，所以主砲换成高角砲几乎不丢 CI 火力却白赚対空；若该船对某高角砲有 fit bonus(如時雨↔12.7cm単装高角砲改三 火力+5/対空+4)则更优，胜过通用秋月砲。
- 潜水节点或反潜任务：只有路线和任务确实需要时才上反潜。需要先制对潜时计算舰船素对潜、装备对潜、装备 bonus 和射程；不需要反潜时不要牺牲主火力。
- 空袭或强航空战：先算目标制空状态，再决定舰战/水战数量和 AACI 舰。不要给所有驱逐都塞电探；AACI 通常由最适合的一艘或少数船承担。一艘 AACI 通常 1 个对空电探就够，多带第二个对空电探收益骤减、是浪费——空出的槽给对空弹幕(`12cm30連装噴進砲改二`)或输出装备。
- **拉烟（発煙装置/煙幕）**：用在空袭/夜战重的点降低敌方命中（开幕烟幕使敌我昼战命中项降到约 25%）。出击侧 `DefaultSmoke=true`，并让队里至少一艘带 `発煙装置(煙幕)` 或 `発煙装置改(煙幕)`（編成≥4 隻、非开幕夜战点才可发动）。**发动率只看旗舰運 + 発煙装置改★**：`k=⌈√旗舰運+0.5×Σ(煙改★)⌉`、`n=発煙装置数+発煙装置改×2`、不発 `Pg0=3.2-0.2k-n`(≥0)；`n≥3` 且旗舰運≥1 → 必发。实用判断：**一个改修过的発煙装置改(如★2~3)在旗舰運≈21 时单个即 100% 必发**——不要画蛇添足带第二个发烟、白占战斗槽。只有当発煙装置改★0 且旗舰運低(战舰旗舰常见)时，才靠 `1改+1無印=n3` 凑必发。配置前用工具查発煙装置改的实际★再决定带几个。
- 战术字段必须有最终配装提供能力。任何条件策略或默认策略启用烟幕时，最终改装中必须存在烟幕装备；移除烟幕装备时必须同步关闭全部烟幕字段。联合舰队退避同理：只有第一舰队旗舰实际装备 `艦隊司令部施設` 时才能把退避设为自动选择，否则保持手动。不能把“策略写了”误当成“游戏能执行”。
- 对地：先确认目标类型（软皮、集积地、炮台、离岛、港湾等），再选择 WG、大发系、内火艇、三式弹、火箭弹等组合。对地装备很多是乘算/分类协同，不能按单件火力直觉配。
- PT：需要小口径主炮、副炮、机枪、见张员、武装大发/AB 艇等成组处理；见张员单独放上去不是完整 PT 对策。
- 普通弱 boss 或只要 A 胜：优先稳定带路、低疲劳和低损耗；不把最稀缺装备都堆上去，也不要引入会改变路线的舰种。

舰载机槽位规则：

- 先查敌制空并设定目标（空确、空优、均势或放弃），再配舰战/水战。
- 交付前用工具或手算列出每个海域的制空目标、无熟练最低值、仅战斗机满熟练值、所有飞机满熟练值。无熟练下限必须排除主炮、电探、高角炮等虽有对空值但不参与航空制空的装备；仅战斗机满熟练值是默认可依赖估算，所有飞机满熟练值只能作为上限参考，不能替代具体熟练度和道中损耗计算。可使用 `<SKILL_ROOT>\scripts\poi-kcps-api\inspect\KCPS-AuditAirPower.ps1` 检查已生成配置。
- 大搭载槽优先给需要生存和输出的舰攻/舰爆/爆战/水爆，或承载制空贡献最大的舰战；小槽适合彩云、舰侦、夜战辅助、触接、纯舰战，或有足够抗击坠且放在小格仍有边际收益的爆战/攻击机。
- 航母 CI、夜袭、喷气机、爆战制空、攻击机熟练度损耗都和槽位有关，不能随意把攻略图的顺序打乱。选择“谁带哪架飞机”时，要同时比较该舰各槽搭载、该机对空/雷装/爆装/索敌/命中、对空射击回避、舰船特定 bonus、是否会阻止对陆攻击、是否会形成 FBA/BA/夜袭，以及该图敌防空是否容易打空小格。
- 不要把攻略图的舰载机方案按航母数量机械复制。先算全队制空和触接需求，再把每一架舰攻/舰爆/舰战/舰侦分配给边际收益最高的船和槽；如果一架彩云已经覆盖反 T 不利，剩余小格应改成制空、FBA、开幕、触接或保熟练度更有价值的装备。
- 如果关键舰载机数量不足，先保证承担主输出或制空阈值的船；其他航母用次一级飞机或调整角色。
- 空母补强槽不能默认全填 `12cm30連装噴進砲改二`。先比较该图航空阶段威胁、是否需要喷进弹幕保命、boss 昼战压力、是否有战舰特殊攻击/警戒阵/其他需要保护先手的机制。`熟練甲板要員+航空整備員`（游戏 API 名称使用 ASCII `+`）可进空母补强，提供超长射程和昼战火力；在没有特殊攻击先手冲突、且 boss 昼战击杀压力明显高于航空战生存压力时，应优先给主力空母。若会导致中破空母、低输出空母或非关键空母抢走大和/长陆/Nelson 等特殊攻击先手，或道中空袭/航空战风险更关键，则保留喷进炮或其他防御性补强。
- 5-5 上路这类 P 点レ级雷击/炮击是主要事故源的图，空母和大型舰补强槽要认真比较 `増設バルジ(大型艦)`、喷进炮和熟练甲板。没有空袭点时，喷进炮常不如バルジ；若有空袭连续点如 6-5，喷进炮价值会重新上升。

KCPS 写法：

- 使用 `BasicRefitEquipmentWorkflow.Ships[].Slots[].Equipments[]`。
- 确认船和库存后，每个槽通常只填一个精确装备选择器。
- 调整舰队顺序时，必须把对应位置的整艘 `改装` 舰船块一起移动，再改 `SelectValue` 和 `Memo`。不能只改 `编成`，否则三槽驱逐的位置可能拿到四槽驱逐/巡洋舰的装备表，或反过来导致槽位缺失、装备空选。
- KCPS 改装按 `BasicRefitEquipmentWorkflow.Ships[]` 和各船 `Slots[]/Equipments[]` 的列表顺序依次选装备。遇到同名装备有多个改修等级时，必须利用顺序控制谁先拿到哪一件：通常舰队位置偏后的船如果更依赖高改修件，就把该船对应的改装船块或该槽装备请求排在更前，使高星同名装备先被它选走；靠前但需求较低的船后执行，拿低星件。默认情况下仍按舰队位置和槽位顺序排，方便用户理解；只有提速、补强槽准入、索敌阈值、特殊攻击倍率、AACI/对地/PT/命中等确实依赖改修等级时才调整顺序，并在 `说明` 写明。
- 精确装备名选择器必须按当前 poi 库存计数核对。同一 `改装` 执行单元内，`天山一二型(村田隊)`、`天山一二型(友永隊)`、`震電改`、`AU-1`、`F4U-7` 等稀缺装备的需求数不能超过账号实际持有数；否则 KCPS 会在靠后的船或槽位报“没能选定任何装备”。数量不足时，先把最强/最稀缺装备给承担主要输出、关键制空或关键触接的船和槽，其余船写入明确的次级替代。
- 不要把宽泛候选列表塞进每个槽，除非用户明确要求 fallback。
- 不要把普通第 4/5 装备槽当成补强增设槽；`Slot = 4` 和 `Slot = 5` 只代表常规装备槽。
- 若补强槽没有明确更优选择，按角色给默认值：驱逐/轻巡偏 `水雷戦隊 熟練見張員` 或 `熟練見張員`，大型舰偏可进补强的测距仪/副炮/机枪/喷进炮，航巡/水母等先按 API 判断再选。`8cm高角砲`、`8cm高角砲改+増設機銃` 这类“普通槽很多船能装、补强槽只允许部分船装”的装备，只有当前船命中 `api_mst_equip_exslot_ship` 且改修等级门槛满足时才可写入 Slot 6；利根改二、筑摩改二、矢矧改二乙、日進甲等不能因此误配 8cm 系补强槽。反过来，不能因为该装备不是所有船都能放就一律禁用；若当前船能放、等级满足，且海域需要昼战火力/对空/副炮协同，可纳入满足本次目标和资源预算的候选。
- 有改修等级门槛的补强槽装备要逐项调查。当前 API 中存在 `api_req_level` 规则，例如某些电探/高角炮/北方装備类装备只有达到指定改修等级后才进入特定船或舰级的补强槽。遇到特殊补强装备时，不要只查 wiki 表格文字，必须同时用游戏 API 或 KCPS fitting 数据确认 `reqLevel`，再检查账号库存中同名装备的改修值。
- 改修等级还可能影响游戏机制门槛，不只影响数值。典型例子：`新型高温高圧缶` 等提速装备在某些船上需要特定星数才满足提速组合；北方装甲等补强槽装备也可能需要指定改修等级才能进入补强槽。写配置时必须先确认“哪个船需要几星”，再通过改装执行顺序保证高星件给到真正需要的船。
- `IgnoreSlotNotAvailable = true` 可以用于兼容未开孔船，但不能因此漏配已开孔船。
- 出击配置不处理工厂或装备消耗任务。这类任务另行规划，保留数量和可消耗范围由本次用户要求明确；实际消耗前核对授权与保留约束。

写入配置前，必须先形成一张内部配装表，即使不输出给用户，也要按这个表核对：

```text
舰船ID | 舰名 | 位置 | 角色 | 槽位 | 搭载 | 装备 | 库存/占用 | 选择理由 | 次级替代
```

配装表必须能回答：为什么这件稀缺装备给这艘船、为什么放这个槽、为什么其他船不用、如果数量不足用什么替代。

## 出击与战斗策略

KCPS 枚举要点：

- 阵型：`1 单纵`、`2 复纵`、`3 轮形`、`4 梯形`、`5 单横`、`6 警戒`。
- 夜战：`1 停止追击`、`2 夜战突入` 是安全自动选项。
- `DefaultMidnight = 0` 是手动，普通战斗点会卡自动化；但明确为现代 `空襲戦`/空袭点的条件策略应保留 `0`，因为现代空袭点没有夜战选择页，这个字段正常不会被消费，反而能在异常走到可夜战页面时停住让用户确认。
- 夜战点本身也不要把 `DefaultMidnight` 留成 `0`。虽然夜战点通常不会再消费“夜战突入”选择，但 KCPS 校验和部分 UI 流程会把手动值视为自动化暂停风险；默认设 `1 停止追击`，真正需要昼夜转换或特殊追击时再按该点机制单独说明。
- 不要把 `航空戦マス` 当成现代空袭点。KCPS/游戏 API 层可区分：`MapCellType.AirBattle`/`api_event_id=7` 且 `MapCellBattleType.AirBattle=4`、战斗 API 为 `airbattle` 的是旧式航空战点，wikiwiki 通常写作 `航空戦`，会出现夜战选择；`MapCellBattleType.LongDistanceAirBattle=6`、战斗 API 为 `ld_airbattle` 的才是现代 `空襲戦`/空袭点，通常没有夜战选择。
- 不要使用 `DefaultMidnight = 3..7`。这些“按旗舰击沉/A胜/AB胜判断夜战”的策略在 KCPS 当前代码中未实装，到夜战选择页可能直接报错。
- 进退：`1 进击`、`2 撤退`。
- 战斗评价：`SS=1`、`S=2`、`A=3`、`B=4`、`C=5`、`D=6`、`E=7`；数值越小评价越高。
- 伴随舰大破：`EscortShipsHeavilyDamagedStrategy = 1` 为强制撤退，`3` 为忽略。KCPS 只判断伴随舰，不判断旗舰；联合舰队二队旗舰也按旗舰处理，不在该字段判断范围内。
- **针路选择节点（手动选路 / 針路選択可能）**：有些节点游戏会弹「艦隊針路選択可能！どちらの針路をとられますか？」让手动选路。KCPS 在该点返回 `strategy.DefaultWayPoint`（`PointArchive` 归一化点击坐标 `{Left,Top,Width,Height}`，相对 1200×720 画面）。**必须给这种节点配条件策略，并把 `DefaultWayPoint` 设成指向下一个目标节点的点击区域；缺策略或 `DefaultWayPoint` 为 null，KCPS 会卡在选路画面。** 点击区域：KCPS 在该矩形内**均匀随机取点**（防机械），所以矩形内每点都得落在可点区域——圆形地图点图标取**外切该圆的矩形（bounding box，宽高≈节点直径）**，区域尽量大但别碰到邻近节点。坐标怎么定：`PointArchive` 归一化相对 1200×720 全画面；**别用游戏实时截图**（拿不准当时画面/视图状态），而是**上攻略站找一张干净的全画面地图截图（整张游戏画面、所有节点带标签）按比例量目标节点中心与直径**，节点在全画面图里的归一化位置即游戏视口里的位置。**别填错坐标**（错的非空坐标会静默点错地方）。选路节点本身无战斗，`DefaultMidnight` 设 `1` 避免误报手动夜战。路线规格用 `"Kind":"waypoint-select","RequiresWayPoint":true` 标记，校验器据此检出缺失。

默认策略硬规则：

- 出击配置必须完全使用条件战斗策略承载自动行为；不要让默认战斗策略或 Boss 专用策略负责正常节点。
- `DefaultStrategy` 只作为漏配点位保险：`DefaultFormation = 0`、`FallbackFormation = 0`、`DefaultMidnight = 0`、`DefaultAdvance = 2`，并且 `EscortShipsHeavilyDamagedStrategy = 1`。这里的 `DefaultAdvance = 2` 是“撤退”，不是手动。已验证行为表明，默认进击为手动时，伴随舰大破保护不能可靠兜住漏点后的进击页。
- `DefaultBossBattleStrategyFlag = false`，UI 中 Boss 战专用 checkbox 不选中。Boss 点也写成地图点条件策略。
- `DefaultBossBattleStrategy` 即使被禁用，也保持同样的手动阵型/手动夜战/撤退/强制撤退值，避免以后 UI 勾选或复制配置时带出隐藏自动行为。
- 每个 `Strategies[]` 条件都使用地图点规则：`Condition.Type = 1`，`Condition.Value = 地图节点编号`。不要用“Boss 专用”“默认 Boss”“战斗次数”等替代正常点位策略。
- `DefaultWayPoint` 只允许设置在游戏实际出现路线选择界面的能动分歧点。普通水面战、潜水战、空袭战、航空战、夜战、Boss 战，以及由编成或索敌自动判定方向的非能动分歧都必须写成 JSON `null`；不得填空名称与全零坐标对象，KCPS 仍会把这种对象显示为已设置路线。路线规格仅对能动分歧节点声明 `Kind=waypoint-select` 和 `RequiresWayPoint=true`，其他节点不得携带这两个标记。
- 能动分歧的 `DefaultWayPoint` 必须包含目标点名称及有效归一化点击框：`Width/Height > 0`、`Left/Top >= 0`，且右边和下边不超过 `1`。不能用全零对象占位，也不能因某点存在后续路线分歧就误判为能动分歧；必须以游戏界面、日文 Wiki 节点类型和路线资料共同确认。
- 条件策略按实际出击顺序排列；如果存在分歧路线，只把分歧子段分开排列，并在 Memo 中写清例如 `E 空袭 B->E` / `E 空袭 C->E`。不要让无关路线的模板节点留在列表里。
- 注意 KCPS/poi 的地图点数值可能依赖“从哪个前置点进入”。同一个物理节点、同一个 wiki 字母点，在不同进入边下可能对应不同 `currentNode`/`Condition.Value`。例如 5-5 boss `S`：从 `P` 进入时条件值是 `28`，从 `O` 进入时条件值是 `19`。因此不能只给“物理 S 点”写一条策略；如果配置允许 `P->S` 和 `O->S` 两种情况，必须分别写 `S boss P->S (28)` 与 `S boss O->S (19)` 两条条件策略。任何从不同前置点进入同一目标点的海域，都按这个规则处理。
- 每个可运行出击配置交付前，都必须把账号路线方案登记到私有 `.work/route-overrides.json`（由工具与公共路线合并读取）。`KCPS-ValidateConfig.ps1` 默认会强制 normal map 出击存在匹配 route spec，并检查 route spec 期望点位是否有地图点条件策略、策略顺序是否一致、阵型/夜战/进击是否符合登记值。只有整理历史旧配置时才可显式使用 `-AllowMissingRouteSpec`，新生成配置不许使用。
- Route spec 的 `Nodes` 只登记该配置按当前编成会经过或合理随机可能经过的有战斗处理节点，以及确实弹出路线选择界面的能动分歧节点；资源点、自动分歧、战斗回避点、终点本身不写条件策略。若同一字母点存在多个进入边，必须各写一条不同 `Value` 的节点，并在策略 Memo 中写清进入边。
- **随机起点/多分歧图必须覆盖全部可达点，不能只配一条假想路线**：起点随机(如 2-3 起点 A/B/C 随机)或编成依赖分歧的图，实际出击可能落到任何分支。漏配的点会落到 `DefaultStrategy`(手动阵型)→ KCPS 停在阵型选择画面等手动 = **卡死**（只配置主路线而遗漏可达分支时，也会在未覆盖节点停住）。做法：用 TsunKit `/api/routing/maps/<sea>-<area>` 拉全 `mapSet.map.spots[].no`(全 cell)+`route`(边表)，把所有可达战斗点(含同物理点的多个 cell 副号，如 1-6 的 K=6/15、D=11/16)都写条件策略并登记进 route spec；起点随机的图直接覆盖全部 1..N。登记后校验器会报 `expects node X value V, but no matching strategy` 精确抓漏点。道中航空点的夜战值取 `1`(停止追击)对现代空襲戦/旧航空戦都不卡(都不会停在夜战选择)，boss 用 `2`(夜战突入)。
- Route spec 的 `Kind` 必须区分 `airraid` 与 `airbattle`：`airraid` 仅用于现代 `空襲戦`/`LongDistanceAirBattle`，期望 `ExpectedMidnight=0`；`airbattle` 用于旧式 `航空戦マス`/`AirBattle`，必须按战术选择 `ExpectedMidnight=1` 或 `2`，不允许因为它也是航空阶段就写成空袭。空襲/混成点若拿不准是現代还是旧式，可省略 `Kind` 并把 `ExpectedMidnight=1`(停止追击，两类型都不卡)，只校验覆盖+阵型+进退。

自文档化（备注与命名）硬规则：

- **每个执行单元都要写 `Memo`**：总控/接任务/编成/改装/出击/出击完成/扔桶/陆航休息/说明 等每个 workflow 的 `Memo` 都写角色说明(这段干什么)，不能留空——配置在 KCPS 里要能一眼看懂每段做什么。
- **每条条件战斗策略都要写 `Memo`**：`Strategies[].Strategy.Memo` 写 `节点字母（进入边值）· 战斗类型 · 阵型/夜战/进退`，便于核对路线覆盖与逐点意图。例如：`E点（5）· 道中水面战 · 单纵阵/不进入夜战/前进`。
- **战斗策略备注只使用中文，不得中日混写**：禁止在 `Strategies[].Strategy.Memo` 中写`単縦、単横、複縦、空襲戦、対潜、針路選択、能動分岐、ボス、到達、経由、発煙装置、一斉射`等日式写法，也不要使用`Refresh、bounding box、currentNode`等英文叙述。统一写成`单纵阵、单横阵、复纵阵、空袭战、反潜战、路线选择、主动路线分歧、Boss战、到达、途经、发烟装置、齐射、刷新游戏、外接矩形、当前节点值`。地图节点字母、数字、`P1/P2/P3`、胜利等级、`PT`及玩家通用术语`Boss`等必要游戏标识可以保留；`Boss`首字母必须大写，禁止使用“首领”“首领战”“首领水面战”。
- **配置名 `WorkflowGroup.Name` 必须使用 `频率 出击 任务名 海域/阶段`**：例如 `<频次> 出击 <当前任务标题> <海域及阶段>`，以频率和种类开头。但**触发用的 Clear 消息与显示配置名解耦**：通常海域保持 `TaskId 海域 Clear`（如 `<任务ID> <海域> Clear`；分阶段时包含实际阶段标识）；活动海域使用 `E编号 阶段 用途 目标 条件 Clear`。任务接取执行单元继续保存精确 `api_no`。
- 校验器 `KCPS-ValidateConfig.ps1` 已加 `MemoCoverageProblems`(执行单元/条件策略缺 Memo)与 `GroupNameTaskProblems`(组名缺任务名)检查。

生成规则：

- 先清空从模板继承来的 `SimpleSortieWorkflow.Strategies`，除非已经按该海域节点逐条重新确认。
- 普通水上道中通常单纵并停止追击。
- 潜水节点确认在路线中后才设单横。
- 混潜节点必须按目标重新选阵：道中只需通过时可优先水上火力/回避；boss 需要 S 胜时必须保证潜水目标能被击沉。5-5 boss 这类混潜且有大和/武藏特殊攻击的点，常见候选是梯形阵触发特殊攻击，或复纵阵兼顾水上火力和反潜；单纵只有在反潜装备/先制反潜足以稳定击沉潜水目标且不需要特殊攻击时才采用，并必须写明。
- 现代 `空襲戦`/空袭点通常轮形，且 `DefaultMidnight` 保留 `0`（手动）。现代空袭点没有夜战选项，自动化不会在该点消费夜战字段；这样在路线判断错误、节点类型判断错误或误入可夜战点时，KCPS 会停在夜战选择处而不是擅自继续。校验脚本只应把 route spec 或 API 确认为 `LongDistanceAirBattle`/`ld_airbattle` 的点视为此例外，不能只靠 Memo 含 `空袭`/`空襲`。
- 旧式 `航空戦マス` 通常也可用轮形阵抗航空伤害，但它有夜战选择页。若任务不需要夜战击沉敌方，默认 `DefaultMidnight = 1` 停止追击；若必须追求 S 胜或白天判定不足，再根据敌编成与疲劳/资源代价设 `2` 夜战突入。典型例子是 1-6 D/F/L：wikiwiki 敌编成表写作 `航空戦`，不是 `空襲戦`。
- 只要求 A/B 胜且舰队明显过强时，boss 也应停止追击，避免夜战疲劳和资源浪费。
- 要求 S 胜或白天 S 不稳时，boss 才固定夜战突入。
- 不要用未实装的条件夜战值假装“白天够了就不夜战”。
- 路线选择点、撤退点、夜战点必须先查 TsunKit 和 wiki，不能复制其他海域节点编号。
- 不要把路线分歧表中的字母点误当成无战斗点。每个经过点都必须再查 wikiwiki 敌编成表或 TsunKit 节点类型；只要敌编成表列出该点，或实际出击日志进入阵型/战斗选择，就必须写条件战斗策略。典型例子：6-4 右路 `M-K-J-I-N` 中，`K` 不是非战斗分歧点，而是水上战斗点；当前已验证 KCPS 条件值为 `K=11`，应设单纵、停止追击、进击。
- 设置每个节点的 `Condition.Value` 前，必须确认“路线边”：上一点是什么、当前点是什么、KCPS/poi 在这条边上给出的数值是什么。优先依据是当前出击的 `/data?type=sortie` 中 `spotHistory/currentNode`、KCPS 日志“第 N 场战斗发生于地图点 X”、以及用户已验证 default 配置；wiki 字母点和 TsunKit/KCNav 用来确认路线与节点性质，但不能直接等同于 KCPS 条件值。
- 同一海域也不能复制另一条路线的策略。典型例子：6-5 只要含空母系就是上起点，但后续路线仍由 C 点分歧决定；空母2+伊势+航巡+轻巡+驱逐这类配置按 wikiwiki 规则是 `A-C-D-G-M`，不能沿用 `E-H-G-M` 或下路 `B-F-I-J-M`。要显式写 A、C、D、G、M，每个点的 `Condition.Value` 按 KCNav/TsunKit 边 ID 登记。
- 特殊攻击必须和阵型一起设计。先判断海域最难点在哪里，再决定是否把 Nelson/Rodney、長門/陸奥、大和/武蔵、Colorado/Maryland、金剛型夜战突击等投入该点。若使用，编成位置、损伤条件、阵型和出击策略必须一起写对；若不用，也要确认不是因为遗漏。
- 烟幕必须作为战术按钮判断。适合用于“通过比击杀更重要、敌方炮击/雷击威胁高、我方不需要在该点稳定击沉”的道中点；不适合用于需要击杀、命中已经吃紧、敌电探较多或烟幕后仍会导致后续火力不足的点。是否使用由 Agent 自行推演决定，不需要先问用户；若使用，说明里写使用节点、装备数量、预期收益和副作用。
- 战斗策略定稿后必须从策略反查装备与编成：每一个烟幕、退避、特殊攻击或其他能力开关都要找到具体提供者；找不到时应修改策略或配装，不能交付一个实际无法发动的开关。

### 消耗品

默认出击配置不许使用会在出击中消耗或可能消耗的装备/道具，包括但不限于：

- `応急修理要員`
- `応急修理女神`
- `戦闘糧食`
- `戦闘糧食(特別なおにぎり)`
- `秋刀魚の缶詰`
- `洋上補給`

只有在推演显示通过率、S/A 胜稳定性或资源时间成本差距很大时，才向用户询问是否接受。用户接受后，必须在 `说明` 写明预计消耗位置、触发条件、风险和替代方案。不要把消耗品作为默认补强槽填充物。

### 伴随舰大破进击白名单

默认所有战斗、空袭、对潜、夜战等可能造成伤害的节点，`EscortShipsHeavilyDamagedStrategy` 必须设置为 `1`（强制撤退）。沉船不可逆，不能为了省一次出击把伴随舰大破进击作为常规策略。

唯一可以设置为 `3`（忽略）的情况，必须同时满足：

- 该节点是当前配置的已确认白名单节点。
- 从该节点结算后的“进击”开始，到本次出击结束、归港或海域结束为止，已确认不会再发生任何战斗、空袭、对潜、夜战或其他可能触发轰沉判定的战斗处理。
- 不能只看下一格是否无战斗；如果后续路径还会进入任何战斗处理，即使中间有无战斗点，也必须强制撤退。
- 白名单依据必须来自日文 wikiwiki 海域页、KCNav/TsunKit 路线数据、用户已验证 default 配置或用户明确确认；依据不完整时保持强制撤退，并在 `说明` 中写明原因。

当前确认白名单：

- `1-6 B`：进击后到 `N` 母港终点，无后续战斗。用户 default 的“常规海域战斗策略”中对应 `Condition.Value = 13`，已设 `EscortShipsHeavilyDamagedStrategy = 3`。
- `1-6 D`：进击后到 `N` 母港终点，无后续战斗。用户 default 的“常规海域战斗策略”中对应 `Condition.Value = 11`，已设 `EscortShipsHeavilyDamagedStrategy = 3`。
- `5-6 R 到达ギミック前的 H`：仅限 `A>B>C(空襲)>H(対潜)>R(戦闘なし/港マス)` 且目标为 R 到达的阶段。该 H 后续到 R 结束，无后续战斗；若 5-6 后续阶段、开路后路线、或配置目标不是 R 到达，则不得套用。

写配置时只列出可用白名单，不要把无关的“战闘なし”中继点写进讨论或说明。中继点本身不在此规则讨论范围内，只有“最后一个可造成伤害的点之后整段出击必定无战斗直到结束”的点才进入白名单。

## 基地航空队

带基地航空队的海域必须同时设计“派哪里”和“装什么”。不能只在备注里写“Boss 集中”，也不能留下 KCPS 出击点为 `null`，除非该海域确实需要用户手选且用户明确接受。

生成规则：

- 先查 wikiwiki 海域页确认每个目标点需要的行动半径，再按生成时最新 `const.$equips[*].api_distance` 逐架读取航程；禁止凭装备名称、熟练后缀或记忆判断。`银河(熟练)` 等装备可能在多数战斗属性上更好、航程却更短，不属于无条件上位替换。
- 没有侦察机延长时，整队有效航程等于四个实际中队中最短的航程。大型飞行艇、舰上侦察机、水上侦察机或陆上侦察机可延长时，按日文 Wiki 公式 `最短航程 + 四舍五入(sqrt(侦察机最大航程 - 最短航程))` 计算，延长量最多为 `3`；侦察机本身也受自身航程限制。特殊海域的额外机制必须另行核对，不能套普通公式。
- 每支出击陆航在定稿前必须同时记录“目标点航程要求”和“按最终四格计算的整队有效航程”，并满足 `有效航程 >= 要求`。使用陆侦延长时写明最短航程、侦察机航程、延长量和结果；不能只逐架声称“能飞到”而不验算整队。
- 航程门槛满足后才比较制空、攻击倍率、命中、抗击坠、活动增伤与攻击槽数量。为延长航程占用一格侦察机时，必须和四架原生可达攻击机方案比较，不能自动认为陆侦方案更优。
- 需要派出陆航时，`SimpleSortieWorkflow` 里对应 `LandBasedAirCorpsNAction` 要设置为出击，`Point1` 和 `Point2` 要写入 `PointArchive`；防空队设置为防空，休息队设置为休息或待机。
- wikiwiki 基地航空队页说明：基地航空队每队单独设置札，出击札会让航空队可出击；出击会蓄积疲劳，出击札下恢复比待机/休息慢；防空也是独立运用札，疲劳恢复量低于休息；休息札恢复最快但会降低铝土自然恢复。生成配置时按当前需求选择，默认在每轮出击后先翻到休息以加速疲劳恢复，长时间放置前再考虑是否需要恢复待机。
- 任何 `LandBasedAirCorpsNAction` 为出击 `Mission=1` 或防空 `AirDefense=2` 的航空队都视为“用到”，都可能疲劳。出击结束后必须加入对应的 `陆航休息N` 执行单元，把该队 `Action` 改为休息 `Rest=4`，并设置 `Resupply=true`、`ResupplySquadrons=15` 顺手补给。一个 `BasicOutfitLandBasedAirCorpWorkflow` 只能处理一个基地航空队；用到多队时必须放多个执行单元。`TakeCover=3` 不按本规则自动切换休息，除非用户另行要求。
- `陆航休息N` 使用 `BasicOutfitLandBasedAirCorpWorkflow`：`SetAirplanes=false`、`SetAction=true`、`Action=4`、`SuccessIfAirCorpNotAvailable=true`、`WaitHomeAtFirst=false`、`RefreshDataBefore=false`、`ReturnRoomAtLast=false`、`EnableOnLoad=false`、`TriggerOnEnabled=false`。执行单元尾号必须始终等于 `Corps`：第一、第二、第三基地航空队分别命名 `陆航休息1`、`陆航休息2`、`陆航休息3`；即使只使用一队也不省略尾号。
- 关联出击没有独立的陆航出击后阶段。把 `陆航休息*` 挂到 `总控.SupplyAfterWorkflows`，放在真正的 `补给` 引用后面；但 `SupplyAfterFinishedEventThreshold` 只计算会发出该阶段成功事件的补给执行单元，不把 `陆航休息*` 算进去，否则会等待一个不会到达的事件而卡住。
- 陆航出击点和路线分歧选择点的 `Left/Top/Width/Height` 必须从地图图像或 KCNav/TsunKit `spots` 坐标换算，不要凭空填。常规海域优先查 `https://tsunkit.net/api/routing/maps/<sea>-<area>` 的 `spots`，该坐标系通常是标准 `1200x720`，节点中心 `(x,y)` 对应 `x/1200,y/720`。wikiwiki 地图图像、用户截图和已验证 default 配置可作为交叉验证。
- KCPS 对 `PointArchive` 是在矩形内随机取点，不是固定点中心点击。因此点选矩形必须整体落在游戏实际可点击判定方框内；不能只和目标点有小面积重叠。先确定节点中心，再取“判定方框的安全内接矩形”，在全框有效的前提下尽可能大。
- Boss 点、普通点、空袭点和访问/未访问状态的图标不同，不能共用一套目测中心。Boss 点优先使用 KCNav/TsunKit `spots` 中的 Boss 字母点坐标；若只能从截图识别，未访问 Boss 用外圈圆/特殊图标外接框，已访问 Boss 用准星交点、圆环外接框和路线几何关系共同确认。普通红/白点、空袭图标、分歧选择点也分别确认中心。
- 现有常规 Boss 点保守尺寸可用标准 `34x34` 像素，即 `Width=34/1200=0.028333333`、`Height=34/720=0.047222222`；若截图或已验证配置显示实际判定方框更小，则必须缩小。不要再使用只擦边的约 `27x25` 小框。
- 如果用户 default.json 已有同海域已验证的陆航点坐标，可以拿来校准；仍要用 wiki 地图复核节点是否相同。
- `说明` 执行单元必须写清：每队动作、每队四格飞机、每架飞机原生航程、目标点航程要求、整队有效航程、是否使用侦察机延长、点选矩形来源。点选坐标如来自 KCNav/TsunKit，应写明节点字母、`spots` 中的 `(x,y)`、换算后的中心和矩形尺寸。

示例备注内容：

```text
【基地航空队】第<编号>航空队<行动>；第1波<目标点>，第2波<目标点>；坐标来源<URL及核对日期>，实际图像尺寸<宽×高>，节点中心<x,y>，安全点选框<Left,Top,Width,Height>。
【陆航配装】第<编号>：<第1槽装备及航程> / <第2槽装备及航程> / <第3槽装备及航程> / <第4槽装备及航程>；各目标所需航程<已核对值>，延长规则<依据>，整队有效航程<计算结果>。
```
## 终止条件

终止条件必须按海域逐个从日文 wikiwiki 读取，不能从任务标题、攻略截图或模板里猜。

通常海域任务默认关闭 `StopIfShipVacancyLessOrEqualThanFlag` 和 `StopIfEquipmentVacancyLessOrEqualThanFlag`。空闲船位、装备位不是通常海域的出击门槛；只有本次明确要求保留掉落空间、以掉落为目标或另有容量安排时，才按该安排启用并在说明中写清依据。活动海域的空位要求按活动规则核对，不套用到通常海域。

生成前必须先做一张“完成条件表”，至少包含：

```text
海域 | 计数目标 | 胜利等级 | 需要次数 | wiki依据
<当前海域> | <目标点或状态> | <所需评级> | <实际次数> | <来源及核对日期>
```

规则：

- `StopIfBossBattleRankHigherOrEqualThanValueRank` 只表示胜利等级，不表示次数。
- `StopIfBossBattleRankHigherOrEqualThanValueThreshold` 必须等于该海域 wiki 要求的次数。
- Boss A 胜两次：rank 为 `3`，threshold 为 `2`。
- Boss S 胜一次：rank 为 `2`，threshold 为 `1`。
- Boss A 胜以上一次：rank 为 `3`，threshold 为 `1`。
- 特定节点任务必须先确认节点编号，再使用点位 rank 条件，不要误用 boss 条件。
- 运输条应使用 `SimpleSortieWorkflow` 的 `MapHpInRangeFlag` 和 `MapHpInRangeValueGauge = Tp` 做出击前检查，避免运输条已清空后继续出击。活动海域可能连续出现两条 TP 条，因此总控 `OnAutoStop()` 不能只检查量值为空、归零或不再是 TP：还应记录生成时 `api_gauge_num`，并由额外出击检查函数在每轮实际出击前主动刷新 `mapinfo`、通过专用 `UserEvent` 把阶段号和 TP 发给总控的 `OnFilterEvent` 保存；战后在阶段编号变化或 TP 相对本轮出击前基线反向增大时停止。禁止用可能早于数据刷新的 `OnEnabled` 建立运行时基线，也禁止用会触发流程的 `OnEvent=True` 接收内部快照。详细状态机见活动出击 SKILL 的“活动 TP 条停止”。
- 普通海域多段 HP 条不能只用地图 HP 判断阶段，因为 P2 清空后可能立即切到 P3 新血条。此类阶段优先使用指定 boss 点旗舰击沉次数、指定点 rank 次数、到达终点次数，或已确认的 API 阶段字段；若字段不可靠，写入说明并不要交付无人值守配置。
- 用「指定 boss 点旗舰击沉次数」(`StopIfEnemyFlagShipSunkFlag: true` + `ValueConditionType: 1` + `ValueConditionValue: <boss 节点进入边值>` + `ValueThreshold: <次数>`) 时：**`ValueConditionValue` 必须是本段 gauge 的 boss 节点进入边值，多段海图逐段核对——别把上一段的 Boss 编号复制到下一段**，否则总控会指向永远到不了的点。通常海域的击破次数条按攻略确认次数设置；活动 HP 条的磨血按 `MapHp`/`OnAutoStop` 判断进度，不启用固定击沉次数；活动 HP 条的斩杀/击破必须在 Boss 旗舰击沉 1 次后直接停止，并把量值变化检查保留为后备。TP 条不适用 Boss 旗舰击沉停止。路线规格只在需要直接击沉停止的 Boss 节点声明 `BossKillCount`，校验器据此检出漏设、节点和次数错配。
- KCPS 界面中的“到达给资源的终点”是历史文案，不表示只统计资源点。`StopIfArrivedEndPoint` 实际统计 KCPS 是否识别到带标准“帰”按钮的归投终点页面；资源终点和到达后直接母港归投的港口终点，只要显示该标准页面，都可以用此条件。配置值应为 `StopIfArrivedEndPointFlag: true`，阈值等于攻略要求的实际到达次数。
- 使用前必须从日文 Wiki、攻略实测或运行日志确认目标点是出击终点，并在到达后显示标准归投页面。第一次试运行后，日志应出现“到达了出击终点”，总控计数应增加一次；只经过前一战斗点后撤退不得增加计数。若没有该日志，不得继续把它当作可靠停止条件，应改用已验证的 API 状态、点位结果或人工确认。
- 对当前资料确认的无战斗终点，且到达后游戏直接归港的场景，可使用 `StopIfArrivedEndPoint` 统计到达次数。必须逐次核对目标节点行为，不能沿用旧活动点名或节点类型。
- 已验证行为中，`StopIfArrivedEndPoint` 不会统计 1-6 护卫成功/N 港到达。1-6 这类任务不要使用“到达给资源的终点 X 次后停止”，也不要用纯循环次数，因为撤退会被误计。
- 1-6 护卫成功/N 港到达类任务应按路线最后一个可造成伤害的战斗点做点位 rank 计数：例如 `C-H-K-M-J-D-N` 路线用 D 点 `Condition.Value = 11`、rank `7`（E 胜以上，表示有战斗结果即可）、threshold 等于任务要求次数。若改用经 B 到 N 的路线，则必须先确认 B 点的当前 `Condition.Value` 后再写。
- 如果 wiki 写“各2回”“反復”“2回クリア”，就不能设置成 `1`。
- 不要留下模板残留次数，例如任务只要求一次却设置成 `2`，或任务要求两次却设置成 `1`。
- 修改现有配置时，必须复核所有海域，而不是只改报错的那一张图。

## 生成后验收

按公共两阶段交付流程运行出击收尾脚本。它只编排现有小工具，不替代任务条件、路线、编成和配装推演：

```powershell
$SKILL_ROOT = '<SKILL_ROOT>'
$WORKSPACE_ROOT = '<WORKSPACE_ROOT>'
$env:KCPS_WORKSPACE = $WORKSPACE_ROOT
$target = Join-Path $WORKSPACE_ROOT '<JST_YYYYMMDD> 单次 出击 <任务名称>.conf.json'
pwsh -ExecutionPolicy Bypass -File (Join-Path $SKILL_ROOT 'scripts\poi-kcps-api\validate\KCPS-FinalizeSortieConfig.ps1') -Path $target
pwsh -ExecutionPolicy Bypass -File (Join-Path $SKILL_ROOT 'scripts\poi-kcps-api\validate\KCPS-FinalizeSortieConfig.ps1') -Path $target -CheckOnly
```

- 第一次运行实际应用集合形状、执行单元顺序、战斗策略、等价船轮换、扔桶和陆航休息的确定性修正，再执行任务 ID 与总校验。
- 第二次 `-CheckOnly`、幂等阈值和任务 ID 跳过限制遵守公共规则。
- 有舰载机或陆航时，统一收尾之后仍要运行 `KCPS-AuditAirPower.ps1` 并把四档制空结果回填 `说明`；该项依赖每个海域的目标制空，不能由通用收尾脚本猜测。

启动前再用 `KCPS-State.ps1` 查询任务指定船。船正在远征、入渠或其他舰队时，应向用户报告“当前不能立即启动”，但不要因此把正确的固定编成降级成次优方案；等占用解除后运行即可。

## 校验规则时效

读取 `KCPS-ValidateConfig.ps1` 输出中的 `HardcodedRuleCheck` 和 `HardcodedRuleFreshnessWarnings`。时效警告不计入配置错误，但过期、尚未核验或缺少核验日期的规则不能直接作为当前结论；先核对对应资料，再决定是否采用其校验结果。

新任务、新海域、新机制尚未被脚本覆盖时，`ProblemCount=0` 不能证明战术完全正确。仍须按资料查询顺序人工推演，并把不确定点写入 `说明`。新生成的任务配置不得使用允许缺失路线或跳过必要校验的历史配置兼容选项。

## 地图点编号与路线规格

KCPS 条件战斗策略的 `Condition.Value` 通常对应 KCNav/TsunKit 路线表的进入边 ID。同一个物理节点从不同前驱进入时可能有不同值，不能按节点字母猜测，也不能沿用旧任务的路线表。

1. 从当前任务条件、编成与最新路线资料确定地图和有序路线，连同难度、阶段开放状态及来源保存到私人工作区。
2. 查询当前地图的进入边，逐条核对路线相邻点。下面的占位符须由本次查证结果替换：

```powershell
$KCNAV_MAP = '<当前KCNav地图号>'
$map = Invoke-RestMethod ('https://tsunkit.net/api/routing/maps/' + $KCNAV_MAP)
$map.result.route.GetEnumerator() |
  Sort-Object { [int]$_.Name } |
  ForEach-Object { [pscustomobject]@{ EdgeId=$_.Name; From=$_.Value[0]; To=$_.Value[1] } }
```

3. 逐点查证战斗类型、阵型、夜战、进退和目标完成条件。只在实际出现操作界面的节点写相应策略；能动分歧才设置 `DefaultWayPoint`。
4. 覆盖当前编成实际可能进入的所有分支。能继续到达目标的分支应完整配置；无法到达目标且出现阵型选择页的分支可使用 `Refresh(7)` 刷新回港。不能刷新时按实际节点机制设计更早的止损或战后撤退，不在无选择界面的点伪造操作。
5. 将最终方案写入 `<WORKSPACE_ROOT>/.work/route-overrides.json` 的 `Routes`。每条方案至少明确下列字段，不以公共节点参考代替本次方案：

| 字段 | 本次输入 |
| --- | --- |
| `Id` | 该任务、地图和阶段的唯一方案标识 |
| `Sea`、`Area`、`KcNavMap` | 当前 KCPS 海域值及对应的 KCNav 地图号 |
| `GroupNameRegex` | 精确匹配目标配置的名称；同一出击执行单元必须恰好匹配一条方案 |
| `Source`、`LastVerifiedJst`、`RefreshAfterDays` | 本次核对的来源、日本时间和复核周期 |
| `Route`、`Nodes` | 有序节点及实际进入边、类型、策略和目标条件 |
| `BranchCoverageRules` | 必须覆盖的分支，以及需刷新回港的进入边 |
| `ExpectedFleetSpeed`、`ShipTypeCountRules`、`LosBranchRules` | 实际适用的速力、舰种和索敌要求；不适用的约束不照抄旧方案 |

基础低速船通过装备提速时，用 `ExpectedSpeedEquipmentOverrides` 逐船登记当前所需装备与证据。允许退避时按可能离队的舰船或组合重新计算带路、索敌和偏航风险，并保存保守余量。两个名称相似的阶段不能共用未经核对的方案。

6. 运行 `KCPS-ValidateConfig.ps1 -RequireRouteSpec -FailOnProblems`。零匹配、多匹配、缺点、进入边不符或关键证据缺失都不能作为通过。`GroupNameRegex` 应收窄到本次配置，不能通过调整数据顺序选择旧方案。

公共 `KCPS-RouteSpecs.json` 的 `NormalMapFacts` 仅提供待核对的通常海域节点参考；其中 `Source` 是公开资料核对入口，不表示已完成当前版本核验。该表没有任务匹配、配船配装和路线顺序，不能自动生成可运行路线。当前地图、活动阶段与航程的独立证据入口见 [运行时计划与证据](运行时计划与证据.md)。

`spotHistory/currentNode` 可用于运行中纠错，但不能成为唯一规划来源。发现偏差时更新本次方案并重新验证。

验收标准：

- `ProblemCount = 0`。
- `HardcodedRuleFreshnessWarnings` 为空，或已逐条刷新资料并确认当前配置不受过期规则影响。
- `KCPS-ValidateQuestIds.ps1` 的 `ProblemCount = 0`，每个 `接任务` 都能在当前游戏 API 中验证到 ID 和标题。
- `BrokenRefCount = 0`。
- `RelatedThresholdProblems` 为空。
- `PostSortieBucketDockingProblems` 为空；每个出击配置的 `DockingBeforeWorkflows` 包含 `入渠` 和 `捞出`，联合舰队还须以 `组成联合舰队` 为第一个启用项；`DockingAfterWorkflows` 只包含 `扔桶`，`AutoStoppedDisableWorkflows` 包含所有入渠执行单元。
- `LandBaseRestProblems` 为空；所有设置为出击或防空的基地航空队都有对应出击后 `陆航休息N`，且 `SupplyAfterFinishedEventThreshold` 没有把 `陆航休息N` 计入。
- 没有空编成候选行。
- 没有同 base 舰船同时出现在同一 `编成` 执行单元；运行 `KCPS-ValidateConfig.ps1` 检查 `SameBaseOrganizeProblems`。
- 通常海域配置已经对目标文件运行 `KCPS-EnableEquivalentShipRotation.ps1`，所有可用等价船已写入多候选自动轮换；再次 `-CheckOnly` 为 `Updates=0`，并且 `MultiCandidateRotationProblems` 为空。
- 每个改装槽位有且只有一个选择器，除非明确设计为 fallback。
- 每艘被改装舰都有 `Slot = 6` 补强增设策略，并设置 `IgnoreSlotNotAvailable = true`。
- 配装表中没有同一件唯一/稀缺装备被同一配置重复占用；运行 `KCPS-ValidateConfig.ps1` 时也必须确认同一 `改装` 执行单元内精确装备名需求不超过当前库存。
- `接任务` 使用游戏 API 的 `api_no`，且 `FailIfNotExist = true`、`SuccessIfFull = false`。
- 同一改装执行单元没有重复堆叠舰队级功能装备；尤其彩云默认不超过 1 架，超过时必须有索敌/触接计算和说明。
- 舰载机槽位顺序和搭载数已按制空、输出、触接、熟练损耗核对。
- 说明执行单元已列出制空目标、无熟练最低、仅战斗机满熟练、所有飞机满熟练四个数值；如数值来自工具估算而非制空权シミュレータ，应写明这是 KCPS 工具估算。
- 已按本次路线证据逐节点检查舰种、船数、速度、索敌和阶段分歧；采用额外战斗或其他替代路线时，说明收益、损耗与风险。
- 夜战、反潜、防空、对地、PT、索敌等机制需求已和海域节点逐项对应。
- `DefaultStrategy` 与 `DefaultBossBattleStrategy` 都只是安全兜底：阵型、夜战为手动，进退为撤退，伴随舰大破为强制撤退。
- `DefaultBossBattleStrategyFlag = false`，Boss checkbox 不选中；Boss 点必须作为 `Strategies[]` 里的地图点条件策略。
- 每个 `Strategies[]` 都使用 `Condition.Type = 1` 地图点规则，并按实际出击顺序排列；分歧路线只在分歧子段拆开。
- 只有路线规格标为 `waypoint-select`/`RequiresWayPoint=true` 的能动分歧策略具有非空 `DefaultWayPoint`；其他所有条件策略和两个默认策略的 `DefaultWayPoint` 均为 `null`，不存在全零坐标占位对象。
- 出击策略中没有普通战斗点或旧式 `航空戦マス` 的 `DefaultMidnight = 0`，除非用户要手动夜战；只有已确认为现代 `空襲戦`/`LongDistanceAirBattle` 的条件策略例外，应保留手动。
- 出击策略中没有 `DefaultMidnight = 3..7`。
- 条件策略里的伴随舰大破默认强制撤退；只有已确认白名单点可设忽略，并且 Memo 必须写明依据。
- 没有模板残留的无关 `Strategies`。
- 每个海域的 boss/节点/终点条件、胜利等级和次数与 wiki 完成条件表一致。
- 所有执行单元的通用触发字段符合公共规则；出击总控的 `EnableOnLoad` 另按“跨海域推进”设置。
- 通常海域的完成消息使用 `任务编号 海域 Clear`，多阶段包含阶段标识；活动海域使用 `E编号 阶段 用途 目标 条件 Clear`。后续监听字符串必须完全一致；只有完成判据达成才能发送，安全停止不得推进下一海域。
- 配置名称和文件名符合本次约定及适用的命名规则。

还要核对以下结构；用户授权界面检查时可在 KCPS 中目视确认，否则通过配置字段与模型定义检查，并说明未进行界面加载验证：

- 每个海域是一个配置。
- 执行单元短名清楚。
- `总控` 只引用本配置内的执行单元。
- `总控.DockingBeforeWorkflows` 包含 `入渠` 和 `捞出`；联合舰队还以 `组成联合舰队` 为第一项，但它不计入入渠完成阈值。`DockingAfterWorkflows` 只包含 `扔桶`；`AutoStoppedDisableWorkflows` 包含所有入渠执行单元。
- 使用陆航出击或防空的配置中，`陆航休息N` 位于 `出击` 后方，并挂在 `总控.SupplyAfterWorkflows`；`SupplyAfterFinishedEventThreshold` 仍只按真正的 `补给` 执行单元计数。
- `编成` 候选行正确。
- `改装` 槽位和增设槽正确。
- `出击` 阵型、夜战、进退策略符合路线和任务目标。
- `总控` 的停止次数与 wiki 完成条件一致。

## 常见失败模式

- 总控阈值比关联执行单元数量大，导致卡在入渠、补给、编成或改装后。
- 把自动停止当成任务完成，因达到安全上限而误发 `Clear`；或省略整条接续链后，仅凭已有通知检查为空就宣称多海域流程完整。
- 空候选行导致编成选船失败。
- 同一舰队同时选同 base 舰船，KCPS 会在前面位置选中后把后面同 base 候选排除，典型报错是“第 N 个位置选取候选船失败”。
- 用旧字段导致 KCPS UI 看起来空、实际也无法执行。
- 改装没有使用 `Ships[].Slots[].Equipments[]`，导致装备槽为空。
- 只按装备类型选装，没参考舰船特定加成、装备协同、海域需求和库存数量。
- 稀缺装备重复分配给多艘船，KCPS 执行时后面的船选不到装备。
- 舰载机没有按搭载数和槽位效果放置，导致制空不足、输出降低或熟练度损耗异常。
- 只看任务要求舰种，不逐节点验带路；忽略分歧优先级造成额外战斗，使损耗和燃弹惩罚成为主要失败原因。
- 路线规格只按海域名匹配，导致新任务错误套用旧任务的节点集合；必须用锚定的任务/海域/阶段正则，并要求唯一匹配。
- 只看 `KCPS-ValidateConfig ProblemCount=0`，没有二次运行规范化与增强工具；如果 `WouldFix/Changes/Updates` 仍非零，交付文件并非稳定终态。
- 把可空的未限制字段 `null` 强制改成空数组，而 JSON 写回又把空数组规范化为 `null`，造成工具每次都报告更新；可选字段必须按 KCPS 实际往返形态做幂等判断。
- 陆航休息工具和扔桶工具各自重排出击后的执行单元，导致两者反复互相移动。规范顺序固定为 `出击 → 陆航休息N → 扔桶 → 出击完成`（活动采用相应通知单元）；统一收尾后两个工具的 `-CheckOnly` 都必须为零变更。
- 审计昼战顺序时只看舰船基础射程，忽略舰爆、整备员等装备改变后的有效射程。
- 漏写 `Slot = 6`，导致已开孔舰补强增设槽空着。
- 模板残留 `Strategies`，在错误节点夜战、撤退或使用错误阵型。
- Boss 只需 A 胜却固定夜战，造成疲劳和资源浪费。
- 使用未实装条件夜战值 `3..7`。
- 跨配置使用原生 GUID 触发，导致流程不可靠。
- 忘记接任务，满足条件也不计数。
- 把“各2回 A勝利以上”误写成 threshold `1`。
- 把 `TriggerOnEnabled` 当成“启用监听”而设为 true，导致加载/启用时立即开跑。
