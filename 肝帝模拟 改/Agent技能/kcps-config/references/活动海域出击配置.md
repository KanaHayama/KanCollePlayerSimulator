## 首要原则

1. 涉及不可逆贴条时，先明确当前标签兼容性与用户的后续保留计划，再做单阶段选船。保留计划可以由用户提供、参考攻略或独立规划；没有未来海域资料时应记录未知范围，不虚构完整锁船表。
2. 采用活动攻略或锁船表时，每次生成或重配前都重新读取相关基础知识、阶段正文、图片、修订时间和分配表。独立方案应重新查证其实际依赖的标签、阶段和带路证据。
3. 活动海域禁止通常海域的等价船疲劳轮换。主出击舰队每个位置固定一个明确舰船实例，避免轮换候选误贴条。
4. 未确认标签、阶段、难度、目标次数、路线或地图点进入边时，不生成可运行配置。
5. 攻略样例是角色分配依据，不是账号配置。必须结合实际持有、多号机、改造、练度、开孔、装备和后续阶段需求重新推演。
6. 采用攻略中的具体编成时，逐船转录为 `GuideFleetBaseline`，记录来源并解释实际调整。用户自定方案或尚无完整攻略时，按当前标签、阶段、带路与战斗条件独立规划并保存证据，不伪造攻略船名单，也不把攻略偏好当成游戏强制条件。

## 调研顺序

每个阶段按以下顺序调查：

1. 明确当前地图、难度、阶段、目标及用户保留要求。查询标签兼容性、开放状态和后续阶段需求。
2. 选择规划依据：采用攻略时读取全局说明、当前阶段正文、相关图片与分配表；独立规划时保存当前机制来源和自己的分配理由，不要求不存在的攻略样例。
3. 交叉验证目标点、次数、胜利等级、舰队形态、路线、制空、索敌、陆航、支援和特殊机制。
4. 从本次实时账号数据建立可用舰船和装备候选，核对实例、贴条、改造、开孔和库存，不把旧快照直接当成当前状态。
5. 将候选与用户确认的保留计划、允许标签及阶段需要求交集；路线可达不能代替标签兼容或保留要求。若调整分配，记录对后续阶段的影响。
6. 采用攻略中的固定船数、舰种或角色建议时，查清哪些是游戏带路条件、哪些是攻略偏好。前者写入 `ExpectedFleetCounts`、`ShipTypeCountRules` 等硬约束；后者允许有依据的调整，并在备注说明。
7. 路线规格用 `GuideBaselineMode="Guide"` 表示采用攻略基准，同时保存 `GuideFleetSource` 与按舰队分组的 `GuideFleetBaseline` 正则列表；独立方案使用 `GuideBaselineMode="Independent"`，保存 `PlanningSource` 与 `PlanningReason`。两种模式都检查标签、路线、舰种、槽位和库存。

采用 `GuideFleetBaseline` 时，船名正则必须覆盖本次允许采用的完整改造链形态，包括未改、`改`、`改二`及其派生形态；不能用 `(?:改二)?` 这种会跳过中间 `改` 形态的写法。生成后必须以实时选中的船名重新执行攻略船队基准校验，任何实际船名不能匹配时均阻断交付。

带路要求高速或高速+时，必须把要求写入路线规格，不能只写在备注。使用 `ExpectedFleetSpeed: "Fast"` 声明全队高速；基础低速船依靠装备满足时，再逐船填写 `ExpectedSpeedEquipmentOverrides`，包括舰队、位置、船名正则、所需装备、日文 Wiki 证据和核对日期。不同船的提速规则不同，禁止把“锅炉+涡轮”当成通用答案；例如夕张改二特与 Samuel B.Roberts Mk.II 等存在特殊规则，必须按当前日文 Wiki 单独查证。校验器应读取账号主数据与最终改装执行单元，确认每艘基础低速船确实带齐该船所需装备；无法取得主数据时不得把高速条件视为已验证。

舰种或舰数决定自动路线分歧时，也必须把条件写成路线规格中的 `ShipTypeCountRules`，至少记录参与判断的舰种集合、最小值、最大值或精确值及分歧理由。校验器应统计所有实际出击舰队后核对这些约束，确认配置名称、备注和条件战斗策略声明的路线确实能由该编成到达；只检查舰队总人数或逐位置船名不足以证明带路正确。存在优先级分歧时，必须把所有可能抢先命中的条件一起建模，不能只写最终一条规则。

路线分歧表按从上到下的顺序判定。应用舰数、舰种、速度或索敌条件前，必须先核对更高优先级的阶段状态，例如“某条边尚未开放”“某出发点尚未开放”或“前一条件完成后才开放”。同一个分歧点在开路阶段与后续削甲回访时可以使用不同编成：不得把后期“六船以上转往Boss”的规则反推到该边尚未开放的开路阶段，也不得把开路期可用的六船方案直接复用到边已开放后的回访。此类路线规格必须写入 `RouteBranchAssertions`，记录相邻边、实际命中的规则顺序、阶段状态、出击舰队编号、准确船数、备注明示正则、外部证据与核对日期；校验器同时核对最终身份检查、`ExpectedFleetCounts` 和备注。

改变舰种时先复核出发点，再复核道中分歧和目标点；已有正确贴条不会强制舰队走原出发点。后期回访必须排除新开放出发点的更高优先级条件，不能只检查目标点附近的战舰上限。把当前选用路线方案的出发点限制一并写入 `ShipTypeCountRules`，使用主数据舰种名称而非数字ID；“重巡级”等集合必须含航巡，数量统计只包含实际参战舰队，排除支援。交付前核对实际参战舰队是否满足已声明的出发点舰种限制。

攻略给司令部且后续存在索敌分歧时，不能让司令部成为摆设，也不能未经计算直接开启退避。先用最终账号配装计算完整舰队索敌；游击部队司令部按每一艘可退避船逐艘审计，普通联合舰队司令部按护卫退避的两船组合审计。路线规格用 `LosBranchRules` 记录公式、系数、阈值，并分别设置 `AuditEverySingleRetreat` 或 `AuditEveryPairRetreat`；备注记录完整值、退避后的保守最低值与余量。只有所有适用的退避组合仍满足带路时，才在对应战斗点开启退避；否则关闭退避，或为偏航分支配置明确的刷新回港策略。

采用攻略作为依据时，网页正文与图片同等重要。实际引用图片中的舰船、装备、路线、标签角标、陆航和备注都要读；只抓取网页文本不算完成调研。

攻略同时给出多套合法正攻舰队或多种特殊攻击时，通用倍卡排序只能作为候选起点，不能越过账号实况直接决定答案。应按实际舰队形式，为参与比较的候选构造完整且满足带路的方案，比较实际可用实例的练度、改造、婚舰、开孔、幸运、命中、资源消耗、特殊攻击发动条件、可实现配装和阶段敌编成；舰队形式变化时还要重算制空、护卫暴露、路线与阵型。不能只把一对战舰换进旧舰队，也不能因为攻略笼统称某方案倍率更高，就让低练度未开孔组合压过账号中明显更完整的另一套攻略合法组合。最终选择及被放弃方案的账号差异写入 `【候选与排除】` 和 `【选船结论】`。

攻略同时给出图片主方案与正文备选方案时，先把图片主方案逐槽转录为结构化基线，再分别计算备选方案。不得因正文更容易提取而把备选方案静默当成默认；采用备选或账号自拟陆航时，必须在 `【陆航方案比较】` 中列出攻略主方案、最终方案及航程、每波制空状态、目标伤害、活动增伤和熟练度维持方面的差异。证据不足以区分优劣时，记录不确定性并结合用户目标选择，不把攻略排序当成强制规则。

采用攻略陆航方案时，路线规格必须区分“攻略四槽原案”和“账号优化定稿”。`GuidePrimary`、`GuideAlternative` 保存 `LandBasedAirCorpsGuideBaseline`；`AccountOptimized` 保存从攻略提取的目标舰种、航程、每波制空线和基地防空线等 `LandBasedAirCorpsGuideRequirements`，并另存最终 `ExpectedLandBasedAirCorps`。禁止把账号最终四槽复制成攻略基线，否则校验会在“最终方案等于自身”的伪比较中失去意义。

运输阶段计算最终方案的 S/A 胜 TP 与所需轮次；采用攻略图片作为基准时，逐船逐槽转录成结构化对照，计算攻略样例、账号适配方案各自的 S 胜 TP、A 胜 TP 与完成整条运输条所需轮次。不得只比较到达率或胜率，也不得把正文中的舰种骨架当成已经读完图片。攻略以烟幕、陆航、支援或司令部退避承担风险时，不得再用大量主舰队槽位重复购买同一种稳定性，造成运输量显著下降。任何相对攻略图片的舰船或槽位偏离都要量化 TP 差额，并在 `【攻略与分配】`、`【候选与排除】`、`【配装对照】` 中说明账号限制和收益权衡。

攻略图片使用普通大发时，也必须继续检查账号中的特大发、武装大发、战车型大发及其改修等级，不能把攻略装备名当成最终答案。普通大发与纯特大发的运输 TP 相同，但纯特大发及其改修可能提供不损失 TP 的战斗收益；应优先使用不会破坏后续对地阶段关键配装的上位实例。多个同名不同改修实例由 KCPS 高改修优先选择时，改装舰船顺序应从更需要高改修装备的位置向前执行，并在备注中说明分配逻辑。

## 通关后捞船

- 捞船以单位时间、单位资源取得目标舰的概率为目标，而不是单轮油弹最低。比较完整航次的抵达率、S/A评级分布、各评级掉率、补给、修理、飞机补充、用桶及整备时间；不得把公开掉率当作本账号的S胜率。没有可靠模拟时，列明已验证的制空、航程、索敌与候选代价，不编造周回成功率。
- 同等角色比较战斗准备程度与实际周转成本，不把婚舰或副本编号作为必选条件。婚后油弹在补给时按实际缺额乘0.85向下取整，非零项最低为1；修理和补充飞机没有同一折扣。高等级的命中、回避、对潜、索敌和婚后耐久也影响周转，不能只比较未婚面板油弹，不能把二号机或低等级等同于低成本。
- 不同改造形态应单独比较：同样已婚时，低消耗形态可能适合周回，但必须明确其火力、耐久、搭载量及特殊攻击代价。已通关且没有后续保留需求时，不因旧模板使用副本而保留主力。
- 先确认所需海域通关状态、难度、通关后的敌编成与贴条规则，再重做路线和配装。`StageDesign.Phase="Farming"` 必须声明 `PostClearRequiredMaps` 和 `DropTargets`；通关后捞船不继承HP/TP阶段门禁。
- 按用户捞船计划可将多个通关海域的独立捞船配置装入文件名含“捞船”的同一文件；这只豁免文件名的单阶段限制，各内部配置仍须完整标明海域、目标船、目标点、舰队及路线，并分别校验。
- 任意目标船掉落停止使用总控原生 `StopIfGetShipFlag`，`StopIfGetShipValueShipName` 为每个名称经正则转义后以或连接、首尾锚定的表达式。原生检查遍历本轮所有战斗的新掉落，因此道中捞到目标也会触发；不是检查已有收藏，也不是见到任意普通船就停止。获得其一后再继续捞另一艘时，用户需缩减停止目标。
- 删除模板残留的胜利次数、旗舰击沉、削弱计数和血条停止脚本；保留多轮安全上限、容量及错误保护。自动循环不强制陆航满熟练度。关闭支援时同步移除支援编成、改装、入渠和补给关联。
- 运行 `validate/KCPS-ValidateEventSortieConfig.ps1` 的捞船校验，确认已通关、目标船名正则正确，且没有残留任务停止条件或一轮上限。

## 多号机定义与解析

同一艘船的改造前后视为同一改造链。编号规则：

- 仅把已锁定、预期长期保留的实例纳入正式多号机编号。
- 在同一改造链内按舰船实例 ID 从小到大排序：最小为一号机，其后依次为二号机、三号机。
- 未锁定实例标记为“未纳入编号”，不得自动当成最末号机，也不得在不可逆贴条决策中自行选用。
- 不因改造形态不同而重开编号；改造前、改、改二和可互转形态属于同一编号序列。
- 攻略或分配表写“船名2”时，先解析账号中的二号机；没有该编号或状态不满足时，重新做全局分配，不可悄悄改用一号机。
- 编号只用于身份识别，不自动代表练度、战力或选船优先级。先核对用户保留计划、现有标签、改造形态和后续需求，再选择实例。
- 本次采用的锁船计划明确指定副本编号时，核对真实编号；缺该副本或条件不符时重新规划，不静默替换。
- `FinalTagCopyPolicy` 是可选的本次选船策略。只有明确采用“优先较早编号”等规则时，才校验该优先级与逐船例外；不因未选一号机、婚舰或最高等级实例就判错。
- 无论采用何种优先级，实际实例必须存在、已锁定、满足标签与阶段条件，且没有违背用户明确的保留要求。选择理由写入私人方案。

使用工具实时解析：

```powershell
pwsh -File (Join-Path $SKILL_ROOT 'scripts\poi-kcps-api\inspect\KCPS-ResolveEventShipCopies.ps1') -Name '<船名>'
pwsh -File (Join-Path $SKILL_ROOT 'scripts\poi-kcps-api\inspect\KCPS-ResolveEventShipCopies.ps1') -ShipId <ID列表> -Format Json
```

选择舰船时至少比较：锁船表指定编号、后续阶段需求、特效倍率、改造形态、先制反潜/对地/运输能力、开孔状态、当前贴条和是否远征占用。不能只按等级或“尽量用二号机”排序。

## 阶段与标签规划

- 开路、解谜、运输、P1、P2、P3、削甲和最终击破分别建立独立配置（workflow group），不得把不同目标的执行单元混进同一配置。
- 每个配置的说明写明：当前阶段、目标点与次数、预计贴条、允许混入的既有标签、选船与不用替代船的理由。路线规格同时用 `ExpectedSallyLabel` 保存标签名，并用 `AllowedSallyAreas` 保存游戏 API 的非零 `api_sally_area` 允许值；未贴条的 `0` 始终可进入候选。
- 若攻略说明两个标签可混编，仍要分别记录每艘船已有标签；“可混编”不等于可以忽略后续分配。
- 支援舰队不贴出击标签，但仍要避免占用后续马上需要的主力与装备。
- 已贴条船只能在确认本阶段允许该标签后使用；看到 `api_sally_area` 非零而无法对应标签时暂停交付。活动校验必须按身份检查声明的所有实际参战舰队逐队检查：单舰队检查实际出击队，联合舰队检查第一、第二舰队，游击舰队检查第三舰队。任一已贴条实例不在 `AllowedSallyAreas` 中，或路线规格没有数值映射而无法证明兼容，都属于硬错误，不能降级为警告。

### 配置文件按推进阶段分组

- “配置文件”是可包含多个配置的容器；“配置”是一个完整的 workflow group；“执行单元”是配置 `List` 中的单个 workflow。三者不得混称。
- 同一海域、同一推进阶段的多个目标必须合并到一个配置文件，但每个目标仍保持独立配置。不得因舰队形式、目标点、陆航或支援不同而拆成多个文件。
- 只有当前一批开路条件完成后才会解锁下一批目标时，才拆为 `开路 第一阶段`、`开路 第二阶段` 等文件；同时开放的目标不得人为分批。
- HP 条文件按本次计划的前置依赖排列：磨血、需要的削甲目标、斩杀。只生成实际需要的变体；没有要求时不自动追加全自动与半自动两套。`RequiredFinalVariants` 仅用于本次显式要求的变体集合。TP 条与只有一个配置的阶段也可使用阶段容器文件名。
- 配置文件命名为 `E# P# 开路.conf.json`、`E# P# 开路 第#阶段.conf.json` 或 `E# P# 攻略.conf.json`；文件名只标明阶段用途，不携带单个目标、舰队形式、陆航、支援和路线码。内部配置名仍保留这些详细信息。
- 削甲或破甲配置回访当前海域更早阶段的 Boss 点时，目标点后必须紧跟半角阶段标记 `(P#)`，格式为 `E<当前区域> P<当前阶段> 削甲 <目标点>(P<原Boss阶段>) <评级与次数> ...`。阶段号表示该点原本所属的 Boss 阶段，不是当前削甲阶段。
- 普通战斗点、空袭点、到达点以及当前阶段 Boss 不加上述标记；例如 W 不是旧阶段 Boss 时仍写 `W点`，不得为了醒目误写成 `W点(P#)`。多字符节点名保持完整，因此节点本名 `P1` 应写 `P1点`，不能误解为阶段标记。
- 生成前以最新日文 Wiki 的海域阶段表核对历代 Boss 点，并把 `点名 -> 原 Boss 阶段` 写入私人 `route-overrides.json` 的 `EventBossStages`。不得只凭攻略图片、当前路线或字母外观推断。最终化流程会先运行 `normalize/KCPS-NormalizeEventHistoricalBossNames.ps1`，再由通用校验器拒绝漏标、错标及普通点误标。
- 合并后每个配置必须完全自包含：所有关联执行单元只指向同一配置 `List` 内的 GUID；同一文件内配置名和 workflow GUID 都必须唯一。不允许跨配置引用或静默重映射重复 GUID。
- 使用 `normalize/KCPS-MergeEventStageConfigs.ps1` 按预期显示顺序传入源文件。先保留源文件生成和校验合并文件；通过通用与活动专用校验后，再删除被替代的散文件。

## 模板选择

按实际舰队形态选择模板，不自行拼凑脆弱结构：

- 单舰队：[活动 单舰队.conf.json](<../assets/templates/event/活动 单舰队.conf.json>)
- 联合舰队：[活动 联合舰队.conf.json](<../assets/templates/event/活动 联合舰队.conf.json>)
- 游击部队：[活动 游击部队.conf.json](<../assets/templates/event/活动 游击部队.conf.json>)

模板只提供完整结构。复制后必须替换所有舰船、装备、地图、路线、终止条件、陆航、支援、说明和关联执行单元；再按本阶段实际方案裁剪，删除不用的支援或陆航执行单元并重新计算关联阈值。不得从零拼出一个看似能跑、实际遗漏活动模板职责的简化流程。

联合舰队模板中的 `组成联合舰队` 不能只保留为孤立执行单元：总控必须把它作为 `DockingBeforeWorkflows` 的第一个启用项。该执行单元借用出击前入渠阶段触发，但不发送入渠完成事件，因此 `DockingBeforeFinishedEventThreshold` 只统计其后的 `BasicDockingWorkflow`，不得按关联项总数计算。任何最终化、入渠增强或执行单元重排工具都必须保留这条引用。

活动配置的执行单元显示顺序固定以 `备注 → 总控 → 抑制其他配置` 开头，其余执行单元排在三者之后。`抑制其他配置` 是活动模板的常驻职责，不属于可裁剪的支援空壳：它在每次循环开始前发送“正在连续出击”，并挂入总控的出击前任务阶段，用于抑制会争用舰队的其他自动配置。活动配置必须保留并正确关联它，但不得因为它先于编成被总控调用，就把它排到总控前面。

该执行单元是 `SimpleRaiseUserEventWorkflow`，只发送 `UserEvent`，不会发送接任务或交任务完成事件。总控的 `QuestBeforeFinishedEventThreshold` 必须保持为 `0`：这样总控触发消息后立即继续后续流程。不得按关联执行单元数量把阈值改成 `1`，否则总控会在“出击前接交任务”阶段永久等待。`TriggerOnEnabled` 仍遵守公共规则保持 `false`，由用户手动触发总控。

活动内部配置名末尾的路线码必须逐点生成，容器文件名仍按阶段命名而不附路线码：先写出发点编号，再按实际经过顺序原样拼接每个节点的完整名称。节点前缀不得合并，例如 `第一出发点→A→B→C→C3` 必须写成 `1ABCC3`，不能写成会漏掉 C 点的 `1ABC3`。多字符节点如 `A1`、`C2`、`C3`、`K1` 都是不可拆分的完整节点。备注换行时不得重复衔接节点：若上一行已写到 `M（空袭战）`，下一行应直接从 `→Y1` 继续，不能再写 `M→Y1`；路线码只记录实际经过的一个 `M`。

“目标本身是否削减海域量值”和“是否需要用海域量值限定当前阶段”是两个独立问题。生成每个活动阶段配置时必须先查 poi `maps`：只要当前阶段存在可识别的 HP/TP 条，配置就应启用 `MapHpInRangeFlag` 作为阶段门禁，即使目标只是开路、解谜、削甲、指定点胜利或到达而不会直接削减该条。只有当前阶段确实没有 HP/TP 条，或实时数据无法形成可靠阶段门禁时才关闭，并在备注说明原因。

启用前必须通过 poi `maps` 数据核对当前地图的 `api_gauge_type`：`2` 对应 KCPS `MapHpInRangeValueGauge=0`（HP），`3` 对应 `MapHpInRangeValueGauge=1`（TP）；不得从 `P1/P2` 名称、攻略俗称或模板值推测。类型不符时 KCPS 会在出击前直接禁止出击。若目的只是确认 HP 血条或 TP 条仍然存在，两种量值都统一使用 `最小值=1、最大值=99999`；不得沿用模板旧值 `9999`。只有确实要限定磨血、斩杀或运输阶段的更窄区间时，才可使用经过攻略与游戏状态验证的上下界。启用后，备注必须新增【海域量值】，写明类型、区间、阶段门禁用途、实时 `api_gauge_type`、生成时当前值/最大值和核对来源；若目标本身不消耗该量值，也要明确写出，避免把目标停止条件与阶段门禁混为一谈。

前一条 HP 击破后、下一条 TP/HP 尚未出现的短暂开路阶段，可以把上一阶段的 HP 量值门禁设为 `0～0`。它表示“上一条已经归零或显示完成”，而不是目标正在削减 HP；下一条不同类型量值出现后，KCPS 会因类型不符拒绝旧配置。路线规格必须同步写明 `GaugeRangeMin=0`、`GaugeRangeMax=0` 与门禁用途，备注也必须说明该窗口的前后边界，禁止简单关闭量值检查。

不能仅凭攻略把某一步称为“下一Boss点开放”或“开路”，就推断下一条量值尚未出现。部分活动会先在 `mapinfo` 暴露下一条 HP/TP 量值，再要求到达指定点开放Boss路线。生成当前可执行阶段时必须以实时 poi `maps` 的 `api_gauge_type`、`api_gauge_num` 和当前量值为准，并用日文 Wiki 的阶段顺序交叉核对；此时应使用已经出现的下一条量值作为门禁，目标本身是否消耗量值另行说明。只有实时数据明确仍是上一条 HP 且值为0，才能采用上一段的 `HP 0～0` 过渡门禁。

允许在前一阶段尚未完成时预先生成后续阶段配置，但不能用当前阶段的实时量值和开放陆航数量覆盖后续阶段资料。此时路线规格必须同时声明 `FutureStagePrerequisite`、`ExpectedMapGaugeType` 和 `ExpectedOpenedLandBasedAirCorps`；校验器只把当前状态差异降为“前置尚未完成”的警告，仍须严格检查配置本身是否采用目标阶段的量值类型、舰队、路线和陆航数量。出击门禁必须保持目标阶段的正确 HP/TP 类型，使误启配置时由 KCPS 拒绝出击。

校验历史阶段或未来阶段配置时，必须比较 poi 的 `api_gauge_num` 与路线规格 `StageDesign.GaugeNumber`。只有编号确实不一致时，当前账号的量值类型、数值和开放陆航数量才可作为阶段差异警告；若实时编号与目标编号相同而 HP/TP 类型冲突，必须硬错误，不能用 `FutureStagePrerequisite` 降级。配置自身仍按路线规格中的目标量值类型、门禁区间和 `ExpectedOpenedLandBasedAirCorps` 严格校验，不能拿当前阶段状态误判旧配置，也不能因此放宽目标阶段的结构检查。

## 活动血条与磨血停止

- 通常海域的击破次数血条与活动 HP 血条不是同一种进度。活动战力条按每次战斗中 Boss 旗舰实际损失的 HP 减少；进入最后阶段后，即使只剩 1 HP，也必须击沉 Boss 才能完成。
- 活动磨血不得用“Boss旗舰击沉 N 次”代替 HP 进度。途中未击沉但造成的伤害同样削减血条，固定击沉计数会晚停；不同战斗造成的伤害也不固定。
- 活动 HP 条的斩杀/击破配置必须启用 `StopIfEnemyFlagShipSunkFlag`，条件类型设为地图点，条件值使用本路线进入 Boss 点的准确边编号，阈值固定为 1。这样在斩杀战击沉 Boss 旗舰后立即结束循环；下一轮量值门禁和 `OnAutoStop()` 只作后备，不能替代直接击沉判定。
- 斩杀与磨血必须使用两个独立路线规格。斩杀规格的 Boss 节点声明 `BossKillCount=1`，磨血规格不得声明固定击沉次数。TP 条不适用此规则；运输完成按 TP 归零、量值消失、变为非 TP 或后续 TP 反向变大等证据判断。
- 每条 HP Boss 在定稿前都要分别读取磨血与斩杀敌编成，确认 Boss 舰种、随伴、制空和反潜需求是否变化。只要任一项变化，即使路线相同，也必须分别重算主舰队、改装、阵型、夜战、陆航、支援和制空；禁止从磨血配置只改量值区间便复制出斩杀配置，也禁止把斩杀的对水面方案反向套给磨血期的潜水 Boss。
- 必须把“磨血 Boss 单舰耐久”“最终 Boss 单舰耐久”“最终编成切换时的血条剩余上界”作为三个独立数据核对，不能用一个含义模糊的 `BossHp` 代替。活动可能在磨血与最终阶段更换 Boss；例如磨血 Boss 耐久很低，但最终编成会在远高于该耐久的剩余 HP 处切换。门禁使用最终编成切换上界，不能直接套用磨血 Boss 单舰耐久。
- 路线规格应在 `StageDesign.GaugePhaseBoundary` 中分别记录 `GaugeTotal`、`GrindingBoss.Name/Hp`、`FinalBoss.Name/Hp`、`FinalPhaseGaugeMax`、`Source` 和 `LastVerifiedJst`。备注【海域量值】必须逐项写清这些数值，并明确门禁按切换上界设置；校验器要同时核对规格、备注、出击门禁和 `OnAutoStop()`，避免出现“门禁数值碰巧正确，但解释错误”的配置。
- 先从当前证据和实时 `mapinfo` 确认最后阶段上界。磨血出击的 `MapHpInRangeValueMin` 设为“最后阶段上界+1”，最大值设为 `99999`；击破配置使用 `1～最后阶段上界`。
- 使用 HP 阶段门禁的路线规格必须显式记录 `GaugeRangeMin`、`GaugeRangeMax`。生成后校验器必须逐配置比对实际门禁与路线规格，禁止生成器计算了阶段范围却在写入 JSON 时退回硬编码的 `1～99999`。
- 若本轮出击后的关联流程必然重新打开当前活动海域并刷新 `mapinfo`，优先在总控 `OnAutoStop()` 中读取当前 HP：HP 已进入最后阶段、量值类型已改变或量值消失时正常自动停止。当前配置若使用陆航，战后“陆航休息N”会重新进入对应海域页面，可作为已验证的刷新步骤。
- `OnAutoStop()` 的阈值必须与出击门禁相邻且无空隙：例如磨血允许 `119～99999`，则停止条件必须是 `HP不高于118`。通知消息也必须写实际条件，不能写推测的击沉次数。
- 即时 HP 停止必须同时具备“可靠刷新步骤”和“HP门禁后备保护”。不能证明 `mapinfo` 已刷新时，不得读取旧缓存并宣称即时完成；改用 HP 门禁配合有限次出击失败停止，并在备注中明确它是保守降级，不发送虚假的完成通知。
- 不得从内嵌 Python 直接操纵界面以刷新数据。刷新只能来自配置中已有、职责明确且经过验证的关联执行单元。

## 活动 TP 条停止

- TP 阶段不能只用“当前量值仍然是 TP”判断是否继续。活动海域可能连续出现两条 TP 条；上一条完成后，下一条仍是 TP，单看 `MapGauge.Tp` 会误入下一阶段。
- 生成配置时从实时 `maps` 同时记录 `api_gauge_num`、当前 TP 和最大 TP，但这些数值只用于生成时核对，不能作为运行时上一轮基线。
- 每轮真正出击前，在额外出击检查函数中主动调用 `MiscApi.Maps()` 刷新 `mapinfo`；舰队与陆航身份检查通过后，核对量值仍是预期 TP 阶段，再用 `Utility.RaiseEvent(UserEvent(...))` 发送包含配置内唯一前缀、`api_gauge_num` 和当前 TP 的内部基线消息。`OnEnabled` 可能发生在重新进入活动海域和刷新 `mapinfo` 之前，只能初始化变量，禁止用它读取 TP 基线。
- 每轮出击后必须先由已验证的关联执行单元再次刷新 `mapinfo`，再在 `OnAutoStop()` 按以下顺序判断阶段结束：地图量值消失；量值变为非 TP；`api_gauge_num` 离开生成时阶段编号；当前 TP 大于本轮出击前基线；当前 TP 归零。任一条件成立即停止。
- `api_gauge_num` 是连续同类型量值之间最直接的阶段标识；“TP 反向增大”是阶段编号缺失、未及时更新或连续 TP 条编号无法依赖时的后备证据。同一条 TP 条只会保持或下降，不应自行增加。
- 出击前检查函数与总控脚本各有独立 Python 作用域，不能依靠普通全局变量共享。总控必须在 `OnFilterEvent(e)` 中识别该专用 `UserEvent`，把阶段号和 TP 保存到自己的脚本变量，并对这条内部消息返回 `False`，防止它继续进入关联出击状态机；不要用 `OnEvent(e)` 返回 `True`，否则会把“记录快照”误成“触发总控”。事件分发器按入队顺序逐条完成广播，出击前基线消息先于之后产生的出击完成事件，因此总控会在进入战后 `OnAutoStop()` 前得到本轮基线。
- 每个内嵌 Python 执行单元都必须自给自足：凡在该脚本中使用 `UserEvent`、`Utility`、`GameState`、`Logger` 等 KCPS 运行时类型，都要在该脚本自己的作用域显式写入 `from KancollePlayerSimulatorKaiCore import *`。不得依赖同一配置内另一个执行单元已经导入；校验器必须分别检查探针、总控及其他托管脚本的运行时导入。
- 消息前缀应按出击执行单元 GUID 等稳定且配置内唯一的值生成，且不得与 `Clear`、`已停止` 等跨配置通知格式混用。每次实际出击都覆盖总控内的基线，`OnAutoStop()` 只读取、不把战后 TP 写回；自动停止后清理变量。若战后找不到本轮基线或无法读取量值，应记录错误并安全停止，不能继续盲跑。
- 出击前仍要保留 `MapHpInRangeFlag` 的 TP `1～99999` 门禁；它负责阻止已经归零或变成 HP 的阶段出击，`OnAutoStop()` 负责在战后立即识别阶段切换。两者职责不同，不能互相替代。
- 以削减或清空 TP 条为目标、使用上述战前基线与战后 `OnAutoStop()` 且允许自然循环的运输配置，`StopIfLoopCountLargerOrEqualThanValue` 默认不得低于 `20`。`10` 次容易在低 TP、A/B 胜、撤退或失败重试较多时提前停止。只有用户明确要求更低上限，或高士气、满熟练度等条件决定配置只能单轮执行时，才可使用更小值，并在备注说明原因。仅以 TP 条作为阶段门禁的开路、到达、守家空优等配置不适用这条默认值。

## 战斗条件计数的能力边界

- KCPS 原生已经支持的条件优先使用原生计数，例如指定点胜利等级、Boss胜利等级、旗舰击沉、到达终点和基地空袭无损。
- 基地防空“航空优势/制空权确保”和“基地空袭无损”是不同结果。`StopIfAirBaseAttackNoDamage` 只能统计损害为零，既不能证明取得空优，也可能在取得空优时因为仍有损害而不计数，禁止拿它代替守家空优计数。
- 削甲需要回打旧阶段 Boss 时，必须重新核对该条件指定的舰队形式、出发点、路线和贴条，并优先复用该旧阶段已经验证过的舰队骨架。例如条件明确要求水上打击部队时，不得直接沿用当前阶段的空母机动部队，也不得无理由引入新的锁船。
### 目标变化重设计门禁

“复用旧阶段舰队骨架”只允许复用重新核验过的舰船实例、舰队形式、贴条和路线骨架。不得以旧阶段 JSON 的配装为新方案起点。目标从运输改为指定点 A/S 胜、从磨血改为斩杀、从到达改为战斗胜利，或目标敌舰编成发生变化时，必须重新联合推演舰船顺序、每个装备槽、补强增设、陆航、支援、阵型、烟幕、退避、入渠阈值、士气、停止条件和通知。

指定点要求 A/S 胜时，目标点默认不得使用烟幕。烟幕会同时压低己方命中与伤害，适合以通过为目的的危险道中点，不应机械继承到要求清场的目标点。只有经过敌编成、雷达舰、己方命中与夜战收尾概率计算后仍能证明收益更高，才可显式设置 `AllowSmokeAtVictoryObjective=true`，并在 `【目标变化审计】` 写明依据。

复用旧阶段舰队时，备注必须新增 `【目标变化审计】`，依次写明：

- `旧目标`：旧方案实际优化的目标。
- `新目标`：本配置要稳定达成的条件。
- `仅复用`：经过重新核验后仍可沿用的舰船实例、舰队形式、贴条或路线。
- `已重算`：配装、陆航、支援、战斗策略和停止条件等重新推演结果。
- `已删除`：不再服务新目标的旧阶段装备、说明和自动化设置。

非 TP 的指定点胜利目标不得保留普通大发、纯特大发或运输桶。若目标敌人是陆上型，确实需要其中某件装备参与战斗，必须新增 `【非运输舟艇理由】`，逐船逐槽说明不可替代的对地用途。`武装大発`、`装甲艇(AB艇)`等因 PT 或陆上型战斗收益而保留时，必须明确写为战斗装备。备注和出击执行单元不得继续引用 S/A 胜 TP、单轮运输量、运输核心或上一阶段目标。校验必须依据配置名和 `【目标】`首行识别当前目标，不能因为正文出现“本阶段不需要运输”等否定句而误判成运输目标。
- 多个削甲配置都能稳定保留一队陆航防空，且该队足以取得基地空袭航空优势时，守家空优应优先并入这些配置顺带完成，默认不再单独生成配置。每个总控仍只统计自身目标，备注必须说明 KCPS 不能独立统计守家空优次数；完成其他条件后以游戏的敌方削弱提示确认，若空袭次数不足，则重复运行路线最短、消耗最低且保留防空的配置。
- 总控 `OnAutoStop()` 不能直接读取关联出击内部保存的本次基地空袭制空状态；`mapinfo` 也不提供各解谜条件的独立完成次数。不要为了表面自动化编写只读最近一次响应或旧缓存的伪计数脚本。
- 游戏在某项解谜条件整体完成后返港时会给出敌方削弱提示。只有已经核实其他可能触发提示的条件全部完成、当前路线只剩一个待完成条件时，才可用 `StopIfEnemyDebufAtHome` 阈值 `1` 把这一次提示作为停止信号；备注必须写清隔离条件和适用边界。该阈值统计的是“条件完成提示”，不是每次空优，因此不得把阈值写成所需空优次数。
- 同一路线仍可能完成多个条件时，返港削弱提示无法识别具体是哪一项。此时应拆分路线、有限次手动确认，或等待有带游标且可去重的事件历史能力；不得宣称 `OnAutoStop()` 已实现通用精确计数。
- 活动港口点若到达后直接显示标准“帰”按钮并母港归投，可使用 `StopIfArrivedEndPoint` 计数；KCPS 界面中的“给资源的终点”只是历史文案，并不把判断限定为资源点。生成前按通用出击规则核对终点页面，首次运行再以“到达了出击终点”日志和计数递增复核。
- `mapinfo` 适合读取当前 HP/TP 等状态，不是战斗历史。poi 通信接口的“最近一次响应”和内建 `battle` 状态也不是事件日志；目标点之后若还有同类战斗，所需响应可能被覆盖。
- 禁止把“最后一次战斗响应”当作通用的空优、空确、削甲或复合条件计数依据。只有目标点被路线设计为本次出击最后一场战斗、随后立即返航，并且同时核对海域、地图点、战斗唯一标识和结果时，才可作为该单一目标的特例。
- “指定战斗点取得航空优势或制空权确保 N 次”若满足上述特例，应使用目标点条件策略的进入昼战回调精确计数，不得把固定循环 N 次当作完成证据。回调必须核对活动地图 ID 和目标点所有可能的进入边编号，读取当前战斗包 `api_kouku.api_stage1.api_disp_seiku`；仅值 `1`（制空权确保）或 `2`（航空优势）计数，均衡、丧失、偏航、撤退和未发生航空战均不得计数。需要兼容存在第二航空战阶段的战斗包时，可在第一阶段缺失后检查 `api_kouku2`，但同一场战斗只计一次。
- 单次出击与总控脚本作用域相互独立。目标点回调应发送包含配置内唯一前缀、地图 ID、进入边编号、战斗时间和制空结果的内部 `UserEvent`；总控用 `OnFilterEvent(e)` 识别前缀，以“地图 ID+进入边编号+战斗时间”为唯一标识去重并累计，对该内部消息返回 `False`。`OnAutoStop()` 只在累计达到所需次数时返回 `True`，自动停止后清空计数与去重集合。
- 精确计数仍须保留大于目标次数的有限循环上限，默认 `10` 次，仅用于偏航、未取得空优或接口异常时的安全停止。由于达到安全上限不等于完成，自动停止通知必须命名为“通知停止”并发送“已停止”，不得发送 `Clear`。备注必须明确“精确计数条件”和“安全上限”两条独立停止路径。
- 生成或修改此类配置后，使用 `<SKILL_ROOT>/scripts/poi-kcps-api/enable/KCPS-EnablePointAirStateCounter.ps1` 写入回调和计数器。`MapId` 使用 poi `battle._status.map` 的组合地图编号；`ConditionValue` 使用该目标点在当前路线中的所有实际进入边编号，不能只写字母，也不能假定同一点从不同前置点进入时编号相同。校验器必须验证受管声明、目标策略回调、总控监听、去重字段、目标次数和安全上限彼此一致。
- 上述精确计数只适用于本队在战斗点取得的制空状态，不适用于基地防空航空优势。基地空袭发生在路线过程中且其响应可能被后续战斗覆盖，仍按守家空优的能力边界处理。
- 返港时出现的敌方削弱提示只能证明“本次至少触发了某项削弱”。同一路线可能同时或先后满足多个条件时，不能据此分别增加各条件计数。
- 若当前可用接口没有带游标、可去重的战斗事件历史，就无法通用地精确恢复一趟出击中每个点的制空结果。此时应把目标拆为在目标点后立即返航的独立配置，或明确要求人工确认；不得伪造自动停止。
- 其他 poi 插件的数据不是通用接口。只有在运行时探测到其公开、版本化接口，并能在缺失时安全降级，才可作为可选增强；不能在未检测能力时假定其存在。

## 活动出击前身份检查

活动配置必须启用 `SimpleSortieWorkflow` 的额外出击前检查函数，只补足 KCPS 内建检查没有覆盖的两项：实际出击舰队中的舰船实例及顺序是否正确；所有设为出击或防空的基地航空队中，四个槽位的飞机种类及顺序是否正确。不得在此函数中重复检查血量、大破、士气、补给、舰载机数量、装备改修、熟练度、陆航疲劳、陆航牌子或海域量值，这些继续交给 KCPS 既有检查。

- 单舰队模式检查 `出击.Fleet` 指向的实际出击舰队，不得写死第一舰队。
- 联合舰队模式固定同时检查第一、第二舰队；第三、第四支援舰队不属于该检查范围。
- 舰船按实例 ID 和位置顺序比较。活动锁船与多号机依赖具体实例，不能只比较舰船种类或改造形态。
- 陆航检查范围由出击执行单元中三队的动作推导：动作是出击或防空的队都必须检查，未使用队不检查。不得写死第一基地航空队。
- 陆航各槽比较装备主数据 ID 和槽位顺序，不比较装备实例 ID。同种飞机的不同实例可互换；熟练度、改修和数量由 KCPS 既有陆航检查负责。
- 陆航中队的飞机实例 ID 是可空值：空槽、飞机配置转换中或接口暂未给出 `api_slotid` 时都可能为 `None`。内嵌 Python 必须先判断 `instance_id is not None`，再与整数比较；空值应作为该槽不匹配并清楚报告，禁止让类型异常中断总控。
- 陆航声明中的装备主数据 ID 必须由生成时最新的 `const` 数据按装备名解析，禁止凭记忆手填。写入和交付校验都必须反查“ID 对应名称”；比较名称时只移除实例显示附带的改修和熟练度后缀，不能把名称相同、ID 错误的声明当作有效配置。
- 每支设为出击的基地航空队必须在路线规格 `RequiredLandBasedAirCorpsRadius` 中按队号登记目标点所需航程，并在 `ExpectedLandBasedAirCorps` 固定最终四格。备注同队动作行必须写 `航程要求N`，其数值与路线规格一致。
- 活动校验器必须用生成时最新装备主数据计算身份检查声明中四格飞机的整队有效航程；低于路线规格或备注要求时属于不可交付错误。无陆侦时取四格最短航程，有侦察机时使用通常延长公式且延长量最多为3。修改任一陆航槽后必须重新校验，不能沿用修改前的航程结论。
- 内嵌 Python 使用受管标记和声明数据，主体遍历 `EXPECTED_FLEETS` 与 `EXPECTED_LAND_BASES`。代码注释保持简短中文，不写私有路径。
- 检查失败时按舰队位置或陆航槽位逐条报告，只写错误位置的预期值与实际值；正确位置不得重复列出。

生成或修改活动配置后，使用 `<SKILL_ROOT>/scripts/poi-kcps-api/enable/KCPS-SetSortieFleetLandBaseChecker.ps1` 写入检查器。`FleetMode` 只能为 `Single` 或 `Combined`；陆航 JSON 必须只声明本配置实际设为出击或防空的队，每队严格四槽。工具从对应编成执行单元读取舰船实例和顺序，因此联合舰队必须同时存在第一、第二舰队的固定编成执行单元。若活动阶段不使用陆航，传入空对象 `{}`，仍保留舰队身份检查。

活动专用校验器必须强制核对：检查器已启用；单舰队或联合舰队范围与配置一致；联合舰队的 `组成联合舰队` 已由总控正确关联且不计入入渠完成阈值；声明舰船与编成逐位置一致；声明陆航队号与出击/防空动作一致；每队有四个飞机种类；Python 使用按声明遍历的通用实现而没有写死舰队编号。此要求只适用于活动出击配置，通常海域配置不强制启用。

单舰队模板中的支援结构按实际方案条件保留：

- 使用支援时先按主舰队形态选择空闲舰队，不能把“道中第三、决战第四”写死。通常舰队或联合舰队可按模板使用第三舰队道中、第四舰队决战；游击部队本身占第三舰队时，道中支援必须改用第二或第四舰队。若同时使用两种支援，应分别占用两个空闲舰队。
- `NormalSupportExpeditionFleet` 与 `BossSupportExpeditionFleet` 是支援舰队编号的唯一事实来源。对应编号的编成、改装覆盖、出击前入渠、补给和总控关联必须成套跟随；主舰队与支援舰队不得重号。
- 前卫支援与决战支援的士气策略分别声明，不互相复制。开启 `NormalSupportExpeditionCheckMorale` 时，候选与换船门槛须满足该检查需要的六舰闪状态；关闭时说明发生率与连续执行的取舍，不能保留与候选策略相矛盾的检查。
- 开启 `BossSupportExpeditionCheckMorale` 时，旗舰候选与换船门槛须满足闪状态；随伴是否要求闪由本次命中与周转策略决定。`StageDesign.SupportMoraleChecks` 与出击检查字段、六个位置的实际门槛一起核对。
- 支援可以按本次计划固定实例或使用通用候选轮换；动态方案不继承主出击舰队的固定实例规则。半自动主队也不意味着支援必须固定；旗舰无闪、随伴疲劳后应可从可用池补位。优化炮击或反潜支援时限定舰种、练度、逐槽兼容性、搭载数和必要制空下限，不锁死当前算出的六艘船。改装必须按支援舰队编号和位置绑定，四格驱逐、五格正航母的额外主槽用“槽不存在则跳过”覆盖。候选不足应明确停止，不放松机制条件或挪用主队。
- 反潜支援可用 `enable/KCPS-EnableDynamicAswSupport.ps1` 按路线规格的 `BossSupportPlan.SelectionMode=DynamicRoles` 生成内嵌通用候选脚本。`PositionRoles` 与 `Roles` 声明舰种和能力门槛；脚本逐槽调用公开装备兼容性接口，KCPS编成设置再过滤士气、修理、远征和其他舰队占用。校验器同时比对角色参数、最终改装、脚本版本和保证制空，不能仅验证某一组示例舰船。
- 同时使用两种支援时，按出击字段实际指定的两个舰队编号建立完整结构，避免与主队重号，并联合分配装备。
- 明确不使用某种支援时，删除该支援相关的编成、补给和仅为它服务的执行单元及关联项，不保留空壳。`【支援】` 必须与最终执行单元结构一致。
- 支援舰队若使用脚本动态选船，支援改装可按候选舰种保留兼容装备备选；主出击舰队固定实例的每槽单候选规则仍然不变。校验器应根据出击执行单元声明的支援舰队编号和改装条目的 `Fleet` 识别支援覆盖，不能依赖固定的第三/第四舰队编号，也不能只依赖执行单元名称中是否含“支援”。
- KCPS 按 `改装.Ships` 与各槽 `Equipments` 的顺序贪心选取装备，不会为后续条目回溯。容量审计必须覆盖同一改装执行单元中的所有主出击舰队、联合第二舰队和动态选船的两支支援舰队，并逐个模拟普通槽、受限主槽与补强增设的候选消耗；不能因为支援编成使用脚本候选就跳过支援改装的装备数量。先满足候选最少的受限条目，再让候选较多的条目使用后备装备。生成器必须固定这套跨舰队分配顺序，重生配置时不得因哈希表枚举顺序改变装备归属。空字符串不是“允许空槽”的有效候选；`IgnoreNoEquipmentMatched=false` 时，任意槽的候选耗尽都会令改装报错。交付前运行 `validate/KCPS-AuditRefitEquipmentCapacity.ps1` 扫描目标文件；批量维护时只扫描用户授权的范围。
- 装备容量要按“同一改装流程最终同时占用多少实例”计算，而不是按仓库空闲数计算：非远征舰船上的装备可由 `Deprive` 拆取，但已经分给本流程前面槽位的实例不能再给后面槽位。结构性总数不足必须改配装；账号总数足够但运行时仍无候选时，再检查所需实例是否随远征舰队出发，远征占用属于瞬时阻塞，不应把当前持有位置写进长期备注。
- 砲击支援的轻空母补强增设应优先比较 `熟練甲板要員+航空整備員`，其装备火力会进入支援攻击力；账号数量不足或暂不可用时，再按舰船兼容性使用 `12cm30連装噴進砲改二`、高性能机枪等后备。动态候选必须覆盖可能选中的轻空母，且两支支援舰队要联合分配，不能各自假定独占同一件装备。
- 动态候选可能具有不同槽数，当前角色计划须覆盖所有可能存在的主槽。额外槽的装备由 `EquipmentNames` 明示，需要兼容较少槽数的船时用 `OptionalSlots` 声明可跳过位置；不能按旧角色名或固定位置自动补电探。
- 第4主槽与补强增设是两套独立兼容规则。部分四主槽舰船的第4主槽可装备范围比第1至3槽更窄，不能因为某装备能进前三槽、能进补强增设，或同舰种其他船能装备，就推断它能进该船第4主槽。生成器和校验器必须按“具体船型、具体槽位、装备改修等级”逐槽验证主槽与补强增设；受限主槽应改用可装备且满足本次目标和资源预算的装备，而不是留空或把补强增设规则套到主槽。

动态反潜支援的当前方案写入 `BossSupportPlan`，使用 `SelectionMode=DynamicRoles`，显式指定 `Fleet`、角色 `Roles` 与六位置 `PositionRoles`。角色名不绑定某个旧方案；每个角色提供 `ShipTypes`、`MinimumLevel`、`MinimumSlots`、`MinimumTotalCapacity`、`MinimumAircraftPerSlot`、`MinimumAirPower` 和按槽排列的 `EquipmentNames`，需要时声明 `OptionalSlots`、`ExpansionEquipmentName` 和 `RequireRemodeled`；未声明改造要求时不默认排除未改造舰。`MoraleExclusionMax` 必须按六个位置提供阈值数组，所需反潜攻击槽数和支援制空下限由本次目标决定；只有显式 `RequireAirSuperiority=true` 才附加空优目标。实际舰种仍须满足反潜支援机制，候选逐槽兼容性和装备总库存仍须核对。

支援收尾只检查缺少的槽位与声明冲突，不自动补入固定电探或其他旧装备。无当前配装方案时报告缺项，由本次规划补齐。

## 活动专用配船流程

1. 根据当前标签与本次保留计划列出可用池；引用锁船表时标注其副本要求与来源。
2. 从实时账号提取同改造链全部实例；已锁定实例按 ID 排号，未锁定实例单独列为未分类。
3. 先保留后续标签明确要求的高价值实例，再选本阶段所需舰船。
4. 对倍率船、导航船、运输船、对地船、夜战主力和特殊攻击核心做冲突表。
5. 按本次目标、资源预算与风险偏好选择方案。低成本方案可以成立，但仍须核对任务、路线与配装的必要条件，并说明相应取舍。
6. 如果低编号主力是锁船表明确分配给本标签，可以使用；如果分配表要求二号机，则必须使用实际解析出的二号机。
7. 写入配置前再次刷新账号状态，确认舰船尚未被其他出击贴上冲突标签。

## 编成与配装

目标点制空计数的去重不能依赖 `battle._status.time`，该字段在回调时可能为空、为零或不是整数。使用单次出击 `OnProcess` 创建本轮标识，结合 `Workflow.BattleCount`、海域及进入边去重；普通战果与计数回调必须测试缺失时间、重复回调和跨轮次累计。停止回调存在不代表停止链已验证，交付前运行 `validate/test_point_air_state_counter.py` 的探针到总控联合测试。

- 编成、顺序、装备、阵型、夜战、陆航、支援和终止条件一体推演，不能先锁死船再机械填装备。
- 联合舰队先逐队验证能否组成，再验证出发点和带路。水打/机动第二舰队必须恰好1轻巡（雷巡、练巡不计）、至少2驱逐，重巡级至多2；输送护卫另按其规则检查旗舰与舰种。全队合计满足带路不能替代逐队组成条件，不能把轻巡都放第一舰队。`KCPS-ValidateConfig.ps1` 已接入 `KCPS-CombinedFleet.ps1`，从最终编成实例和实时改造主数据检查全部候选；缺数据不放行。批量排查使用 `validate/KCPS-AuditCombinedFleet.ps1`。原生低速战舰放护卫队须另外证明组成联合时的提速状态；遇到新舰种时重新查证其护卫空母资格，不能按名称猜测。
- 为目标分歧更换慢速舰、增减舰种或调整两队归属后，要从出发点重新推演整条路线；低速在后段可固定目标，也可能在前段增加战斗。同步修改所有实际进入边编号、条件策略、名称、备注和身份检查，不只修改目标点之前的一个分歧。
- 每个战术开关都必须与最终改装形成“能力提供者闭环”，并在定稿后反向复核：烟幕开启必须有实际出击舰队携带 `発煙装置(煙幕)` 或 `発煙装置改(煙幕)`；联合舰队自动退避必须由第一舰队旗舰携带 `艦隊司令部施設`，并保留第二舰队可担任护卫的驱逐；特殊攻击必须满足舰船、顺序、装备和阵型条件。缺少提供者时，不得留下看似积极但实际无效的策略字段：烟幕关闭，联合退避保持手动选择，特殊攻击按普通阵型处理。
- 以上闭环必须以最终生成的改装执行单元为准，不能只看攻略意图或生成器中间变量。改动船或装备后必须重跑活动校验器；“战术开关有设置、能力提供者却不存在”属于阻断交付的问题。
- 主出击舰队每个位置只放一个候选。`Selections` 与 `SelectShipArgs` 都必须指向同一实例 ID。
- 编成候选的 `Memo` 使用“船名 + 几号机”的简洁格式：一号机只写船名，不写“一号机”；二号机及以后写作 `船名 二号机`、`船名 三号机`。实例 ID 已在 `Value` 中，不在备注里重复。若实际选择与锁船分配表不同，末尾追加简短原因，例如 `船名 二号机（分配表建议一号机；一号机预留后段）`；与分配表一致时不追加解释。
- 主出击舰队的固定实例必须用舰船 ID 作为改装对象，并与编成中的实例一一对应；不得按舰队位置绑定，也不得依赖同名船自动匹配。动态支援候选无法预先确定实例时，才保留按舰队位置改装。
- 所有可用主槽和已开补强槽装满。固定活动船的改装对象必须设置 `IgnoreNoShipMatched=false`；每个普通槽必须有且只有一条非空改装行，并设置 `IgnoreSlotNotAvailable=false`、`IgnoreNoEquipmentMatched=false`。已开放补强槽同样不得在找不到装备时静默跳过；补强装备必须同时满足该船、改造形态与改修等级的装备条件。
- 只有刷陆航熟练度等明确需要刻意空槽的专用工具配置可以例外。对应 `改装.Ships[].Memo` 必须写 `KCPS_ALLOW_EMPTY_SLOTS=2,6; REASON=中文理由`，逐项列出允许空置的槽号；普通战斗、开路、运输、削甲和 Boss 配置禁止使用该例外。
- 补强槽也必须按目标点、舰船补正、射程和全队协同逐船优化，不能把机枪当作通用占位。纯潜水路线若没有敌方航空兵力，机枪的核心对空收益通常无效；应核对该船可装的反潜装备、见张员及其他特殊装备。日本驱逐在普通 `熟練見張員` 上可获得额外对潜与回避补正时，应把它与机枪逐项比较；`水雷戦隊 熟練見張員` 会把射程改为中，只有在推演先制反潜攻击顺序后确认有利才可使用。若无航空战仍选择机枪，必须在备注新增 `【补强机枪理由】` 说明不可替代的收益。
- 补强槽可装范围不得只按装备大类推断。生成前同时核对实时 `api_mst_equip_exslot`、舰船专属补强规则、改造形态、装备改修等级和日文 Wiki 的最新说明；某类装备并非所有船都能放，能放也不等于当前海域最优。
- 稀有装备冲突时，按舰船角色和顺位分配；需要高改修阈值的装备先给真正依赖该阈值的船。
- 舰载机槽位按搭载数、制空、击坠风险、攻击能力和航程排列；不能只按装备名列表顺序填入。
- 三档制空必须用 `inspect/KCPS-AuditAirPower.ps1` 对最终改装方案复算。工具同时输出不计改修值和按账号库存改修下限/上限估算的结果；备注默认采用保守改修估算。攻略样例装备与账号同名装备改修不同导致跨不过目标线时，不得照抄，必须重新分配槽位或替换装备并写明差异。
- 消耗装备默认不用；只有通过率差异显著时先征得用户同意。
- 游击部队运输或长航路配置必须把“旗舰装备 `遊撃部隊 艦隊司令部` 并使用单舰退避”作为独立候选，与旗舰输出、单次 TP 和整队撤退方案比较。攻略明确采用司令部且账号有兼容旗舰与装备时，默认遵循；若偏离，必须在 `【攻略与分配】` 和 `【配装对照】` 量化少一格装备换来的收益及偏离理由。
- 使用游击司令部时，司令部必须装在七艘游击部队旗舰的主槽，但不得把自动退避机械复制到所有战斗点。对每个可能发生退避的战斗点，枚举可退避的船及退避后的剩余舰种、数量、速度和索敌，重新计算后续每个分歧。普通联合舰队还要计入两船退避与退避船疲劳；游击部队虽只退一船，也不能忽略偏航风险。
- 攻略把司令部或电探放在补强槽时，必须先核对账号中实际选定的舰船实例是否已开补强槽以及该装备是否可装。未开槽时不得假设 KCPS 会替用户开槽，也不得把原本用于保障索敌的洞电探直接删除；应在主槽重新分配司令部、电探和运输装，并量化损失。
- `遊撃部隊 艦隊司令部` 与 `精鋭水雷戦隊 司令部` 不可混为一谈。前者用于七艘游击部队退避并占旗舰主槽；后者在旗舰为驱逐/轻巡、全部伴随船为驱逐/雷巡的水雷战队通常舰队或游击舰队中，也能提供单舰退避，并可依舰船适装规则进入主槽或补强槽。生成前须分别核对游戏数据与日文 Wiki；活动校验器必须按最终编成逐位置校验精锐水雷司令部的舰种闭环，不能一律拒绝，也不能只凭装备名放行。
- 退避策略按战斗点分别决策。较早战斗点的投入成本低、退避后偏航概率高，或退避后可能进入无阵型选择页的错误路线时，优先把该点 `DefaultEscortRetreat` 设为不退避，由 `EscortShipsHeavilyDamagedStrategy=ForceRetreat` 让整队回港。较晚战斗点若保留退避收益更高，才允许开启自动退避，并继续保留“两艘以上大破拒绝退避”和伴随船大破强制撤退兜底。若多次退避会破坏后续带路，则只在一个经过推演的来源战斗点开启退避，其后所有战斗点关闭退避，从配置结构上限制为最多退避一次。
- 只能选择一个退避点时，不能机械选择第一个水面战。应比较各点实际造成大破回港的概率、到达该点前已经投入的时间与资源、退避后剩余战斗数、Boss目标是磨血还是击破，以及分歧判定发生在退避之前还是之后。优先选择“回港风险较高、已经投入较多、退避后仍有目标收益且不会破坏后续带路”的较晚节点；概率工具尚未模拟退避时，至少用逐节点到达数差额估计各点造成的回港比例。
- 退避是否实际触发具有随机性，只在最难、最晚的一个战斗点开启，可能让司令部在前方已经发生大破时完全失去作用。应在不显著增加偏航和额外战斗成本的前提下，考虑从该难点之前一个或数个战斗点开始形成“退避窗口”。逐个模拟零次、一次及连续退避后的舰种、舰数、速度和索敌；只有仍能走目标路线，或偏航可以在阵型选择页明确刷新止损、或立即进入无战斗终点自然结束时，才允许扩大窗口。不能因为某点最危险就机械地只在该点退避，也不能为了提高触发率把整条路线全部开启。
- 只要某点开启退避，就必须从最新日文 Wiki 与 KCNav/TsunKit 路线表列出退避后所有可达分歧。对会到达阵型选择页的偏航战斗点，逐条增加地图点条件策略并设置 `Formation=Refresh`，不得依赖默认战斗策略。对无阵型选择页的节点绝不能伪造刷新策略：若它是立即结束海域、不会再发生战斗或额外资源损失的无战斗终点，可在比较退避收益后允许自然结束，并在备注说明；其他情形必须在更早的来源战斗点关闭退避。
- 退避发生在索敌分歧之前时，必须用该分歧规定的公式和难度门槛计算满编值，并逐艘枚举“恰好退避该船”的结果。所有允许发生的一次退避都要高于门槛且保留明确余量；备注写出公式、系数、门槛、保守最低值和余量。若允许累计退避，还须枚举可达组合；无法保证时必须加入偏航点刷新止损，或从策略结构上限制退避次数。
- 33式索敌必须在生成配置前运行 `<SKILL_ROOT>/scripts/poi-kcps-api/analyze/KCPS-AnalyzeLos33.ps1`：直接传入拟定船 ID 与逐船 `Slots` 装备方案、分歧点系数和门槛。游击部队单舰退避使用 `-AuditSingleRetreat`；普通联合舰队司令部退避至少使用 `-AuditPairRetreat`，按任意两船组合给出保守下界，并把路线规格对应 `LosBranchRules.AuditEveryPairRetreat` 设为 `true`。该工具读取实时账号素索敌与装备库存，但不读取生成后的配置；生成脚本必须在 `Pass=false` 时拒绝输出。路线规格中的 `LosBranchRules` 和最终校验负责确认“该分歧需要计算”，分析工具负责确认拟定方案本身确实过线，两者不可互相替代。
- 当期地图级索敌分歧必须独立登记在私人 `route-overrides.json` 的 `RouteBranchRules`，不能只写进某个配置自己的 `LosBranchRules`。校验器应将配置的有序路线与地图级分歧逐边求交集：路线经过已知索敌边却未声明对应公式、系数、阈值时必须阻断交付。这样可防止生成器和路线规格同时漏掉同一分歧而产生假阴性。遇到“低于或等于阈值去歧路”的反向条件时，备注必须明确目标边要求严格高于阈值。
- 司令部装备、退避策略和偏航止损必须形成闭环。若所有地图点都拒绝退避，不得仍把司令部当作退避装备使用；只有逐项比较后确认其面板补正优于可用替代装备时才能保留，并在备注写明“仅使用面板补正”及比较结论。所有因退避才可能到达的偏航点必须随着退避关闭而删除；无退避时仍保留刷新策略，必须明确存在随机分歧、索敌不足或其他非退避原因。
- 每个 `Formation=Refresh` 的偏航策略都必须在 `【退避与偏航】` 中点名，并写清来源点、触发条件和为何会出现。不得为了“以防万一”加入当前编成、退避决策与索敌条件下不可达的战斗点。
- 备注必须单列 `【退避与偏航】`，写明每个来源战斗点是开启还是关闭退避、会破坏的带路或索敌条件、所有偏航进入边及止损方式。概率工具若未模拟已启用的单舰或联合退避，结果必须标为未计入退避收益的保守基线；若配置关闭退避，模型说明应与此一致。

## 磨血与斩杀的独立阶段设计

同一血条的磨血与斩杀不是只改停止条件的两个副本。生成前必须分别建立阶段设计，再联合迭代编成、顺序、配装、制空、陆航、支援、入渠阈值、士气、夜战、特殊攻击位置和自动化方式：

- 磨血以单位时间削减期望血量、道中通过率和连续周回稳定性为主；允许保留更多本队输出、较低入渠阈值和普通多循环，但不能因此把Boss输出能力让给道中。
- 斩杀以击沉Boss旗舰概率为主。应重新比较Boss触接/特殊攻击、T字不利规避、制空余量、本队输出槽、陆航与支援；不得从磨血机械复制，也不得把所有余量都堆给制空。
- 特殊攻击放在道中还是Boss必须按阶段分别计算。若斩杀必须击沉Boss，默认优先保留给Boss；只有道中回港率造成的总体击破率损失更大时才允许提前使用，并在 `【阶段设计】` 写明比较结论。
- 每个路线规格用 `StageDesign` 声明阶段与执行策略。`AutomationMode` 可为 `Configured`、`MultiLoop`、`SingleLoop` 或 `SemiAutomaticSingleLoop`，`LoopLimit` 明示；后两种模式只规定一轮，多轮模式要求大于一轮。`MoraleMinimum`、`DockingHpThreshold`、`BossFlagshipSinkStop`、`BossNightBattle` 等声明后逐项反查成品，不由模式名推断。实际使用陆航逐队声明 `LandBaseProficiencyChecks`；启用的支援在 `SupportMoraleChecks.Normal/Boss` 声明士气检查策略。
- `Grinding` 与 `Final` 可以都使用普通多循环，也可以只把真正困难的斩杀改为半自动单次；选择依据是攻略强度与账号实装能力，不是“斩杀”名称本身。
- 配置备注必须单列 `【阶段设计】`，说明本阶段的胜利目标、特殊攻击使用点、制空/输出取舍、入渠和士气阈值、循环方式，以及为何不采用另一自动化模式。

## 特殊攻击与阵型语义

特殊攻击规则会更新，生成时必须从当前日文 Wiki 查明具体攻击的舰船、改造形态、舰队位置、舰队形态、发动阵型、昼夜阶段、损伤限制和装备条件。不得把“大和型”“长门型”“Nelson”“金刚型”等特殊攻击当作同一种阵型规则。

- KCPS 的阵型数值必须结合舰队形态解释。单舰队/游击部队：`1=单纵阵`、`2=复纵阵`、`3=轮形阵`、`4=梯形阵`、`5=单横阵`、`6=警戒阵`；联合舰队：`5=第一警戒`、`2=第二警戒`、`3=第三警戒`、`1=第四警戒`。只看数值或只看中文阵型名都不足以证明正确。
- 当前已核实示例：大和改二与武藏改二组合在单舰队/游击部队使用梯形阵、联合舰队使用第四警戒；长门改二与陆奥改二组合在单舰队使用梯形阵、联合舰队使用第二警戒；Nelson Touch 在单舰队使用复纵阵、联合舰队使用第二警戒；金刚型夜战突击可用阵型范围另行按昼夜与舰队形态核对。未知或过期的机制条目必须重新查证后才能生成。
- 每个采用特殊攻击的路线规格必须保存 `FleetFormationMode` 和结构化 `SpecialAttackPlan`：规则 ID、发动舰队、发动节点及进入边值、明确抑制发动的节点、同阵型但规则上不会发动的例外、所需舰船位置。
- 目标点必须使用该舰队形态下的合法发动阵型；所有更早或目标外节点若使用同一发动阵型，必须证明不会发动并登记例外。例如敌方全为小艇群时，只有当前规则明确记载不会发动且路线节点也被核实为纯小艇群，才可作为例外。
- 为保留Boss特殊攻击而使用的抑制阵型必须逐点登记。校验器应拒绝未登记的提前发动阵型、发动点阵型错误、单/联合阵型语义混用、所需舰船位置不符，以及备注和实际策略不一致。
- 特殊攻击不仅影响阵型，还会反向影响编成顺序、装备倍率、昼夜输出分工和Boss入夜策略。修改任一舰船、位置、装备或阵型后，必须重新推演并重跑校验，不能只修一处字段。

## 路线与进入边校验

- KCPS 地图点条件值是“从上一点进入当前点的边编号”，不是当前点的固定编号。同一个 B2、F 或 Boss 点从不同前置点进入时可能使用不同数值，禁止只按点字母复用条件值。
- 每个活动路线规格必须同时保存 `KcNavMap` 与完整有序 `Route`。`KcNavMap` 使用本次查询到的 KCNav/TsunKit 地图号，不预置期号；`Route` 从实际出发点开始逐点记录，不得省略不发生战斗的中间点。
- 交付校验必须联网读取 `https://tsunkit.net/api/routing/maps/<KcNavMap>`，按 `前一点→当前点` 逐边核对 `Route` 与路线规格中该点的 `Value`。只比较配置与本地运行时路线方案不足以证明正确，因为配置和本地规格可能一起抄错。
- 配置中的条件策略顺序必须与有序 `Route` 一致。能动分歧、战斗点、可刷新止损的偏航点分别按其实际进入边设置；同一点存在多个可达前置点时，每一种会实际到达阵型选择页的进入边都要单独列出条件策略。
- 只有游戏实际弹出路线选择界面的能动分歧点才设置 `DefaultWayPoint`，并在路线规格写 `Kind=waypoint-select`、`RequiresWayPoint=true`。普通战斗点、空袭点、潜水点、Boss 点以及自动路线分歧必须保持 `DefaultWayPoint=null`；禁止使用空名称和全零坐标对象占位。活动终检必须同时拒绝非能动节点的非空路线对象，以及能动节点缺少目标名称、点击框尺寸为零或点击框越界。
- KCNav 当前数据中不存在某条相邻边、进入边编号不一致、路线规格缺少 `KcNavMap/Route`，或联网核验失败时，活动配置均不得交付。

## 陆航与支援

- 说明写出每队陆航的牌子、四个槽、航程、目标点和集中/分散方式。
- “舰队路线没有航空战”与“基地不会遭空袭”是两个独立判断，禁止互相代替。每个活动海域都必须从最新日文 Wiki 或攻略核对 `基地への空襲`，并在 `【陆航】` 第一行明确写 `基地空袭：有` 或 `基地空袭：无`。
- “已经开放/可以配置的基地航空队数量”“当前阶段允许设为出击的队数”“当前阶段是否发生基地空袭”是三个独立状态。必须分别从实时数据、最新日文 Wiki 和攻略核对，不能看到已开放两队就假定两队都能出击，也不能看到第二队不能出击就自动改成防空。若某队已开放但本阶段不能出击、且当前阶段没有基地空袭，该队应保持待机；身份检查、疲劳检查和战后 `陆航休息N` 都不得把它当作正在使用的航空队。
- 预先生成尚未开放阶段时，备注写目标阶段将开放的队数，路线规格用 `ExpectedOpenedLandBasedAirCorps` 固定该结论，并用 `FutureStagePrerequisite` 记录开放前置。不得为了迎合当前实时数据而删除后续阶段应有的出击队、防空队或陆航休息执行单元。
- 从实时 `landBasedAirCorps` 数据确认当前阶段实际开放的基地航空队数量，不得按模板假定一队或三队。基地会遭空袭不等于应先把最后一队锁定为防空：必须同时枚举纯防空、集中出击、分散出击及本队独立承担等候选，比较目标达成率、道中生存、制空状态、基地损失和后续连续出击成本。只有某队不用于出击的边际收益更高时，才默认把最后一支开放队设为防空；例如开放三队且一队防空时使用第三队，开放一队时第一队就是最后一队。若所有开放队都用于出击而不设防空，备注必须单列 `【不设防空理由】` 说明收益权衡。
- 上述比较必须使用目标点最新敌制空、账号本队实际配装制空及每波陆航出击制空，不能只凭“有基地空袭”或“本队看起来够强”决定。把候选结论写入独立的 `【陆航方案比较】`，至少说明纯防空、集中出击、分投和本队独立承担为何取舍；`【不设防空理由】` 是另一独立小节，校验器必须分别读取，不能限定它出现在 `【陆航】` 小节内部。
- 同一队的两波可以集中同一点，也可以分别投向两个点。分投时逐波核对航程与制空状态，并区分主目标和顺带推进的其他条件：总控停止条件、通知消息和事件计数只统计本配置主目标，不得把顺带取得的空优、到达或胜利混入停止次数。
- 已有实战记录或用户报告时，先按节点统计到达次数、战果、撤退与大破来源，再重新分配陆航、烟幕和退避。不得继续向已经稳定的节点投入稀缺陆航，却把反复造成劝退的水面节点只交给阵型或烟幕；若把陆航从目标点或其他节点移走，必须确认剩余本队手数仍能满足目标胜利等级。
- KCPS 只能切换陆航牌子、补给和检查疲劳，不能替用户更换基地飞机。`【陆航】` 必须逐槽写出用户需要手工配置的飞机、改修与熟练度。
- 只有专门给“当前已装飞机”刷熟练度、且本来就不固定四槽种类的辅助配置可以使用动态陆航方案。此类出击脚本必须显式写入 `# KCPS_DYNAMIC_LAND_BASE_PLAN <reason>`；普通攻略、开路、运输、削甲和防空配置禁止使用该豁免。没有固定身份检查或路线定稿、也没有该标记的活动陆航配置按遗漏处理。
- 陆航熟练度会在连续出击中下降，当前工具不会自动补回。开启 `LandBasedAirCorpsNCheckAnyProficiencyNotFull` 会在熟练度不足时阻止后续出击；是否需要该门禁及届时如何整备，应由本次计划明确，而不是从旧模板继承。
- 陆航满熟练度检查由当前计划逐队决定，在 `StageDesign.LandBaseProficiencyChecks` 中按基地编号显式声明布尔值，并与实际使用队一致。开启时写明依据、准备方法及熟练度下降后的处理；循环数另由 `StageDesign.LoopLimit` 决定，不因阶段名称或自动/半自动标签捆绑固定值。
- 选陆航飞机时枚举账号全部装备实例；装备当前装在舰船、其他基地或仓库都不得成为淘汰候选的理由。配置会重复使用，当前占用位置属于瞬时信息，禁止把“从哪里拆、挪到哪里、当前由谁占用”写入备注。
- 陆航逐槽方案还必须做账号总库存容量审计：同一配置中所有设为出击或防空的航空队会同时占用飞机，同一装备主数据 ID 的需求总数不得超过账号持有实例总数。备注、身份检查和路线规格四方一致只能证明“写的是同一方案”，不能证明方案可实现。交付前运行 `validate/KCPS-AuditLandBaseEquipmentCapacity.ps1`；修改后检查本次授权范围内的配置；只有用户要求全面审计时才扫描整个私人配置目录。
- 防空配装不能只比较面板对空。使用 `analyze/Optimize-KcpsLandBaseDefense.ps1 -CorpsCount <队数> -RaidType <Normal或HighAltitude> -ProficiencyMode <Zero或Max>`，按 `对空＋迎击＋2×对爆`、搭载数、内部熟练度、改修、侦察机倍率及高高度迎击修正枚举全库存；其中 `Zero` 与 `Max` 是显式选择的熟练度对照基线，不读取实际内部熟练度，输出不能冒称账号当前状态；再用当前维护中的制空权模拟器交叉核对。防空队数量从一队变为两队或三队时必须重新联合优化，禁止从另一套防空表中截取若干行复用。高高度空袭的火箭战斗机数量与0.5/0.8/1.1/1.2倍补正按全部防空队合计计算，火箭机可以集中在同一队；不能要求每队各放一架，也不能把 Me 262 等非火箭机误算作火箭机。按敌攻击机槽位把高对爆飞机优先放在前面的中队。`【陆航】` 对每队写侦察机倍率后的本队防空制空，再统一写 `高高度空袭：是/否`、`防空队合计火箭局战：N架`、全队补正与最终合计制空；身份检查、备注数量与优化结果必须一致。
- 出击陆航与防空陆航必须分开推演。出击方案还要同时考虑目标点航程、侦察机延长航程、每波制空状态、前一波击坠对后一波与本队航空战的状态传递、目标种类、攻击倍率、活动增伤、对空射击回避、熟练度损耗及多队投放顺序；不能把防空制空最高的四架飞机机械用于出击。
- 每个陆航目标点必须从最新敌编成表记录目标类别，并让编成、阵型和飞机职责同时匹配。潜水目标只能把东海或满足当前基地反潜攻击门槛的飞机计作有效目标火力，不能把普通对舰陆攻集中到潜艇点后声称“加强输出”；阵型必须采用对潜阵型。空优目标应优先比较远程战斗机削减敌机与本队独立达线两类方案，不能复用对舰轰炸表；路线规格至少保存目标类别、敌制空或敌舰种来源及核对日期，校验器应拒绝“目标类别、阵型、陆航职责”互相矛盾。
- 同一目标点同时存在潜艇和水面舰时，必须按水潜混编目标单独建模，记录两类敌舰数量、阵型、夜战策略和资料来源。要求 S 胜时应把手数明确分为“清水面”与“击沉潜艇”：通常至少一队有效反潜陆航、一队对舰陆航和足量本队先制反潜；一队对舰陆航已经能清空水面舰时，不得再把第二队纯对舰陆航集中同点，否则后投队可能因没有合法目标而整队无效。
- 水潜混编目标优先比较反潜支援而非炮击支援。反潜支援只攻击潜艇，可与清理水面舰的陆航互不抢目标；决战支援必须满足支援舰队的舰种条件，并逐槽统计真正参与反潜支援攻击的航空反潜装备。不得把母舰面板对潜、声呐或爆雷误计为支援伤害，也不得只凭“已启用决战支援”判断它有效。
- 水潜混编目标含敌空母时，反潜支援仍会进行制空判定和被击坠判定。必须按支援舰实际搭载数和对潜哨戒装备对空值计算支援制空，且不计通常舰载机熟练度与改修；优先利用能同时参加反潜与制空的一式战20战队、爆战或带对空的有效反潜机跨过所需制空线，再比较少数低对潜槽与其余大槽残机稳定性的得失。动态候选必须按位置保证制空下限，合计仍跨过目标制空线；不能把一组固定示例船的制空写成任意换船后的保证值。路线规格记录敌制空、最低支援制空、预期航空状态及来源，校验器核对每个角色门槛和逐槽配装。
- 普通单舰队或游击舰队昼战后进入夜战时，对潜攻击通常只能造成擦伤且不能击沉潜艇。水潜混编 S 胜目标若昼战未清完潜艇，目标点必须自动停止夜战止损；阵型应采用与舰队形态对应的对潜阵型，不能靠夜战补救反潜手数不足。
- 路线规格用 `MixedSubmarineSurfacePlan` 固定敌舰组成、目标阵型、禁夜战、本队先制反潜实例与陆航职责，用 `BossSupportPlan` 声明反潜决战支援舰种骨架、通用候选能力及保证的航空反潜槽数，不固定支援舰船ID。2驱逐、2轻母、2正航母系是可轮换骨架；携旋翼机的驱逐可以增加攻击，但不能未经核验就用来替代第二艘必需反潜舰。活动校验器必须交叉核对这些声明、最终改装、陆航身份检查与战斗策略。实战复盘还应识别“后投陆航没有合法目标”和“支援到达但没有有效攻击”等信号，不能把它们归为随机失败。
- 目标点所需航程必须从当前活动、当前阶段的最新日文 Wiki 节点表核对；存在基地迁移时使用迁移后的阶段值，不能沿用前一阶段或迁移前的数值。每支出击陆航的波次目标、真实所需航程、资料 URL 和核对日期都写入私人 `route-overrides.json` 的 `LandBasedAirCorpsTargetRadii.Routes`，以路线规格 `Id` 关联。同一基地航空队分投多个点时，队级 `RequiredRadius` 取各波目标真实航程的最大值。该表是独立证据，不得从成品备注、身份检查脚本或路线规格反向复制后直接标记为已核对，配置生成脚本也不得写入或覆盖该证据表；新目标必须先独立查证并单独维护证据，再运行生成与校验。
- 交付时必须把独立证据中的地图、目标点和航程，与 `【陆航】`、`RequiredLandBasedAirCorpsRadius`、出击前身份检查四槽及整队计算有效航程交叉验证。四者内部彼此一致仍不够；缺少独立证据、目标点不同、任一处航程不同或整队有效航程不足均阻断交付。对潜值合格的舰载反潜机也可能因半径过短而不可用，必须先满足航程硬约束再比较伤害和抗击坠。
- 用户或攻略复核已经否决某个陆航方案并确认替代方案后，必须同时更新成品配置、它的规范生成脚本和路线规格中的 `ExpectedLandBasedAirCorps`，不得只手改成品。生成器重跑前必须比较既有路线规格中的已确认陆航；不一致时拒绝覆盖，直到重新调查并明确更新定稿。成品中的 `【陆航】`、出击执行单元三队动作、出击前身份检查声明和路线规格定稿必须四方一致；活动校验器逐队逐槽比较，防止后续维护把已否决方案带回来。生成器不得提供“跳过身份检查器更新”后仍直接写出成品的开关；确需中间加工时只能写临时文件，最终写回前必须重建检查器并通过一致性审计。
- 修改陆航波次目标或航程时，必须在同一次生成中同步更新成品配置、规范生成脚本、路线规格和独立航程证据表；四者中任一仍保留旧目标、旧阶段或旧航程都视为不可交付。独立航程证据必须来自本次查证资料，不能由成品配置反向生成后冒充外部证据。
- 攻略存在图片主方案时，路线规格必须保存 `LandBasedAirCorpsGuideSource`、逐队逐槽的 `LandBasedAirCorpsGuideBaseline`，并以 `LandBasedAirCorpsPlanClass=GuidePrimary|GuideAlternative|AccountOptimized` 标记最终方案来源。`LandBasedAirCorpsDecision` 必须明确写“采用攻略图主方案”或“采用备选/账号方案并已完成比较”，不能只写最终四格。标记为 `GuidePrimary` 时最终四格必须与图片基线完全一致；另外两类必须有 `【陆航方案比较】`。备注与路线规格若把攻略正文中的可选方案描述成默认方案，视为调研证据不一致，禁止交付。
- 陆航的普通型、熟练型、诱导弹型等同系列装备必须按生成时账号中的具体实例逐架比较，不能把生成器或旧配置中的硬编码清单当成当前库存，也不能把名称中的“熟练”自动视为全方位上位。比较至少包含：雷装/爆装、命中、对空射击回避、航程、活动增伤、目标舰种补正、改修对基地攻击力的 `0.7×√★` 收益、改修对陆攻制空的 `0.5×√★` 收益，以及替换后是否跨过每一波的硬制空线。目标点航程是硬约束：上位型号即使面板更高，只要与当前侦察机组合后的整队有效航程不足，就必须改用能够到达的型号，并在 `【陆航方案比较】` 明确写出两套有效航程。跨配置共享陆航时，根据本次运行顺序、准备成本和保留要求安排飞机，不把最高面板作为唯一目标。账号同时拥有上下位型号而最终仍使用下位型号时，备注必须点名两种装备并说明改修、制空、命中、抗击坠、活动增伤、目标舰种补正与航程的取舍。
- `【陆航】` 以操作信息优先，禁止塞入成段的机制说明。固定按“基地空袭与开放队数一行 → `第N队：动作；第一波目标、第二波目标。` → 第1至第4槽各占一行 → 制空结论一行 → 自动控制一行”排版；不得把两个槽合并在同一行。每个槽写成 `第N槽：装备名｜简短理由。`，只保留影响选择的关键理由；长篇计算和候选比较放入 `【陆航方案比较】` 或生成记录，不放进用户照着配飞机的区域。
- 陆航四槽理由必须对应实际装备职责：侦察机写航程与伤害补正，战斗机写每波制空与陆攻损失，陆攻写目标舰种、命中或抗击坠，火箭局战写高高度空袭补正。装备职责应优先由最新装备主数据的类别判定；名称匹配只能作后备，并须覆盖“艦戦”“戦闘機”“隼”等常见命名。禁止用“兼顾制空、命中与输出”一类无法解释具体槽位的通用句填满四格，也不得把战斗机写成“按目标舰种补足输出”。
- 基地防空结论必须引用当前海域、当前难度的最强基地空袭敌制空，并用最终四槽、18机和声明的熟练度/改修条件重新计算。明确分别写出空优线和确保线，以及最终只能空优还是可以确保；不得沿用其他海域的固定近似值。
- 舰队经过的空袭战和母港基地遭到的基地空袭使用不同的参战单位与制空计算。防空牌子的基地航空队只迎击基地空袭，不会帮助本队取得路线空袭点的制空；备注和方案比较不得把两者混为一谈。
- 出击与防空中的基地航空队都视为正在使用；出击后为每队分别加入 `陆航休息N` 执行单元，并在需要时补给。
- 一个 `陆航休息N` 执行单元只控制同编号的一队，不能用一个执行单元代替多队。
- 陆航点选矩形必须覆盖目标点在未访问、已访问和特殊图标状态下的共同有效区域；不能只与有效圆相交一小块。
- 陆航也按实际方案条件生成，不能把模板中的三队占位执行单元全部照搬：
  - 某队用于出击时，在 `出击` 执行单元中把该队动作设为出击，开启疲劳检查和四中队补给，并设置两个经过图像校验的目标范围；集中时两个目标相同，分散时分别设置。
  - 某队用于防空时，把该队动作设为防空并开启疲劳检查和四中队补给，不填写出击目标范围。
  - 每个设为出击或防空的航空队都单独配置一个位于 `出击` 之后的 `陆航休息1/2/3` 执行单元：尾号必须等于基地航空队编号，单队也不省略；只切换到休息并补给四中队，不在此处重配飞机；挂入总控 `SupplyAfterWorkflows`，但事件阈值不计入陆航休息单元。
  - 未使用或尚未开放的航空队动作保持未设置，目标范围为空，疲劳检查关闭；不得为它保留陆航休息或其他基地航空队执行单元。
  - 三队全部不使用时，不生成任何 `BasicOutfitLandBasedAirCorpWorkflow`。`【陆航】` 必须与 `出击` 中三队动作及陆航休息单元逐队一致。
- KCPS 出击配置负责陆航牌子、补给、疲劳和目标点；实际四槽飞机配装按攻略、航程、制空、对空射击回避和账号库存决定，并完整写入 `【陆航】`，不能仅写“陆航出击”。
- 支援只在能显著改善道中通过率或目标胜率时加入；支援舰船和装备也要按账号库存核验。
- 支援决定不能只写在备注里：读取出击执行单元中的道中/决战支援舰队编号，相应编成、改装、入渠、补给和总控关联必须成套出现。没有使用的支援结构应从模板中移除。
- 配置名中的 `道中支援`、`决战支援`、`【支援】` 备注以及出击执行单元的两个支援开关必须四方一致；活动校验器应直接对照，不能只相信备注文字。

航母补强槽必须和全队炮击顺序一起推演。`熟練甲板要員+航空整備員` 会提高射程，可能让航母抢在特殊攻击旗舰或高价值战舰之前行动；只有这种顺序变化能提高目标成功率时才使用。若航母是纯舰战架或需要让法国战舰等旗舰尽早发动特殊攻击，优先保留喷进炮等不扰乱射程的方案，并在 `【配装对照】` 写明。

## 备注执行单元

活动配置使用名为 `备注` 的 `MemoWorkflow`，并且它必须是配置内第一个执行单元；名为 `总控` 的 `RelationalSortieWorkflow` 必须紧随其后成为第二个执行单元。不得把抑制消息、编成或其他执行单元插在备注与总控之间。备注至少包括：

复制模板或旧阶段配置后，除主备注外还必须重写所有执行单元自身的 `Memo`。`总控`、`出击`、`组成联合舰队`尤其不得残留其他 E/P 阶段、旧路线、旧目标、错误联合舰队类型或大和型等旧战术说明。校验器应扫描所有非备注执行单元中的 `E#P#` 标记，并把与当前配置名阶段不一致的内容视为硬错误；路线规格声明联合舰队类型时，`组成联合舰队`说明也必须写明相同类型。

KCPS 的备注框不会自动换行，必须在 JSON 字符串中主动写入换行。备注正文统一使用 LF（`\n`），不得保留 CRLF（`\r\n`），否则不同 KCPS 界面版本可能无法稳定显示章节空行。按显示宽度计算单行上限为 120 列：中文、日文和全角符号按 2 列，ASCII 按 1 列。章节标题单独一行，每个完整判断、候选排除、配置结论或装备组自然成行；一句话或同一连续表达在合并后仍不超过 120 列时，不得过早断行。每两个 `【小节】` 之间必须恰好保留一个空白行，不能让章节首尾紧贴，也不要堆叠多个空白行。`【陆航】` 中不同基地航空队的内容块之间必须恰好保留一个空行；每队内部的动作、四个槽位与结论连续排列。`【选船结论】` 和 `【配装对照】` 中不同舰队的内容块之间也必须恰好保留一个空行；同一舰队内各位置连续排列。URL 可以单独占一行；禁止把整个章节压成一条超长行，也禁止机械沿用较低字符数阈值切碎正文。

- `【目标】` 难度、阶段、目标点、胜利等级、次数。
- `【锁船】` 只写本阶段实际使用的锁船标签；“活动出击会贴条”“贴条不可逆”等活动常识不重复解释。
- `【资料来源】` 分别写出攻略、锁船分配表及其他实质采用资料的准确名称和 URL。默认引用生成配置时可取得的当前攻略，不写“新版”“旧版”“最新版本”等无助于复核的版本形容词。
- 攻略正文、汇总表与日文 Wiki 的条件列表不一致时，必须比较页面更新时间并查找更新记录或第二来源。日文 Wiki 已确认而攻略尚未补入的新条件不得静默遗漏；采用结论及差异写入备注，配置文件仍按完整条件集生成。
- `【多号机】` 每艘选中船的实例 ID、正式编号和放弃替代船的理由。
- `【路线】` 写完整节点序列，每个节点后用中文括号标明点类型，例如 `A（潜水战）→B（能动分歧）`。进入边编号只属于 KCPS 条件战斗策略实现，不写进给人阅读的备注；能动选择也由路线与策略表达，不重复罗列内部数值。
- `【攻略与分配】` 先概括攻略建议的编成、战术与锁船分配表候选池，并说明这些候选在后续哪些标签或阶段还可能使用。
- `【候选与排除】` 列出账号中满足任务、路线和舰种要求的实际候选，逐类核对改造形态、几号机、战力、其他标签用途和当前不可用原因；写清排除哪些船以及为什么。
- `【选船结论】` 在上述候选中说明最终每个位置的选择、职责、舰队顺序和与锁船分配表不一致之处。不能只用“对潜高”“练度高”等单项理由代替完整筛选过程。
- `【配装对照】` 先写攻略采用或允许的配装与战术，再写账号可用的装备、数量与改修情况，明确相对攻略缺少或富余多少，最后说明在攻略可选战术中为何采用当前方案。攻略没有给出具体装备时必须明确写明，不能伪造逐件差距。
- `【编成与顺序】` 每艘船角色、位置和特殊攻击关系；内容可以并入 `【选船结论】`。
- `【配装】` 每槽用途、稀有装备分配和补强槽；内容可以并入 `【配装对照】`。
- `【制空】` 门槛及三档舰队制空；没有航空战则写不适用。
- `【出击阈值】` 出击前入渠剩余 HP 上限、旗舰/伴随舰最低士气、阈值依据，以及是否为高士气单次出击。
- `【出击概率分析】` 在使用概率分析时记录当前难度和阶段的估算；磨血与斩杀分开。无法可靠建模时写明原因，不得伪造概率；这不替代路线、编成与终止条件的实际验证。
- `【陆航】` 每队四槽、航程、目标点；不用则说明理由。
- `【支援】` 使用与否及理由。
- `【终止】` 具体节点、评级、次数或血条条件。
- `【不确定项】` 攻略尚未确认或偏离标准打法之处；存在关键不确定项时不得交付可运行配置。

备注面向实际使用者记录决策，不承担 KCPS 内部调试日志的职责。地图点的条件值、进入边、GUID、事件计数器等实现细节应由条件策略和校验工具保证，除非它们构成需要用户人工处理的已知限制，否则不得写入备注。

活动配置的最低士气同样遵守通常出击规则。要求高于 49 时关闭两个自然恢复等待开关，说明手工准备和不足时的处理；循环数按当前计划声明，不自动添加刷闪或给粮流程。

自动化方式由本次目标、用户是否参与和准备条件决定，写入 `StageDesign` 及 `【自动化模式】`。分别声明循环上限、最低士气、修理阈值、陆航熟练度检查、目标点夜战与停止条件，不将它们捆绑成所有任务必须遵循的一套数值。

- 自动循环必须覆盖每个会暂停等待的操作。需要用户手动夜战、补充熟练度或准备高士气时，明确安排交接点或单次执行，不声称无人值守。
- 高于自然恢复上限的士气要求不能靠自然等待实现；保留单次准备与用户确认的边界。具体要求由当前方案给出，不把某次高难度任务的数值作为全局最低值。
- 满血、满熟练度、手动夜战是否必要应分别有依据。半自动不自动意味着三者全开，目标战斗没有夜战时也不能要求无效的手动夜战窗口。
- 仅生成用户要求且当前阶段需要的变体。需要同时比较自动与半自动方案时，使用独立 GUID 与独立路线规格；`FinalAutomationPair` 只用于本次明确成对的变体，所需变体集合由本次计划声明。
- 从实战记录比较方案时按完整出击统计瓶颈；配置重构后，旧样本只作诊断参考，不直接当作新方案成功率。

仅在本次需要一对自动/半自动方案时使用 `enable/KCPS-EnsureHpFinalAutomationVariants.ps1`。除源配置、目标名称、阶段、目标点及路线标识外，必须提供 `-AutomaticPolicyPath` 与 `-SemiAutomaticPolicyPath`。两份私人 JSON 策略各自包含 `LoopLimit`、`MoraleMinimum`、`DockingHpThreshold`、`WaitForNaturalMorale`、`LandBaseProficiencyChecks` 和 `BossNightBattle`；各项数值必须由本次策略明确提供。先用 `-CheckOnly` 核对预期变更。

指定点到达、空优或胜利即完成且不再需要继续前进时，目标点条件策略必须把战后动作明确设为撤退：`DefaultAdvance = 2`。不能只在备注写“回港”而保留 `DefaultAdvance = 0` 手动选择；总控通常要等出击返回后才能统计目标并自动停止，这种文字与字段不一致会让 KCPS 卡在进击/撤退页面。交付前必须逐条核对策略备注中的“进击、撤退、回港”与实际枚举值一致。还必须根据路线终点与节点类型独立检查非Boss战斗终点，无论备注是否写“回港”；路线规格的 `ExpectedAdvance` 也必须为2，不能让规格与配置同时写错而通过校验。目标战未取得要求评级时同样先回港，再由总控决定继续循环，不能停在进击页面等待。

## 活动停止与完成消息

`通知通关.Message` 必须能唯一标识本次完成条件，固定写成：

`E编号 阶段 用途 目标 条件 Clear`

其中“用途”写 `开路`、`解谜`、`削甲`、`运输`、`磨血` 或 `击破` 等阶段目的；“目标”写具体地图点或血条；“条件”写胜利等级与累计次数、到达次数、制空条件或血条归零条件。示例：

- `E<区域> P<阶段> 开路 <目标点> <胜利等级与次数> Clear`
- `E<区域> P<阶段> 削甲 <目标点> <胜利等级与次数> Clear`
- `E<区域> P<阶段> 运输 TP条归零 Clear`

禁止使用省略用途和次数的短消息。同一地图点可能在不同阶段承担不同要求，后续配置的 Python 监听字符串必须与完整消息逐字一致。`通知通关` 仍挂在总控的自动停止后触发列表中。

只有总控的每一种自动停止原因都能证明目标已经完成时，才允许使用 `通知通关` 和 `Clear`。若总控同时保留循环次数上限、连续失败上限等安全停止条件，这些条件本身不能证明完成，应把执行单元改名为 `通知停止`，消息固定写成：

`E编号 阶段 用途 目标 已停止`

格式为 `E<区域> P<阶段> <用途> <目标> 已停止`。`通知停止` 同样挂在自动停止后触发列表中，但消息不得包含 `Clear`，备注必须说明它只表示流程停止，用户应依据游戏状态确认是否完成。不得为了保留安全上限而发送虚假的完成消息。

## 固定舰船练级

练级使用 `StageDesign.Phase=Leveling` 与 `SelectionMode=FixedInstances`，不继承旧攻略的血条、掉落或评级停止条件。当前检查器支持固定实例方案，不声明尚未实现的自动换船或自动改造能力。

- 由用户目标和当前节点证据确定待练对象、舰队形态、路线、战斗次数及停止条件。训练优先级和各位置职责均由本次计划声明。
- `TargetStrategies` 按目标进入边声明 `ConditionValue`、`Formation`、`Advance`、`Midnight`、`WayPoint`。单点撤退、多点战斗和其他训练路线按实际节点配置，不能沿用旧地图的条件值。
- `RouteCompositionRules` 保存当前路线的舰种或船名谓词、舰队范围、速力与数量上下界、来源和查证日期；缺少可核实路线约束时报告缺项，不使用内建活动地图特判。
- 需要先制反潜的方案才提供 `OpeningAsw={Fleet,MinimumCount}`，并按实际舰队、改造形态、配装和敌人检查；其他训练模式不强制套用反潜职责。
- `SelectionPolicy` 可按本次角色声明允许副本编号与等级上限，未声明时不限制成固定的副本和等级组合。`SelectionAudit` 保存实际角色、主数据ID、槽数和当前形态供复核。
- 旗舰经验分配通过 `FlagshipTraining.ExpectedIds` 按舰队号声明。改装资源分配由 `RefitFleetPriority` 与可选 `RefitFirstShipId` 表达实际顺序，不写死某队旗舰优先。
- 改造规划按明确的实例或角色声明 `RemodelPolicy`。改造后重新核对形态、槽位、先制条件和路线；规划本身不授权自动改造，也不隐含等级停止要求。
- `FatigueMode`、`SupplyPolicy`、修理阈值和循环上限由本次风险与效率目标决定。采用红疲劳或条件补给时，相关门禁、实际补给单元和事件阈值须与声明一致；不能同时保留互相矛盾的满补给门禁。
- 不需要的装备槽可在比较收益后显式卸装，理由用 `KCPS_ALLOW_EMPTY_SLOTS=槽号列表; REASON=中文理由` 记录。原生普通槽必须从第1槽连续装入，空槽只能在末尾；补强增设独立。`FillAllUsableSlots=true` 时按该声明检查，不让旧模板的装备分配成为全局策略。
- 陆航动作与疲劳检查分别通过 `LandBaseActions`、`LandBaseFatigueChecks` 声明；按当前路线查证基地空袭风险，不能由“练级”或“首战撤退”推断所有基地休息。
- `VacancyPolicy` 使用当前游戏要求及明确的安全余量。原生“小于等于”停止比较需要区分最低可出击空位与停止值，不固化某次活动的门槛。
- 实例分组是否需要跨方案互斥由本次计划声明。更新配置时保留用户不相关设置，但必须同步最终编成、改装、身份检查和路线方案，不只改名称或备注。

`KCPS-LevelingValidation.ps1` 对照上述运行时策略核验。

## 校验

统一收尾工具会先完成通用规范化，再依据 `SimpleSortieWorkflow.Sea=0` 自动调用活动专用校验。新活动配置交付前优先运行：

```powershell
pwsh -File (Join-Path $SKILL_ROOT 'scripts\poi-kcps-api\validate\KCPS-FinalizeSortieConfig.ps1') -Path '<CONFIG_PATH>'
```

需要单独定位问题时，再分别运行通常结构校验和活动专用校验：

```powershell
pwsh -File (Join-Path $SKILL_ROOT 'scripts\poi-kcps-api\validate\KCPS-ValidateConfig.ps1') -Path '<CONFIG_PATH>' -RequireRouteSpec -FailOnProblems
pwsh -File (Join-Path $SKILL_ROOT 'scripts\poi-kcps-api\validate\KCPS-AuditRefitEquipmentCapacity.ps1') -Path '<CONFIG_PATH>' -FailOnProblems
pwsh -File (Join-Path $SKILL_ROOT 'scripts\poi-kcps-api\validate\KCPS-AuditLandBasePlanConsistency.ps1') -Path '<CONFIG_PATH>' -FailOnProblems
pwsh -File (Join-Path $SKILL_ROOT 'scripts\poi-kcps-api\validate\KCPS-AuditLandBaseEquipmentCapacity.ps1') -Path '<CONFIG_PATH>' -FailOnProblems
pwsh -File (Join-Path $SKILL_ROOT 'scripts\poi-kcps-api\validate\KCPS-ValidateEventSortieConfig.ps1') -Path '<CONFIG_PATH>'
```

`KCPS-FinalizeSortieConfig.ps1` 默认把 `Ready=false` 作为失败退出；只有生成器尚未安装身份检查器等明确的中间加工阶段，才可临时使用 `-AllowNotReady`，并且成品必须再次无该开关运行。禁止只把校验输出丢弃而不检查结果。单独运行 `KCPS-ValidateConfig.ps1` 时必须带 `-FailOnProblems`，使 `ProblemCount>0` 直接返回失败。

规范生成器若在初次最终化之后还会注入身份检查器、点选计数器、TP 基线脚本或重写备注，注入完成后必须再次执行最终化的应用阶段，再执行一次只读 `CheckOnly`。交付判定只能采用最后一次 `CheckOnly` 的结果；不能拿后处理之前的通过结果证明最终文件可用。

活动专用校验必须确认：

- `Sea=0`，不是通常海域。
- 已启用活动出击前身份检查；单舰队检查实际出击队，联合舰队检查第一、第二舰队，出击/防空陆航逐队逐槽检查。
- `【陆航】`、出击动作、身份检查器和路线规格的陆航方案逐队逐槽一致；不得因生成器跳过检查器更新而保留旧阶段方案。
- 每支出击陆航在独立航程证据表中都有来源与核对日期；证据目标点、证据航程、备注目标点、备注航程、路线规格航程和最终四槽有效航程全部一致且可达。
- `【陆航】` 的不同基地航空队之间、`【选船结论】` 与 `【配装对照】` 的不同舰队之间均恰好保留一个空行。
- 同一配置全部出击/防空陆航的逐装备需求总数不超过账号总持有量，容量扫描无问题。
- 联合舰队的 `组成联合舰队` 是总控 `DockingBeforeWorkflows` 的第一个启用项，且 `DockingBeforeFinishedEventThreshold` 只等于其中启用的入渠执行单元数量。
- 主出击舰队各位置只有一个明确实例候选。
- 每个固定实例都有按舰船 ID 定位的唯一改装块，找不到舰船时不得静默跳过；除显式声明的专用工具例外外，所有普通槽和已开放补强槽均有明确装备，找不到槽位或装备时不得静默跳过。同时按公共规则检查配置中不存在的主槽，不能只验证实际槽已配齐。
- 选中实例存在、已锁定，并能解析出正式几号机。
- 备注记录带名称和 URL 的攻略、锁船分配表、标签、完整候选筛选、配装对照和每艘船的编号。
- 路线中每个地图点都标明点类型，且不包含进入边编号或条件值。
- 路线规格包含 `KcNavMap` 和完整有序 `Route`；通常校验已联网按相邻点核对全部进入边编号。
- 存在阶段开放状态优先于舰数、舰种、速度或索敌的分岔时，`RouteBranchAssertions` 已记录实际命中的高优先级条件；最终船数、`ExpectedFleetCounts` 与备注中的阶段说明三者一致。
- 所有实际参战舰队均已完成贴条核对；已贴条实例必须命中路线规格的 `AllowedSallyAreas`，冲突或无法证明兼容时校验失败；远征占用仍作为实时状态提示。
- 通常海域的等价船轮换脚本没有改写活动配置。
- 战术开关与最终改装形成双向闭环：无烟幕装备不得开烟幕；携带烟幕装备却没有任何策略使用烟幕同样是无效占槽；无旗舰司令部不得自动退避。
- 动态支援驱逐第1、2位的第4主槽使用“槽不存在则跳过”的电探规则。
- 账号同时拥有陆航普通型和熟练型而仍选择普通型时，备注有可复核的 `【陆航方案比较】`。
- 磨血/斩杀路线规格的 `StageDesign` 与成品士气、入渠、循环、陆航熟练度、Boss击沉停止及自动化模式一致。
- 使用特殊攻击时存在未过期的规则条目和 `SpecialAttackPlan`；舰队形态、发动阵型、抑制节点、惰性例外与核心舰船位置全部通过。

校验通过仍不等于锁船计划永远有效。攻略或锁船表更新后必须重新读取并重跑校验。

## 交付前清单

- 已读攻略开头、阶段正文、全部图片和锁船分配表。
