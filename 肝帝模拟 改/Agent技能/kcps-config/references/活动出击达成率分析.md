# KCPS 活动出击达成率分析

概率分析用于用户需要比较方案或估计达成率时，不是生成每份配置的前提。通用配置校验仍负责路线、编成、配装、标签、资源与停止条件；模型尚未覆盖某种机制时，说明无法可靠估算，不能编造数字，也不能把模型限制说成游戏禁止该方案。

## 数据流与支持范围

```text
当前目标、路线证据、敌编成、账号快照与显式初始状态
  -> 分析请求
  -> 满足硬条件的候选
  -> 完整航次模拟与目标统计
  -> 结果、假设与不确定性
  -> 需要时写入最终配置备注
```

已有配置可以作为候选基线，不能成为唯一生成入口。账号快照、请求、候选、模拟批次和结果保存在本次明确指定的私人路径；使用工作区默认位置时，工具采用 `<WORKSPACE_ROOT>/.work/sortie-analysis/`。运行资料不写回 Skill。

当前适配器支持**单舰队、固定路线、目标点胜利等级**分析，`Simulation.ModelScope` 为 `SingleFleetFixedRoute`，`Goal.Type` 为 `RankAtNode`。舰队排列与配装可以形成候选；每个候选须事先满足游戏和任务硬条件。

以下输入尚未完成适配，不得用简化结果冒充完整方案概率：我方或敌方联合舰队、陆航、支援、随机路线分支、退避及其他未建模的一次性机制、跨阶段状态变化、非满载机初始数量和精确内部熟练度。工具应明确拒绝未支持输入。假设方案与实际配置不同的分析只能标为独立基线，不能声称是实际配置的成功率。

## 工具与契约

运行需要 PowerShell 7、Python 3（含 `jsonschema`）、Node.js，以及用户选定且通过接口检查的 KC3Kai 引擎版本。输入结构会在运行时严格校验，未支持字段不能静默忽略。

工具位于 `../scripts/poi-kcps-api/analyze/`：

- `Get-KcpsEventSortieAccountSnapshot.ps1`：只读获取账号船、装备、舰队和主数据，写入私人目录。
- `Get-KcpsSortieAnalysisSources.ps1`：获取指定地图的路线与敌编成，记录来源、采集时间和内容哈希。
- `New-KcpsEventSortieCandidateScenarios.ps1`：根据请求与快照生成候选，解析显式状态与增伤。
- `runtime/KC3Kai-HeadlessRunner.js`：按固定种子运行已适配的 KC3Kai 模型。
- `Invoke-KcpsEventSortieCandidateAnalysis.ps1`：去重、批量模拟、统计完整航次的目标结果与抽样区间。
- `Export-KcpsEventSortieAnalysisResult.ps1`：导出所选候选的结果、输入假设和可靠性。
- `KCPS-FormatSortieProbabilityMemo.ps1`：从结果生成中文备注，可靠性不足时不展示伪精确概率。
- `Set-KcpsEventSortieAnalysisMemo.ps1`：将分析备注写入最终配置。

请求与结果均为版本 `2`，结构分别见 [请求契约](../scripts/poi-kcps-api/data/KCPS-EventSortieAnalysisRequest.schema.json) 和 [结果契约](../scripts/poi-kcps-api/data/KCPS-SortieAnalysisResult.schema.json)。旧请求需要补齐显式假设，不能继续沿用“缺省即满状态”的解释。

## 请求内容

请求显式提供当前地图、难度、固定进入边和战斗点顺序、来源、候选舰船与配装、模拟次数及非空且不重复的种子。

`Goal` 包含 `Type=RankAtNode`、`TargetNode`、`MinimumRank=S|A|B`、`RequiredSuccesses` 与布尔值 `IndependentRepeatedSuccesses`。目标点和每个战斗点的阵型、夜战等必须与模拟器实际支持的语义一致，不能静默忽略额外战术。

`FleetSearch` 的实例、位置、可交换范围和配装由本次任务提供，不保存特定活动舰队。攻略可以作为有来源的候选依据，自定方案也可以分析；候选范围、编成与配装由本次请求明确提供。

## 显式初始状态

`Simulation.InitialState` 必须包含 `Kind=Actual|Baseline` 和 `Source`，并逐项声明：

| 字段 | 模式与数据 |
| --- | --- |
| `Supply` | `Snapshot`、`Explicit` 或 `Full`；显式数据为 `Ships` 按舰船实例 ID 映射的 `{FuelFraction,AmmoFraction}`，取值 0 至 1。 |
| `Hp` | `Snapshot`、`Explicit` 或 `Full`；显式 `Ships` 映射到实际耐久整数。 |
| `Morale` | `Snapshot` 或 `Explicit`；显式 `Ships` 映射到 0 至 100 的士气。 |
| `AircraftCounts` | `Snapshot`、`Explicit` 或 `Full`；显式 `Ships` 映射到各槽飞机数量数组。当前适配器对非满载机输入报告不支持，不把它补满后继续。 |
| `ShipAircraftProficiency` | `SnapshotDisplay`、`ExplicitDisplay` 或 `MaxDisplay`；显式 `Equipment` 按装备实例 ID 映射到显示熟练度 0 至 7。 |
| `LandBaseAircraftProficiency` | 当前只接受 `Mode=NotApplicable` 及 `Reason`，因为尚未适配陆航。 |

`Actual` 读取或声明真实状态，禁止 `Full` 与 `MaxDisplay`。满血、满补给或满显示熟练度对照必须另建 `Baseline`，并记录假设来源。即使实际状态恰好已满，也要用快照或显式实际值表述，而不是用未经核对的满状态模式替代。

显示熟练度不能等同于已验证的内部熟练度；传入显示值 7 不代表内部值 120。油弹、HP、士气与熟练度在候选、结果和备注中保持一致，不能在导出时改写成满状态。

## 增伤与来源

`BonusProfiles` 必须恰好有一个 `Role=Primary` 主模型；其他模型可用 `Role=Sensitivity`。每项保存 `Name`、`Applicability`、`Verified=true`、`Source` 和 `LastVerifiedJst`。

- `Applicability=Applicable`：当前支持 `Model=DamageMultiplier`，在 `ShipBonuses` 中为每艘选中船显式提供 `DefaultDamage`，必要时提供 `ByNode`。不把缺失船舶倍率自动当成 1。
- `Applicability=NotApplicable`：提供查证来源和日期，明确 `Multiplier=1`，不附带 `ShipBonuses`。
- 未知倍率、未经核实的机制或超出模型范围的增伤，应报告不能可靠分析；“没有查到”不等于“已确认不适用”。

当前路线、敌编成和机制每次使用前重新核对，来源快照保留 URL、采集时间、哈希和可信度。引擎记录仓库与版本。

## 统计与多次目标

单次出击按节点顺序模拟，不能将分别测得的各点成功率独立相乘。分别报告到达目标点、到达后满足评级以及同一完整航次联合达成目标的统计；单次达成率使用最后一项。

只有请求明确 `IndependentRepeatedSuccesses=true`，且重复航次的初始条件、路线、敌编成和战术保持适用时，才估算累计完成所需次数。否则可以报告单次结果，但不套用独立重复公式。

HP/TP、开路、削甲、敌编成或跨航次资源发生变化时，需要对应阶段状态模型。当前适配器尚未实现这类状态机，不能把多个阶段的估计合成一个“通关概率”。

候选比较使用相同来源与可比较的种子和次数。根据候选差异和目标稀有程度安排样本量，不能仅凭固定次数称为充分；抽样区间与模型误差分开说明。差异小于抽样噪声或敏感性方向不一致时，不宣称明显更优。

## 备注与交付

使用分析时，备注记录引擎版本、实际状态或基线假设、目标与支持范围、模拟次数和种子、抽样区间、候选范围、最终取舍以及最大不确定项。初始状态从结果原样传递，不能手写与分析不同的准备条件。

引擎警告、缺失批次或不支持输入不能默认为可靠。可靠性不足时输出原因，不展示具体成功率。无法提供可信概率时，可以继续验证与交付本身已充分核实的配置，但必须如实说明未建模部分；路线、标签、编成、配装或停止条件等执行事实缺失时，仍须先解决缺项。
