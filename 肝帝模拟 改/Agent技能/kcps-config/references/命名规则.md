# KCPS 配置命名规则

所有新生成或重新整理的 KCPS 配置文件和内部配置统一使用本规则。通用任务查证、术语、JSON 和交付规则见 [公共规则.md](公共规则.md)；出击、演习和编成的类型专用命名后缀分别见 [通常出击配置.md](通常出击配置.md)、[演习配置.md](演习配置.md)、[编成配置.md](编成配置.md)。

## 配置文件名

```text
<JST_YYYYMMDD> <频率> <种类> <标题>.conf.json
```

- 日期按日本时间 UTC+9 计算。
- 已确认的频次只允许：`单次`、`日常`、`月常`、`周常`、`季常`、`年常X月`。年常必须写开放月份，例如 `年常6月`。
- 频次结论本身仍写有“検証中”“暫定”“推定”“不确定”，新任务整行仍处于验证中且缺乏周期复现证据，或可靠来源互相冲突时，在频次后追加 `（不确定）`，例如 `月常（不确定）`。不要因为旧任务的前置条件仍标“検証中”就否定已经长期复现的频次。连基本频次也无法确认时写 `频次不明（不确定）`，不得猜成 `单次`。
- 种类只允许：`出击`、`编成`、`演习`、`工厂`、`远征`、`改装`、`补给／入渠`。
- Windows 文件名不能包含半角 `/`，因此最后一类固定写全角斜杠 `补给／入渠`。
- 不在种类后写游戏 API ID、wikiwiki 编号或攻略编号。

示例：

```text
<JST_YYYYMMDD> 月常（不确定） 编成 <当前任务标题>.conf.json
<JST_YYYYMMDD> 年常<开放月份>月 出击 <当前任务标题>.conf.json
```

## 频次查证

1. 先查游戏当前任务数据中可用的重置类型字段；再以日文 wikiwiki 当前任务页或新着任务页的频次栏交叉确认。不要从标题、任务 ID、前置关系或“期間限定”字样推断频次。
2. `期間限定` 只表示任务存在期限；它可以同时是月常、周常或其他频次，不能自动写成 `单次`。
3. 读取任务整行的独立频次标记，例如 `デイリー`、`ウィークリー`、`マンスリー`、`クォータリー`、`イヤーリー`；不要把奖励、期限或任务分类当作频次。
4. 若频次本身标有 `検証中`，新任务整行仍在验证且没有周期复现证据，或多个可靠来源不一致，频次保留当前最有依据的判断并追加 `（不确定）`。不得静默选择一个看起来最像的值。
5. 新生成的每个任务配置都应在 `说明` 记录 `【频次依据】`、来源 URL、JST 查证日期和不确定原因。期间限定任务及任何带 `（不确定）` 的配置缺少这行时，命名校验必须直接失败。
6. 若之后可靠资料确认频次，删除 `（不确定）`，同时更新文件名、全部内部配置名及 `说明`；不得只改其中一处。

## 内部配置名

```text
<频率> <种类> <标题> [海域或阶段]
```

- 不写日期。
- 以频率和种类开头，不以任务编号开头。
- 一个配置文件包含多个海域或阶段时，每个配置都重复相同的频率和种类前缀。
- 任务接取执行单元仍必须保留精确游戏 API ID。
- 出击配置的 `Clear` 用户消息仍使用已验证的任务/攻略标识和海域，不因显示名称改变而改写。

示例：

```text
年常<开放月份>月 出击 <当前任务标题> <海域>
月常 出击 <当前任务标题> <海域与阶段>
月常（不确定） 编成 <当前任务标题>
```

## 校验

```powershell
pwsh -ExecutionPolicy Bypass -File (Join-Path $SKILL_ROOT 'scripts\poi-kcps-api\validate\KCPS-ValidateNaming.ps1') -Path '<CONFIG_PATH>'
```

向 `-Path` 传入 配置目录时，校验器必须递归检查所有子目录中的 `.conf.json`，不能只检查根目录第一层。
