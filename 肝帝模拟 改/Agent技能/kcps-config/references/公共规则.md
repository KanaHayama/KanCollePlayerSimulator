本文件保存 KCPS 各类任务配置共用的规则。先读本文件和命名规则，再按实际任务类型读取对应的专用规则：

- 出击：[通常出击配置.md](通常出击配置.md)
- 演习：[演习配置.md](演习配置.md)
- 编成：[编成配置.md](编成配置.md)
- 远征：[远征配置.md](远征配置.md)
- 命名：[命名规则.md](命名规则.md)
- 当前任务、路线与阶段输入：[运行时计划与证据.md](运行时计划与证据.md)
- 共用工具：`../scripts/poi-kcps-api`

专用规则与本文件冲突时，先判断规则是否确实只适用于该任务类型；类型专用流程由专用规则决定，通用安全、查证、命名和交付规则由本文件决定。

## 术语

- **配置文件**：KCPS 可加载的一个 `.conf.json` 文件，可以包含多个配置。
- **配置**：KCPS 左侧列表中的一个条目，通常对应一个任务、海域或阶段，可以包含多个执行单元。
- **执行单元**：配置中的 workflow，例如 `说明`、`总控`、`接任务`、`编成`、`改装`、`出击`。
- 游戏单位统一称“船”或“舰船”。不要在配置说明和用户沟通中使用其他称呼。

讨论和修改时必须说清是配置文件、配置还是执行单元。精确匹配任务、舰船和装备时使用游戏原名；解释文字使用中文，必要的日文、英文专名、接口字段、枚举和错误原文保留原样。

## 连接设置与运行资料

`<SKILL_ROOT>` 表示本 Skill 根目录。将 `KCPS_WORKSPACE` 设置为用户明确选定的工作区 `<WORKSPACE_ROOT>` 后，连接设置和路线证据的默认位置分别为 `.work/kcps.local.json` 与 `.work/route-overrides.json`。也可通过 `KCPS_SETTINGS_PATH`、`KCPS_ROUTE_OVERRIDES` 分别指定文件。连接设置提供本机地址、安装路径和口令；路线证据提供本次路线、阶段、标签和航程条件，工具将其与公共节点参考合并。具体字段与读取顺序见 [API 工具说明](../scripts/poi-kcps-api/README.md) 和 [运行时计划与证据](运行时计划与证据.md)。

## 输出与文件卫生

- 配置输出到用户明确指定的路径；需要工作区时，由用户明确选定，本文用 `<WORKSPACE_ROOT>` 表示。
- 输出只写入用户明确指定的位置，不覆盖 `<SKILL_ROOT>/assets/templates/` 中的模板，也不向 Skill 目录写入账号配置或运行产物。
- 读取、检查和修改现有配置时，以用户明确指定的文件或目录为范围。文件的位置不决定其新旧或用途，不因更新规则而扩大扫描、批量修正、移动或改名范围。
- 文件名、内部配置名、JST 日期和频次统一遵守 [命名规则.md](命名规则.md)。
- 文件名不写任务 API ID、wikiwiki 编号或攻略编号；运行时 `接任务` 仍保存精确游戏 `api_no`。
- 不创建只放任务名的空配置，不默认创建 `预编成` 或 `收尾`。
- 交付仅包含用户要求的配置和必要使用说明。临时调查数据、一次性生成脚本等保存到本次明确指定的私人位置，不混入交付结果。

## 先判定任务类型

必须读取完整任务详情，不能按标题猜类型：

- 只要求组成指定舰队：编成流程。
- 要求与演习对手交战：演习流程。
- 要求进入海域、到达节点或取得海域战斗胜利：出击流程。
- 远征、工厂、改装、补给/入渠使用对应类型，不借用出击或演习总控。

任务详情包含多个动作时，以真正触发完成判定的动作选择专用规则。仍无法分类时停止生成并向用户确认。

## 任务 ID、频次与条件

### 游戏任务 ID

任务 `api_no` 必须来自当前 poi/KCPS 缓存的 `api_get_member/questlist`，不得从 wikiwiki 的字母编号、攻略编号、年份规律或文件名推断。

```powershell
$SKILL_ROOT = '<SKILL_ROOT>'
$WORKSPACE_ROOT = '<WORKSPACE_ROOT>'
$env:KCPS_WORKSPACE = $WORKSPACE_ROOT
. (Join-Path $SKILL_ROOT 'scripts\poi-kcps-api\KCPS-Common.ps1')
$quests = Get-PoiQuestList
$quests.api_list |
    Where-Object { $_.api_title -like '*任务标题关键词*' -or $_.api_detail -like '*任务详情关键词*' } |
    Select-Object api_no, api_category, api_type, api_state, api_progress_flag, api_title, api_detail
```

- `api_state = 2` 表示遂行中，`api_state = 1` 表示可接受；两者都能用于确认 ID。
- 当前缓存页查不到时，先刷新游戏任务页的 `All`、`遂行中` 或对应分类/页码再查。截图显示存在而缓存没有时，不得直接断言任务不存在。
- 新实装任务可能沿用旧 ID，而缓存详情暂时仍是更新前文本。ID 和标题用游戏 API 核对，最新条件用游戏画面与日文 wikiwiki 交叉验证，并把差异写入 `说明`。
- 无法从游戏 API 确认 ID 时，拒绝生成可运行任务配置。任务已经接受也必须保留 `接任务`。

`接任务`统一使用精确 ID：`SelectMethod = 0`、`SelectValue = api_no`、`FailIfNotExist = true`、`FailIfAccepted = false`、`SuccessIfFull = false`。`Quests` 始终是数组。任务栏满时不能假装接取成功；是否替换低优先级任务由任务时限和用户要求决定。

### 频次

频次不能由“期間限定”、任务标题、任务 ID 或前置关系推断。游戏重置类型与日文 wikiwiki 频次栏必须交叉确认；不确定标记、来源记录和更名规则见 [命名规则.md](命名规则.md)。

### 条件

- 任务条件优先以当前游戏显示和日文 wikiwiki 为准。
- 攻略站可补充新任务暂缺资料，但必须与游戏 API、日文 wikiwiki 或社群常用数据工具交叉验证。
- 账号中的船、装备、任务状态、舰队、入渠和远征占用必须读取当前 poi/KCPS 数据，不凭记忆。
- 任何信息不完整、来源冲突或推测都必须写入 `说明`；无法确认安全关键字段时拒绝生成可运行配置。

## 当前账号状态

```powershell
pwsh -ExecutionPolicy Bypass -File (Join-Path $SKILL_ROOT 'scripts\poi-kcps-api\inspect\KCPS-State.ps1') -QuestIds <QUEST_ID>
pwsh -ExecutionPolicy Bypass -File (Join-Path $SKILL_ROOT 'scripts\poi-kcps-api\inspect\KCPS-Inventory.ps1') -ShipPatterns '<SHIP_REGEX>' -EquipPatterns '<EQUIP_REGEX>'
```

- 船按真实实例 ID 选择，核对改装谱系、所在舰队、远征、入渠、血量和任务资格。
- 装备核对总数、改修等级、锁定状态、当前持有者和远征占用。`Deprive = Allowed` 也无法取得正在远征船携带的装备。
- 临时占用不能成为永久降低正确编成或配装标准的理由；应报告当前不能立即启动、等待占用解除或选择经过验证的等价候选。
- 任务要求、路线、顺序、配装和当前可用性必须一起推演，不能先拍定编成再机械塞装备。

### 改装槽位

- 按最终选中的实例及当前改造形态核对 `api_slotnum` 与主数据 `api_slot_num`；`api_slot`、`api_maxeq` 数组可能补齐到五项，长度不是实际主槽数。两种槽数冲突或数据缺失时不得视为验证通过。
- 同时检查“实际槽是否配齐”和“写出的槽是否存在”。主槽编号为1～5，补强槽独立使用6；`api_slot_ex=0` 表示未开放，`-1` 表示已开放但空槽，正数表示已装备。未开放补强槽不得必装。
- 活动固定实例应删除不存在的主槽配装，不能用 `IgnoreSlotNotAvailable=true` 掩盖错误形态。通用轮换候选可以保留可跳过的第四、第五槽；按位置改装必须匹配同一总控策略关联的编成分支，不能交叉套用另一分支或当前舰队的槽数。
- `KCPS-ValidateConfig.ps1` 与活动专项校验共用 `KCPS-RefitSlots.ps1`，槽位错误必须阻断最终化。批量复查使用 `validate/KCPS-AuditRefitSlots.ps1 -Path <WORKSPACE_ROOT> -FailOnProblems`。

## 通用执行单元规则

- 说明性质的 `MemoWorkflow` 必须是每个配置的第一个执行单元：普通配置命名为 `说明`，活动出击配置按活动专用规则命名为 `备注`。整理、补全或重写执行单元列表后必须重新检查首项，不能把它移到末尾。
- 配置中存在名为 `总控` 的关联执行单元时，它必须紧跟说明性质的 `MemoWorkflow`，成为第二个执行单元。总控关联的接任务、抑制消息、编成、改装等被调用单元都排在总控之后；调用先后由总控内的关联列表决定，不得用执行单元显示顺序倒置总控与被调用单元。
- 每个执行单元写非空、与实际字段一致的 `Memo`。
- 所有战斗策略备注只使用中文，不得中日混写或用英文句子代替中文说明。该规则覆盖出击的默认策略、Boss战专用策略、地图点条件策略，以及演习的默认策略和条件策略。地图节点字母、数字、`P1/P2/P3`、胜利等级、`PT`、`Boss` 等必要游戏标识可以保留；外国舰船名称在备注中使用通行中文译名，配置选择器和舰船ID仍使用游戏原名。
- 海域最终目标统一称 `Boss`，节点或战斗类型写作 `Boss点`、`Boss战`、`Boss水面战`、`Boss混成战`。禁止在新配置和说明中使用“首领”“首领战”“首领水面战”。
- 使用新的 GUID；同一配置内的引用同步更新，避免多个配置同时加载时冲突。删除或替换执行单元时，必须遍历所有单引用与关联集合并移除旧 GUID；任何悬空 workflow 引用都属于不可交付的硬错误。
- `TriggerOnEnabled = false`，默认不勾选“启用时立即触发”。
- `EnableOnLoad` 不能统一硬套：出击链监听总控与普通执行单元不同，按专用规则设置。
- 所有关联阈值不得超过实际启用且会发出对应阶段完成事件的执行单元数量。
- 不使用跨配置原生 GUID 串联；需要跨配置推进时只使用对应专用规则已验证的消息机制。

## JSON 结构

执行单元的 `Type` 必须保留完整程序集限定名，包括可解析的 `Version=...`。KCPS 在反序列化前先读取该版本，只有类名和程序集名的缩写会导致单元被跳过。新增同程序集单元时可从有效模板或已有单元保留程序集标识并替换类名，不凭当前日期猜版本，也不随意升级既有版本。

KCPS 模型声明为集合的字段即使只有一项也必须序列化为 JSON 数组。常见字段包括：

`Quests`、`ConditionalStrategies`、`Positions`、`Selections`、`SelectShipArgs`、`Ships`、`Slots`、`Equipments`、`Strategies`、`AreaClearBonusSelections` 及所有关联 workflow 集合。

- 不得把数组缩成单个对象，否则会触发 `Cannot deserialize ... into ObservableCollection`。
- `DefaultStrategy` 等模型定义为单对象的字段不能反过来写成数组。
- `RelationalSortieWorkflow.SortieWorkflow` 必须写成关联对象：`{"Guid":"出击执行单元GUID","Enabled":true,"IgnoreTriggerFailure":false}`，不得简写成GUID字符串或数组。校验必须同时检查原生载入格式、字段类型、启用状态以及同配置内唯一的 `SimpleSortieWorkflow` 目标；仅检查GUID存在不足以保证总控可载入。KCPS会跳过反序列化失败的执行单元，因此“文件里有总控”不等于“载入后有总控”。
- 可空未限制字段按 KCPS 实际往返形态保存；不要把 `null` 和空数组来回改写造成收尾脚本不幂等。

通用结构工具：

```powershell
pwsh -ExecutionPolicy Bypass -File (Join-Path $SKILL_ROOT 'scripts\poi-kcps-api\normalize\KCPS-NormalizeRelatedWorkflowCollections.ps1') -Path '<CONFIG_PATH>'
pwsh -ExecutionPolicy Bypass -File (Join-Path $SKILL_ROOT 'scripts\poi-kcps-api\normalize\KCPS-NormalizeWorkflowOrder.ps1') -Path '<CONFIG_PATH>'
pwsh -ExecutionPolicy Bypass -File (Join-Path $SKILL_ROOT 'scripts\poi-kcps-api\validate\KCPS-ValidateNaming.ps1') -Path '<CONFIG_PATH>'
```

## 说明/备注执行单元

通用最低内容：

- 游戏 `api_no`、准确标题、任务类型和完成条件。
- `【频次依据】`：频次、来源 URL、JST 查证日期；不确定时写明原因并同步使用 `（不确定）` 命名。
- 实际选择的船、资格、顺序理由和当前占用风险。
- 使用装备时写明关键装备分配、库存限制及替代影响。
- API、游戏画面、日文 wikiwiki 或攻略资料存在差异时写清采用哪个结论及原因。
- 自动流程的起点、停止条件、需要用户手动操作的部分和已知限制。

`说明`是实际配置字段的摘要，不是独立散文。修改编成、改装、条件、次数或流程时必须同步更新；按本次目标、资源预算和风险偏好解释取舍；降低成本可以是合理目标，但不能省略任务条件、路线或装备可用性的核验。

## 交付与验证

出击、演习和编成各有对应的 `KCPS-Finalize*Config.ps1`。这三类配置的交付流程固定为：

1. 对最终文件运行一次收尾脚本，应用确定性修正。
2. 再运行同一脚本的 `-CheckOnly`。
3. 只有 `Ready = true`、`PendingChangeCount = 0`，且通用、命名、任务 ID 和类型专用问题数均为 0 才能交付。
4. 新任务不得使用 `-SkipQuestValidation`。它只用于任务完成后已从当前列表消失的历史结构审计，并且不能声称实时任务 ID 已验证。
5. `ProblemCount = 0` 只证明脚本覆盖的机器规则通过；无法机器证明的任务条件、战术、路线或配装仍按专用规则人工复核。
6. 按用户授权范围检查最终文件；用户要求批量复查时，以明确指定的目录为边界，排除 Skill、工作文件和备份，不因生成单个任务而自动修改其他配置。
