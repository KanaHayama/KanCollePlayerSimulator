用这份规则指导 Agent 生成、修复或审计可直接加载的 KCPS 演习任务 `.conf.json`。

开始前必须阅读 [公共规则.md](公共规则.md) 和 [命名规则.md](命名规则.md)。任务实际是出击时改用 [通常出击配置.md](通常出击配置.md)，实际是纯编成时改用 [编成配置.md](编成配置.md)；三者共用 `../scripts/poi-kcps-api` 工具。

## 演习输出差异

- 种类固定为中文 `演习`；文件名为 `<JST_YYYYMMDD> <频次> 演习 <任务名>.conf.json`，配置名为 `<频次> 演习 <任务名>`。
- 一个演习任务通常只建立一个配置，不带海域或地图阶段后缀。
- 其余输出位置、JST、频次证据、文件卫生和术语遵守公共规则。

## 严格区分演习与出击

演习配置使用 `RelationalExerciseWorkflow`，不得因为模板相似而加入以下出击专用内容：

- `RelationalSortieWorkflow`、`SimpleSortieWorkflow`。
- 海域、路线、地图点、阵型节点表、进击/撤退、带路、索敌、制空路线门槛。
- 陆航、陆航休息、出击后扔桶、通知通关、跨海域 `UserEvent`。
- 出击疲劳轮换和活动海域贴条规则。

演习仍需决定普通对手和潜水对手的阵型、夜战、舰船顺序及配装，但依据是演习对手类型，不是地图点。

如果任务完整详情只要求“编成”“配備”指定舰队，后续没有“同艦隊で演習”等演习动作，它是纯编成任务，应改用同目录的 `编成配置.md`。不得仅凭标题含“編成”或指定了多艘船，就擅自补出演习胜利条件。

## 先确认任务

先按公共规则确认游戏 `api_no`、频次和当前详情，再专门确认指定船、允许的改装后形态、胜利等级、次数、是否要求“本日中”和刷新时刻。

- API 与最新游戏画面/日文 wikiwiki 条件不一致时，按公共规则保留差异证据，不能悄悄使用旧演习文本。
- 任务当前已接受也保留 `接任务`；`Quests` 的数组形状和接取失败策略遵守公共规则。

## 调查账号状态

先按公共规则查询船、舰队、装备和占用，再处理演习特有决策：

- 固定唯一候选不能依赖出击配置的疲劳轮换。
- 任务只要求五艘时，第六位用于补足最需要的能力：水上高甲对手可用强战舰，潜水对手可考虑反潜轻空母或其他强反潜船。编成与两种对手策略一起推演。

## 配置结构

一个演习任务通常只建一个配置。推荐执行单元顺序：

1. `说明`：`MemoWorkflow`
2. `总控`：`RelationalExerciseWorkflow`
3. `接任务`：`BasicAcceptQuestWorkflow`
4. `编成`：`BasicOrganizeFleetWorkflow`
5. `改装`：`BasicRefitEquipmentWorkflow`
6. `补给`：`BasicSupplyFleetWorkflow`

不要创建只放任务名的空配置，不加 `收尾`，不默认加 `预编成`。

`RelationalExerciseWorkflow` 的演习前固定顺序是：编成、改装、入渠、补给。因此演习总控中的入渠不能在编成前捞出正在修复的固定候选，也不能在改装前解决入渠占用。除非已验证流程目的，否则不要套用出击配置的 `捞出`/`扔桶`。

执行单元通用字段、GUID、Memo 和触发设置遵守公共规则；本配置所有执行单元的 `EnableOnLoad = false`。

## 编成决策

先整体推演指定船、自由位、顺序、装备、对手类型和夜战，再落 JSON：

1. 先满足指定船数量、旗舰/位置限制和允许改装谱系。
2. 自由位优先补足水上清场或反潜短板，不机械复制旧演习阵容。
3. 强力水上输出通常放旗舰，提高保护和昼战稳定性。
4. 夜战顺序让较弱船先清理、可靠终结者靠后；若主要输出船不能夜战，不要让它占据需要夜战收尾的位置而不解释。
5. 若普通对手与潜水对手需要完全不同的自由位或装备，可建立独立的 `潜水编成`/`潜水改装`，由潜水条件策略引用。结合本次目标、维护成本和对手差异决定是否拆分，并说明取舍。

固定唯一候选时，六个位置都写实际船 ID。除非用户明确要求轮换，不要把出击配置的同型船疲劳轮换逻辑复制进演习。

## 精确配装

- 每个常规槽写一个精确装备名，不使用只按类型的模糊选择。
- 根据船的装备加成、改修等级、可装备槽、装备数量和全队职责分配上位装备。
- 比较上位替换时计入船补正、隐藏值、库存保留和准备成本，按本次目标与资源预算选择。
- 相同装备数量不足时，把高改修或唯一上位装备给收益最大的船；利用 `Ships`/`Slots` 顺序和 `LevelPriority` 控制分配。
- 所有常规槽必须填满。每艘船都写 slot 6 补强增设策略；默认假定已开放，`IgnoreSlotNotAvailable = true`，未开放时安全跳过。
- 补强增设必须用实时 `api_mst_equip_exslot`/`api_mst_equip_exslot_ship` 兼容数据校验，不能因某装备不是全船通用就一概禁用。
- 普通水上对手需要夜战稳定性时，驱逐舰可用主炮/主炮/声呐的折中配置；潜水对手明显较强时应改成完整反潜套装，而不是只写一句“海域简单”。
- 不默认使用消耗品。

配装后运行：

```powershell
pwsh -ExecutionPolicy Bypass -File (Join-Path $SKILL_ROOT 'scripts\poi-kcps-api\inspect\KCPS-AuditFit.ps1') -Path '<CONFIG_PATH>'
```

## 对手选择与策略

总控可用 Python `OnPick(candidates)` 优先选尚未演习且最容易的对手。稳妥评分可综合：舰船数、总等级、最高等级；脚本必须是 KCPS IronPython，禁止写 JavaScript 的 `function OnEvent(...) {}` 语法。

至少设计两类策略：

- 普通水上对手：通常单纵阵。任务要求 A/S 胜时，根据舰队夜战能力决定是否进入夜战，不能机械照抄“不夜战”。
- 潜水船占半数以上：条件类型使用潜水比例，常用阈值 `50`；通常单横阵且不夜战。若采用其他阵型，必须说明计算依据。

`ConditionalStrategies` 必须为数组，`DefaultStrategy` 必须为对象。普通和潜水策略分别关联正确的编成、改装和补给执行单元，关联阈值不得超过实际启用的引用数。

## 评级停止陷阱

当前已验证版本的评级停止行为会把 B/C 等较低评级误计入“A以上3次”。

在该行为修正前：

- 必须设置 `StopIfBattleRankHigherOrEqualThanFlag = false`。
- 用 `StopIfExecuteCountLargerOrEqualThanFlag = true` 和合理场次上限控制执行。
- 在 `说明` 中写清楚任务所需胜利次数、配置最多执行场数，以及低于要求时需要重新启用补打。
- 不得把“校验器通过”误写成“保证三场都达到 A/S”；成功率来自舰队、配装和优先选择弱对手。

此限制依赖 KCPS 版本。升级后先核对当前版本的评级停止行为，未经验证时仍按上述方式处理。

## 说明执行单元

`说明`必须放在最前面，并至少写：

- 公共规则要求的任务、频次、来源、船和流程信息。
- 指定船、胜利等级和次数。
- 实际编成和自由位理由。
- 普通/潜水对手的阵型、夜战和配装差异。
- 装备被远征占用时的替代方案或生成时状态。
- 自动停止采用场次而非评级计数的原因。

说明配装如何满足本次胜利目标及资源预算，并记录成功率、成本与准备时间的取舍；不能用笼统评价代替必要条件核验。

## JSON 与交付检查

先满足公共 JSON 数组与幂等规则；演习还要重点检查 `ConditionalStrategies` 是数组、`DefaultStrategy` 是对象，以及普通/潜水策略引用的执行单元和阈值一致。

生成后使用共用收尾脚本：

```powershell
pwsh -ExecutionPolicy Bypass -File (Join-Path $SKILL_ROOT 'scripts\poi-kcps-api\validate\KCPS-FinalizeExerciseConfig.ps1') -Path '<CONFIG_PATH>'
pwsh -ExecutionPolicy Bypass -File (Join-Path $SKILL_ROOT 'scripts\poi-kcps-api\validate\KCPS-FinalizeExerciseConfig.ps1') -Path '<CONFIG_PATH>' -CheckOnly
```

交付必须满足：

- 第二次 `-CheckOnly` 的 `Ready = true`、`PendingChangeCount = 0`。
- 通用配置、任务 ID、演习专用和配装审计问题数均为 0。
- 没有出击 workflow，没有启用时立即触发，没有评级停止陷阱。
- 六个位置、六艘改装对象和所有装备槽一致；所需装备当前可调用数量足够。
- 文件卫生符合公共规则。
